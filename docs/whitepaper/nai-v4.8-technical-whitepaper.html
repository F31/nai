01摘要

这套系统的工程核心不是「把模型接进来」，而是把「什么内容允许出门」变成一条每一步都能被否证的路径。

直播现场最常见的失败，不是 AI 不够聪明，而是失控：说错了版本、抢了主播的话、被要求停下却停不住、把成本花在没人在意的段落上、事后无法说清到底播出了什么。数字人产品又常把两件事混为一谈——「外观像真人」和「能被授权地在正确时刻说正确的话」是两种能力，前者不蕴含后者。

V4.8 的取舍因此很明确：

把授权做成主链

所有观众可见内容只经一个逻辑出口（DeliveryGate）；模型、模板、缓存、预生成素材都必须过同一组门。没有「这次特殊，直接播」。

把完成做成证据

生成成功、HTTP 202、TTS 返回、平台受理，都不是完成。完成指对应目标的实际播放/发送/动作 ACK，且不等于观众理解或问题解决。

把停止做成不变量

P0 静音与撤权不依赖数据库、云连接或普通队列；先停，再补审计。撤销是收紧许可，不是撤回已经发生的物理事实。

把不确定留在「不确定」

结果未知、影响未知、回执缺失，都有独立取值与处置路径。系统不允许把「没量到」写成「没有」，也不允许把「可能已发送」重发一次。

代价是复杂度，本文不掩盖它：62 条不变量、两道互不通用的门、三套分开的生命周期、五层输出证据、四种运行策略。这些不是装饰，每一条都对应一次真实可能的事故形态。下文按「一条评论如何变成一次上屏」的顺序展开，再向上讲治理、向下讲工程与预算。

阅读约定。「必须」指契约或不变量；「初值 / 目标」需要实测；「假设」需要客户验证；「待认证」的能力不得在 UI 上显示为可用。 本文所有图示为设计意图的表达，不是运行截图。

02问题：直播创作的成本结构

要证明「更省事」，先得把「事」拆成可计量的四段。

一场常规的产品讲解直播，成本集中在四段，且它们互相污染：

成本段具体形态现有工具的切面交接处丢掉了什么
备播从资料到一份能预演的节目单；反复核对价格、限制、口径提词器、文档、素材文件夹改动没有回写到「下一场」
临场找资料、切工具、判断这条问题该不该接人工场控 + 聊天窗口判断依据不留在记录里
版本价格 / 活动 / 权限变化后，哪一段话术已经错了人工比对与记忆影响面无人计算，只能「都重录一遍」
接续答不上来的问题去哪了、谁接手、接了什么上下文口头交接、聊天记录传输成功被当成「已解决」

数字人类产品另有两处常见错位，本文刻意避开：把「无人连续直播」当作卖点（平台用途许可、值守责任、内容风险都不支持这个承诺）；把渲染质量当作全部价值（观众能看出「好看」，但留不住人的是内容与回应是否相关）。

因此本方案对比的基线不是「其他 avatar 厂商」，而是客户今天的直播工具栈：提词器 + FAQ 文档 + 素材文件夹 + 人工场控流程。

03定位与三条边界

产品身份由「谁最终负责」决定，而不是由「模型有多强」决定。

一句话定位：给有真人值守的直播团队一个会备内容、帮接问题、懂节目进度、能协同数字人的直播助手工作台。数字人提供可辨识的表达角色，智能体帮助把场景与内容连接起来，主播决定何时呈现、何时接管。

边界一：真人持有主持权

主持权是显式状态，切换记录 epoch 并终止旧输出与工具任务。VAD 触发、网络心跳、模型建议都不能授予自动外发权限。

边界二：智能体只产出候选

意图、话术、建议、复盘修订都是候选。采纳是人的动作；采纳后仍走对应的输出门，不因为「用户点了同意」就继承旧批准。

边界三：数字人只呈现获准内容

批准绑定到最终呈现身份（文本 hash、素材、表演计划与工件 digest），换人、换模型、换表情范围都使批准失效。

默认行为：Assisted

AutoSupervised 需要同时满足渠道规则、用途权限、风险策略、值守与依赖，不因订阅档位自动开放。

价值如何被计量

「更省事」必须落到可测的人工分钟与错误率上，同时接受约束项，避免把指标做漂亮：

价值测量必须同时报告的约束
更快备播从已有资料到可预演节目单的实际人工分钟计入核对、素材整理与反复修改
更从容控场寻找资料 / 切换工具次数、误操作、有效辅助率不把「接管少」当成绝对好事
内容更连贯重复与打断错误、断点恢复、节目完成质量安静展示与真人主持不是故障
互动有用合格问题处理率、问题到输出/转人工的时间覆盖率、错误率、队列过期率同时报告
越用越省事下场复用率、编辑量、准备时间变化记录维护新资产的额外成本

不承诺流量、成交增长、平台审核通过或取代全部主播。成交与停留等结果只在取得获准真实数据时观察，不能由工具事件推算。

三个维度不能互相顶替

档位（Lite / Standard / Pro）只决定默认能力包。部署形态（Local / Hybrid / Distributed）、呈现形态（ContentOnly / Voice / Avatar / HumanAssist）、行为模式（Rehearsal / Assisted / AutoSupervised）各自独立解析。Pro 不强制上云，Standard 不强制写实，Lite 不因为「轻」就缺少闭环——三档同内核，Lite 可一键直升。

04系统总览：进程与门控

逻辑上只有一条授权主链；物理上却是若干可以独立失败、独立停止的进程。把这两件事画在一起，架构才说得清。

进程职责与故障后果

进程职责故障边界（实际会发生什么）
engine核心机制、领域模块、知识/Provider、两个门、授权、状态与日志失联后 keeper 到租约截止静音；恢复只到待机，不自动续播
output-keeper音频设备与混音、已批准安全画面、最小合成与标识、租约 / P0 / ACK不加载模型、Provider 与第三方解码器；自身崩溃仍会中断出画，不承诺无缝
media-worker2D / ONNX / 3D 渲染，帧与 PCM 通道普通崩溃不直接带走 keeper；驱动或整机故障另行验证
platform-bridge必要的官方 SDK / C++ 薄桥接平台失联即撤销相应自动权限，不伪造事件补播
voice-input-worker可选 ASR / VAD / 回声处理只在启用语音指令时存在；不进直播主链的必备依赖
supervisor / update-helper限次重启、维护窗口替换极小的体量；不继承旧的自动授权

为什么 engine 不拆成微服务

领域模块（内容、节目、表演、商务、交接）在同一个进程内按端口组合，理由是可验证的：这些模块之间是事务与判定的紧耦合（发布事务要同时写快照、依赖与审计；批准要在一个事务里校验角色、bundle hash、版本与过期时间）。拆成服务后这些判定会退化为跨服务补偿，而补偿无法保证「撤销先于通知」。

真正需要独立进程的是故障隔离与权限边界：媒体设备、GPU 模型、不可信原生 SDK。这三类不省进程，也不因省 RSS 合并进内核。

Lite 的实际形态。不启动独立数据库、向量库或消息中间件；SQLite + 文件型对象仓 + 可重建索引即可。Standard 的写实 + 本地语音指令 + 轻量平台事件的候选拓扑是五个应用进程（desktop / engine / media-worker / voice-input-worker / keeper），WebView、驱动、OBS 等外部子进程另计——不能用「五个进程」宣称整机只有五个。

05主链：从一条评论到一次上屏

这条链上每一个箭头都是一次「可以拒绝」的机会；链的价值不在通畅，而在该断的地方真的会断。

准入先于花钱

问题池保存已获准来源的事件、主题、与当前对象的相关性、去重键、时效与风险、处理状态与责任人。三条硬规则：未入选不发起付费模型调用；来源未给人数时只报事件数；过期候选取消生成与合成，迟到结果直接丢弃，不在话题变化后补播。

调度是规则优先的：P0 静音/撤销 > 人工点播 > 关键节目 > 相关问题 > 合并感谢 > 寒暄。语音债务（当前剩余 + 待播时长）初值最多 2 条待播、20 秒待播、单答 20–40 字、一般不超过 60 字；每分钟约 30 秒的互动预算意味着只能容纳约 3 条短答——所以不能用模型 QPS 承诺直播响应能力。

四道 guard 各管什么

阶段要回答的问题失败时的合法结局
输入来源是否可信、作用域是否覆盖当前对象？外部文本、文档、工具返回是否被当成指令？拒答或降级为私有提示，不解释为「模型不确定」
证据结论是否被引用支持？数字、单位、条件、否定项是否逐项核对？标注待补 / 转人工；不允许截掉否定条件后继续回答
输出目标对象、版本、范围内表达是否正确？是否越过禁用声明？改用已批准替代候选，或放弃本次
交付前许可、epoch、批准 hash、撤销水位是否仍然有效？拦截；已提交的外部副作用转入核对

关键点：模板跳生成，不跳门控。缓存命中、语义命中、预生成音频都走同一组检查，因为它们省的是钱，不是责任。

「完成」分为五层

输出证据是分层的，且后层缺失时前层不得冒充：本地帧/播放 → 设备或宿主接收 → 推流服务器接收 → 平台直播状态 → 获准观众端实看。每层都带 request/stream id、时间与版本；没有后层证据就保持 unknown。静音工作台、停 OBS、停流、结束平台直播是四条不同授权命令，不能被一个「停止成功」合并。

06状态、许可与停止

系统的可靠性不体现在「从不失败」，而体现在任何时刻都能回答三个问题：现在处于哪个状态、谁还有许可、停止要走哪条路。

三套生命周期必须分开

维度状态典型误用
会话Created → Preparing → Ready / ReadyDegraded → Running → Draining → Stopped，严重错误 Faulted用「房间已开始」推断自动模式已开启
行为Rehearsal / Assisted / AutoSupervised用订阅档位推断可以无人值守
媒体Standby / Buffering / Playing / Muted / DeviceLost / Failed用「音频设备在播」推断观众听到了

三者任一维度的绿灯都不能顶替另一维度。这也是 UI 禁止「伪成功」的技术根源：待设备 ACK、已播放、平台可见、观众理解，是四个不同状态。

租约：用时间换取确定性

播放许可是短期、只允许指定 bundle 与输出通道的令牌。初值为 200ms 续租、600ms 截止，具体数值按设备缓冲实测调整。这个设计的意义是：当 engine 卡死、网络断开或数据库锁住时，keeper 不需要判断「是不是该停」，只需要判断「许可是否过期」。

两条方向相反的持久化规则：扩大授权先持久化（避免授权失效后仍被使用）；撤销与静音先执行、后补审计（避免卡在数据库上停不下来）。P0 鉴权后不因过时 revision 拒绝，幂等报告实际结果。

「取消」与「撤销」不是一回事。取消是阻止未提交的事情发生；撤销是试图影响已经发生的物理事实。前者本机可控，后者取决于平台是否真的支持——因此撤销必须形成新的独立意图、风险、批准与幂等身份，不能称为本地回滚。

值守不能靠心跳

自动值守租约由人主动确认，网络心跳不能证明有人在。桌面存在有效值守时，手机失联不应误判为「无人」。重连不恢复旧权限、不重放过期命令、不因为连接恢复就认为交接已被接收。

07智能体 Harness：上下文、任务与建议

「更懂你」如果不由授权与预算约束，就会变成「更敢说」。

装配顺序是固定的

每次模型调用按同一顺序装配，顺序本身就是一种安全机制：

  1. 安全约束（不可裁）
  2. 人设 / 场景（不可裁）
  3. 任务与输出 Schema（不可裁）
  4. 当前事件与状态（LiveContext 有界快照）
  5. 必要事实与证据
  6. 获准记忆
  7. 相关技能（初值 ≤ 5 条）
  8. 已交付历史（注明证据类型）
  9. 不可信工具返回（标记为数据，不是指令）

前 3 段不可裁。必要事实容纳不下时，拒绝该路径，而不是截掉否定条件或优惠限制后继续回答。上下文片段带来源、作用域、数据/指令标记、revision 与 TTL；日志记录片段 ID、hash、预算与裁剪原因，因此在合法保留 payload 存在时可以完整回放，删除后明确「不可完整回放」。

四类任务，一个 Harness

任务触发与输入产物执行方式
备播人发起 / 复用；产品包与目标节目草稿、候选话术、缺项清单非实时、可取消，发布前人工核对
互动筛选后的有效问题；LiveContext 与证据短答、依据、素材候选、转专家建议实时短路径，按授权呈现
场控实际进度、队列、主持状态下一步 / 重复 / 超时建议规则先行，按需模型解释，默认私有
复盘人发起；真实运行记录问题摘要、具体修订、下场草稿低优先异步，有费用上限，不自动发布

四者是任务 profile，不是四个常驻进程、也不是四轮模型互聊。内核的授权、调度与费用共用；模型不能通过「换一个 Agent」获得更高权限。委派（delegation）作为 Preview 能力存在，硬上限为深度 1、并发 2、整棵树工具/模型调用合计 8，且子任务权限取父权限、配置权限与任务需要的交集——不能扩大，也不能重新委派更深。

建议的频控是产品的一部分

初始值：最多 3 张显著卡、同类建议 30 秒冷却、每分钟至多 2 条非紧急主动提示。安全阻断不受普通建议冷却影响。主播可以忽略、静默某类、只看问答或关闭主动建议；采纳后记录动作与实际输出，拒绝后可选反馈理由——不弹问卷打断直播。

「越用越懂」被拆成四层：本场临时进度 / 产品事实与 FAQ / 主持明确保存的表达偏好 / 团队审核过的节目经验。只有明确采纳或审核才进入持久资产；跨场读取受权利、ACL、来源、有效期与预算约束。不自动训练、不秘密分析观众画像、不把高互动推断成真实性。

一个反直觉的取舍：系统宁可「少建议」，也不靠隐藏风险来降低拒绝率。曝光、采纳与有效完成是三个分开的指标——只优化采纳率，最省事的办法是不提示风险，而这恰好是最坏的结果。

08表演子系统：意图、计划与门控

数字人不是「一个模型」，而是五条轨、一个计划身份、一组区域所有权规则，以及一个随时可以被打断的执行器。

五种 profile，各自声明边界

Profile输出推荐用途明确不保证
sprite-lite2D 帧 / 有限嘴型低资源、预演、轻量助播写实、精确音素、任意全身动作
photoreal-video真人底版视频 + 实时嘴部 / 有限表情写实讲解、应答、动作片段从单张脸任意转身、拿物、跳新舞
neural-portrait生成式肖像帧表情 / 头动质量对照，独立高配包任意全身动作、单卡全档位实时
rigged-3d骨骼人物 + 表情 / 动作参数 → 渲染帧手势、舞蹈、姿态与镜头控制无资产制作即达到真人拍摄质感
remote-avatar外部 API 流 / 帧可选服务替换与专项配置低费用、任意动作、数据不出机

区域所有权：一个可变区域只有一个 owner

嘴部默认归口型轨，眉眼归获准的表情轨，身体归动作轨。若某后端只能输出整帧，则不允许其他后端再叠加面部系数——只能通过整体模式切换或预制素材切换。这条规则的直接后果：MuseTalk 与 LivePortrait 不是默认串联组件，必须独立验证区域冲突与身份一致性后才能组合。

优先级是硬编码的：P0 / 撤销 → 真人接管 → 已提交的短安全边界 → 人工动作 → 已批准节目动作 → 自动装饰动作。动作冲突只有三种结局：拒绝、排队（有界）、在安全边界中止。

动作的三种「可用」

注册表里有这个动作 ≠ 资源已 Ready ≠ 本场已获准执行。未知动作返回 UnsupportedAction，可以建议已支持的替代，但不得用「点头」冒充「跳舞」；反之，声称支持挥手或跳舞的 profile，必须另有实际动作的正向验收——不能用「正确拒绝」冒充「效果通过」。

四种运行策略，不许互相冒充

RuntimePolicy允许禁止 / 失败语义
NativeOnnx（默认写实目标）Rust + ONNX Runtime 与受控原生算子桥，完整本地链路不运行 Python / PyTorch 服务；导出不全即 NotReady
NativeInterop（可选）独立 C++ / TensorRT / Unreal 等明确后端不宣传「纯 ONNX」，不静默替换严格 profile
Remote（可选）明示远端 API / 流、预算与上传政策不称本地推理，不称零云费用
ReferenceLab（研发工具）隔离的 Python 参考、导出、对齐、资产制作不进入生产 Ready 清单，不作为运行期旁路

认证分四关：G0 来源与许可（肖像、声线、素材、代码与模型）→ G1 参考与目标实现逐段 / 端到端对齐 → G2 目标机器并发直播 → G3 长播、取消、打断、设备、OOM、恢复与打包安装。G1 不要求不同路线像素相同：同模型迁移按 golden 特征 / 帧误差、口型与身份验证，跨路线用独立质量协议。

09事实治理与影响面

「改一个价格，哪几句话作废」——这个问题如果没有机械答案，内容治理就只是给人看的后台。

依赖图：不必是图数据库

以对象字段路径 + 事实版本为源，连接话术 AST 节点、演示步骤、素材声明、证据 chunk、CueBundle、缓存与活动会话。边记录 source/target/version、关系类型、发现方式（显式绑定 / 抽取建议 / 人工核对）、可靠性与更新时间。关系表加倒排索引即可实现——不引入图数据库，因为它解决的是查询形态，不是语义准确性问题。

结构化变量优先显式绑定；图片、录屏、自由文本中的内嵌参数可能无法精确提取，因此必须支持「素材事实声明 + 人工核对」。不能声称字段依赖天然覆盖所有视觉内容——这是设计里最诚实的一处留白。

处置矩阵（摘要）

变化 / 影响尚未执行正在执行已经播出
权限 / 权利撤销、已失效敏感承诺立即阻断相关包与自动路径立即收紧输出，切安全画面 / 转人工记录范围，评估通知与更正；不能撤回已听见内容
重要参数被判错（未列即时撤销类）按政策阻断待核，提供已批准替代按风险立即停止或在安全边界中断生成更正候选与关联证据，不自动对外道歉或承诺
一般有效版本更新标识旧版，在安全点选新 snapshot不热替换旧 bundle；边界切换需重新核验记录使用版本，不改写历史结果
表达 / 布局变化，事实未变按依赖核验后重新生成默认不打断无需误报事实事故

顺序是「先收紧、再清理」：有效期到期、权限撤销、被明确判错且必须停止的价格与活动，先收紧许可，再异步清索引与缓存。许可收紧不等通知送达；离线客户端重连必须先同步撤销水位才能恢复自动。部分失败不回滚已生效的撤销，未 ACK 的留在待处置——「已通知负责人」不是「风险已解除」。

知识分四层

层内容写入规则
KB0结构化权威事实（类型、条件、来源、有效期）只经发布流程写入；LLM 抽取与翻译均为草稿
KB1已发布说明 / FAQ / 条款负责人核对后发布
KB2语义索引（chunk + embedding + 归一化）由已发布正文派生，可重建
KB3第三方来源带 authority 与有效期，冲突策略逐字段确定，不一律「最新胜」

会话里的叙述不是权威事实，客户问题不自动进知识；局部沿用须有依赖证明——仅产品 ID 相同不足以复用缓存或批准。

10平台接入与证据分层

「能推流」「能收评论」「允许自动应答」是三件事，它们经常被同一段 demo 混为一谈。

四层分离

connector

获准事件、身份、房间。只做协议薄层，不在回调里跑模型。

output adapter

画音 / 流：preview、OBS、virtual-device、platform-sdk、RTMP / WebRTC 各自独立。

interaction policy

用途、事件类型、自动行为的许可。SDK demo 可运行不代表本产品账号已获准。

channel profile

把上面三者与认证条件绑在一起，带版本与期限。

目标事件路线输出候选缺条件时的默认行为
抖音官方互动工具 / 直播伴侣 SDK，或实际获准的服务端能力获准 SDK 素材通道、伴侣采集、OBS 衔接未获事件权限仅手工录入；用途 unknown 禁止相应自动

微信视频号待核实现行官方 / 合作接口与用途官方直播工具的实际可用采集入口无事件则手工问题与提词；无输出证据不标「已支持」

事件归一化（NormalizedEvent）必须带：schema 版本、平台与 product_id、app/connection、room/session、source_event_id、来源与接收时间、user_ref（带作用域）、类型、payload、数量语义（delta / cumulative / unknown）、权限快照、raw 引用与 replay 标记。ID 大整数用字符串；缺源 ID 时用来源范围 / 序号 + hash 做有限去重并标注可靠性——不承诺绝对去重。

礼物与点赞数量按 delta / cumulative / unknown 分别处理；动态礼物目录按接口取，不从旧网页硬编码价目；不把礼物金额作为放宽应答权限的理由。没有可靠个体身份时只做场次问题聚合，不跨平台按昵称合并观众。

回调不是必须的。只有必要时才部署网关：原 body 验签 → 重放与范围检查 → 持久 inbox → 按协议 ACK → 异步派发。本地工作站以主动出站为主；网关不跑模型、不保存全部原始内容。云网关需要时才启用，单实例起步资源须实测。

11安全模型：不变量与双门控

62 条不变量不是清单文学，每一条都对应一处「如果不写下来，实现时一定会走样」的地方。

两个门不共用一种回执

DeliveryGate 控制观众可见的文字与音视频，BusinessActionGate 控制有外部副作用的业务动作（发券、改活动、切讲解卡）。两者共享 guard、身份、撤销与批准机制，但不共用一种回执：讲解成功不证明优惠已发出，平台受理不等于业务完成，活动已创建不等于被领取。

组代表不变量它拦的是什么
授权与身份
INV-01/03/04/08/39		无渠道 / 用途 / 行为许可不外发；审批绑定 bundle hash、epoch、版本、范围与 TTL；旧 epoch 结果不得重播；重连不恢复「这次先播，权限回头补」
证明与门控
INV-02/18/20/29		AI / 模板 / 缓存 / 预生成同样过门；必需视觉就绪才 commit；完成以目标 ACK 为准；任意生产输出走 DeliveryGate用生成成功冒充「说对了」
停止与撤销
INV-06/07/34/58		本地 P0 独立于 engine / 云 / DB；新授权先持久化、撤销先执行后审计；停止对已交付与未交付分别报告「发个请求就当停了」
边界与隔离
INV-09/12/14/26/37		外部文本 / 工具 / Agent 无指令权；签名不等于安全；local_only 不外发；kernel 不依赖插件；私有提词与公共画面隔离把「本地库」当成「不出机」
商务与对账

呈现与形象
INV-41/42/44/46		动作只来自认证目录；同一区域单 owner；RuntimePolicy 真实；生成视觉按不可变计划批准宣称「逐帧审核过未来画面」

威胁与控制

威胁控制
提示注入 / 知识投毒结构化上下文、输出 Schema、权威来源分级、守门；工具返回标记为不可信数据
错误外发Bundle + 审批 + epoch + 租约；文字已发出不可用「静音」撤回

不能承诺的边界，必须写下来。四阶段语义检查不能证明生产零错误；引用存在也不证明结论被支持——敏感场景保留人工复核。管理员同机高权限、整机恶意软件、驱动或断电，属于应用层无法完全隔离的范围；决策链完整性不等于防篡改。声称「应用解决了全部」是这类系统最常见的不诚实。

计量口径要分开

压力下的降级顺序

GPU OOM：先关预览 / 降认证负载 → 取消句或待机 → 重启 worker → 预热体检；不在 OOM 时加载第二大模型。CPU / 内存压力：暂停索引与解析。API 配额压力：暂停后台 Embedding。新会话先查峰值显存 / 吞吐 / 设备 / API 总额，拒绝新场优于拖垮现有场。

预览与生产并发时，预览使用容量 2 帧的有界队列，落后丢旧保最新，不反压生产；初始策略为 ≤640×360、≤10fps、preview GPU 工作时间占预算 ≤10%，且不得持预览锁阻塞 keeper 与 P0。模型默认空闲 TTL 600 秒，从最后一个引用释放时起算；活动模型不被后台 TTL 强制杀死。

把风险写成「有一定挑战」等于没写。下面每一条都能指向一个具体的验证动作。

风险当前状态验证动作失败会怎样
