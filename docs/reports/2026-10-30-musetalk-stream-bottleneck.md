# 真人视频连续帧瓶颈与 GPU 打包实验

## 结果

在 25 FPS、60 秒、队列 8 帧上限、4 帧批次的本地模拟探针中，加入每批 CUDA 同步计时。第一次分阶段测量消费 1247 帧、欠帧 253，1256 帧生成中 UNet 累计 17.420 秒、VAE 解码及转 CPU 22.672 秒、融合 14.603 秒；解码/回传是该次最大单项。三个阶段为串行计时，但包含同步/探针开销，不能推断独立并行后的吞吐。

研究实验增加可选 `--gpu-pack`：解码后在 GPU 上转为 uint8 再回传，保留原计算顺序和 BGR。合成输入的 CPU 与 CUDA 两项逐字节等价测试通过；尚未对真实模型解码输出做逐帧视觉或二进制比较。60 秒启用时消费 1473 帧、欠帧 27；同一脚本随后关闭该选项、定位缓存命中时消费 1492 帧、欠帧 8。两次条件和系统状态未严格控制，启用时定位为冷缓存，GPU/电源/负载可能不同；不能声称该改动提速或导致欠帧变化。各轮启动即开始消费，头几次欠帧包含首帧生成。优化保持显式实验选项、默认关闭。

启用轮生成 1484 帧，UNet 13.387 秒、解码及打包/回传 25.992 秒、融合 11.210 秒；对照轮生成 1500 帧，UNet 16.172 秒、原解码/回传 26.490 秒、融合 13.939 秒。解码耗时含模型执行、数据转换和回传，不能单独归因于数据复制。各轮数据由 `stream-probe.json` 单独记录，进程显存峰值包括形象准备，冷/热缓存不同不能直接比较。

欠帧时原探针保留旧帧顺序，没有与真实语音做时间对齐；所有结果仅模拟帧消费，没有真实音频、OBS、直播或 10 分钟长稳。对照轮虽接近目标但仍有欠帧，不能宣称直播通过。

## 验证与后续

GPU 打包合成输入等价测试 2 项、队列测试 3 项、OpenSpec strict 通过。CodeGraph MCP transport closed，已直接查阅参考代码。没有调用模型 API、推流或更改用户资料。接下来需要更稳定的负载/温度与长时间测量，分开 GPU 解码计算、同步及主机传输的时间；围绕音频时钟建立明确过期帧策略和 bounded backpressure。若不能稳定达到门槛，应比较其他模型或服务。1.3.7 未闭环，正式宿主/许可及 OBS 验收均未完成。
