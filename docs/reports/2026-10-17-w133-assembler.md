`registry.yaml` 的 `H01`/`H02` 两条 notes 加起来近三千字，逐轮记着 W69 的判定面、W104/W106 的 runtime
接线、W127 的口径收紧。开工前**现测**，这些记录都是真的——但漏掉了一层：

```
grep -rn "AssemblyPlan" --include="*.rs" crates/ apps/ | grep -v tests

  nai-runtime/src/assembly.rs:180           plan: &AssemblyPlan      ← 消费
```

**没有任何一行构造它。** `record_assembly` 的入参是一份计划，而计划在生产代码里没有生产者：判定面
（`evaluate_assembly`，40 项）能判，执行体（落链、读回、只靠链重建）能写能读，但两者之间是空的。
仓库里每一份 `AssemblyPlan` 都诞生在测试里、也死在测试里 —— 「H01 已接线」描述的其实是一个
**没有调用方的函数体**。

四环落点：①判定面（W69 已建）→ ②执行体（W104/W106 已建）→ ③**调用方（本轮获得第一个真实入参）**
→ ④真实产生者（未接线）。

### 分组为什么不按原计划凑四条

开工设想是「H01–H04 装配与记忆」一组。勘定后**放弃了**：四条 notes 都写着「真实产生者未接线」，
但缺的东西**不同型** ——

| 条目 | 缺什么 | 本轮能否补 |
| --- | --- | --- |
| H01 / H02 | 一个**纯计算**的构造者（把候选装配成计划） | **能** |
| H03 / H04 | 「一次对话轮次**产生**一条记忆候选」的规则（需模型输出解析） | 不能，与 H16 同源 |

H03/H04 的控制面链已由 `apps/engine/src/lib.rs:327` 注入 `MemoryAdapter` 接通（现测），缺的只有上游。
硬凑成四条会让报告出现「四条都推进了」这类不实陈述 ⇒ 本轮只做 H01/H02，H03/H04 具名登记。

## 二、交付

### 装配器（`crates/nai-kernel/src/assemble.rs`，新建）

`plan_assembly` 把「按段分组的候选片段 + 调用方给定的逐段预算」装配成一份计划，只决定三件事：

1. **顺序** —— 施加 §41.1 的固定序列，不回显调用方的输入顺序。顺序存在的理由是「约束不被挤掉」，
   回显恰好丢掉这一点。
2. **在场** —— 调用方没给候选的段**不出现**，绝不补空切片。1–3 段必需，而「必需却缺席」是判定面
   该拒的（`UncroppableSegmentMissing`）；补一个空切片会让那条拒绝在真实路径上**没有对象可拒**。
3. **裁剪** —— 段内超预算从**尾部**裁，同时记录被裁项与原因；1–3 段任何预算都不裁，由此产生的
   超预算段原样输出，交判定面拒。

**零业务常量**：没有第二份九段表、没有可裁性表、没有默认预算。九段与顺序来自 `SEGMENT_ORDER`，
可裁性来自 `Segment::uncroppable`，每个上限来自调用方的 `SegmentBudget`。§41.2 的初值须由 §47.2
黄金集回放标定并记入 ADR（§48.7 禁止采外部观察值）——在这里发明一个数字，等于把 §41.2 答第二次，
并把一个没有证据选过的数冻进仓库。

**只拒一件事**：§41.1 未定义的段名 ⇒ `AssembleError::UnknownSegment`（`assemble.unknown_segment`），
不静默丢弃。丢弃会让 `AssemblyRejection::UnknownSegment` 从产生侧**不可达**，并把「我不认识它」
变成「没有东西需要认识」。

`PlannedAssembly::with_plan` 是借用视图：`AssemblyPlan::slices` 是借用切片而计划在运行时构造，
两者同存会成为自引用结构 ⇒ 切片序列每次现场构造，不做自引用。

### 端到端接线（`crates/nai-runtime/tests/assembly.rs`，+2）

- `a_plan_from_the_assembler_reaches_the_chain_and_rebuilds_from_it`：候选 → 装配 → 落链 → 逐行读回
  → 只靠链重建，并断言重建序列与 §41.1 顺序一致。
- `an_incomplete_plan_from_the_assembler_appends_nothing`：装配器造得出但 §41.1 仍拒的计划，
  **一个字节都不落链**。

**判定面与执行体本轮零改动**（`evaluate/assembly.rs`、`runtime/src/assembly.rs` 未动）——补的是
它们之间的那一段，不是它们的语义。

## 五、具名登记（本轮发现但不修）

1. **H01/H02 的 `status` 仍 `pending`**。闭合的是「②执行体获得真实入参」，不是验收达标：④真实产生者
   （把装配结果喂给模型的调用点）与 §41.2 初值标定仍未接线。与 W106/W127 的处置一致。
2. **H03/H04 本轮未纳入**，理由见 §一的分型表。
3. **`usage_counts_only_what_survived` 对裁剪位置不敏感**：K3 只让「尾部裁剪」那条变红，usage 用例
   仍是绿的——它算数量与总和，不比身份。这不是缺陷（身份由前一条钉住），但 MUST NOT 被读作
   「usage 用例守住了裁剪方向」。
4. **`CropFromFront` 在真实路径上仍无对象**：装配器不做段间整段裁剪（§41.2 明确「按段分配，不是一个
   总上限」，引入总预算才是更大的错），该维度只能由手工构造的计划触发。如实登记，不新增判据。
5. **`plan_assembly` 仍无生产调用方**：端到端用例证明的是「装配器 → 落链 → 重建」这条路能走通，
   走通它的是**测试**。`record_assembly` 的第一个生产调用点要等模型调用路径（H16）。
