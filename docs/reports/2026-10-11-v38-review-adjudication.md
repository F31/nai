# V3.8 方案评审裁定：逐条核实与 V3.9 议程

- 日期：2026-10-11
- 基线：[直播数字人 + 智能体系统技术方案 V3.8.md](../直播数字人%20%2B%20智能体系统技术方案%20V3.8.md)（ADR 0047）
- 依据：V3.8 全文实测（本文所有 `§NNN` 均指 V3.8 行号）、`tests/registry.yaml`（87 条）、`docs/development-plan.md`、`docs/reports/`、`git log`
- 性质：**审视与裁定**，不是变更。本文不改任何 `status`、不新增验收、不动基线、不建 OpenSpec 变更。
- 输入：外部评审（下称 K）的五维度批评；以及项目负责人（下称 U）对 K 的纠正与 V3.9 方向建议。

## 0. 结论摘要

1. **K 的三条主批评成立**：R1 偏离 Lite 定位（把未来扩展能力变成首版**发布门槛**）、讲品能力优先级偏低、版本只有加法没有减法。这三条与 §18.1 已自认的「**首版交付面过宽（高）**」是同一件事——**文档已登记该风险，但没有围绕它重排资源**。
2. **K 的技术侧判断里，两条不成立、两条被读反、一条成立但真因不同**：§25.5 算术自洽；§14.3 本就不追求无中断；六进程 ≠ 安装组件数；「44 张表」既不是 44 也不全档位承担；wasm 的问题不是「首版负担」而是**文档自相矛盾**。
3. **U 的纠正基本准确**，但两处需再修：`§23.2` 表数实测 **32**（U 未纠正数字）；「§5.9 已有指标」成立，但缺口应表述为**讲品与业务结果**指标。
4. **双方都未发现的五处问题**（本轮实测新增，见 §4）：A12–A14 在基线文档**零命中**而注册表有；**W45 在仓库里完全不存在**，而 §48.6 声称「已执行 W41–W55」；§47.6 与 §48.1 两处「**冻结** `memory.access@1`」已被 W57 证伪；§47.6 的 W64 单行**跨 R1/R2**；§48.5 的 A 行索引比注册表**少 3 条**。
5. **V3.9 的形状是「保留方向、压缩默认、重排门槛、订正冲突」**，不是砍架构。见 §5。

## 1. 核实口径

- **凡数字必复测**：`grep -c` / `wc -l` / 正则抽取，不引用文档自述。
- **区分三类陈述**：① 基线**现状**（V3.8 写了什么）；② 仓库**事实**（注册表/报告/提交里有什么）；③ **判断**（该不该这样设计）。K 与 U 的多数分歧不是事实分歧，而是把 ① 当成 ② 或把 ③ 当成 ①。
- **不采信「文档说已实测」**：文档里「实测」只覆盖仓库内可复现的事实（如 §42.6 的目录状态、§47.6 的轮次占用）；产品侧数值 §18.3 已自认「未做任何模型运行、硬件基准、平台授权申请或真实直播验收」。

## 5. V3.9 议程（建议）

原则：**保留完整架构方向，压缩默认运行范围，重排交付门槛，订正规范冲突**——即 U 已明确的三条约束（不降低扩展性与灵活性、三档共用稳定内核与平滑升级、降低运行维护成本）在 V3.9 的落地形式。

### A. 平台准入独立成轨（K2 / U10）

把人选轨拆成三条**互不替代**的命题，各自有硬门槛（K 与 U 都同意但其合取未被拆开）：

| 轨 | 可继续的工作 | 硬门槛 |
| --- | --- | --- |
| 平台规则准入 | 核对账号、类目、用途、事件权限与官方输出路径；发书面确认 | **未获允许，不进入真实自动互动** |
| 平台事件接口可用 | 桥接 PoC（调试版伴侣） | 事件能稳定进入本机 |
| 画面能进直播 | 输出路径确认 | 官方入口存在 |

同时要求：若自动互动不获准，「人工辅助 / 演练录制」是否仍值得做**须单独做需求验证**——不能因为技术上能退回，就认定商业上成立。

### B. 拆开三个维度：发布阶段 / 产品档位 / 部署配置（U 的「R1 = Lite 容易混淆」）

现状把「R1」同时当作**首版范围**与**Lite 的永久能力**。V3.9 应显式区分：

- **R1 = 首版发布门槛**（缩小）；
- **Lite = 默认组合**（保持轻量，但**仍可加装**其它能力包）；
- **能力包**（市场客户端、MCP/A2A、复杂工具规划、wasm 宿主…）= **保留设计边界，启用时才承担运行/验收/维护成本**，不作为本地讲品闭环的发布门槛。

### C. R1 收缩的落法（U9 的可判定分界）

**保留在 R1（基础纪律，调用 LLM 的前提）**：

| 保留 | 理由 |
| --- | --- |
| 上下文来源标注与长度预算（H01/H02） | 没有它，证据与工具日志会挤掉约束 |
| 外部文本不具指令权（V3.8 INV-31） | §11.7 既有 AI 专项安全的前提 |
| 已播完内容的有界记录（§5.5 工作记忆） | 既有实现（W57 前已在 `evaluate::memory`） |
| 事实、审批与缓存失效检查 | S05 既有口径 |
| 失败原因具名与 §12.2 降级（H17） | 无具名降级即无法诊断 |
| 关键链路记录与回归 | R07 既有口径 |

**按需启用或后置**：独立意图分类模型、多步工具循环、通用记忆服务与长期观众记忆、语义缓存、MCP、A2A、完整 Harness 专项评估平台。

⇒ **分界判据**：*「一个确定性的上下文装配函数能不能满足它？」* 能 ⇒ 留 R1；只有建独立子系统才能满足 ⇒ 能力包。**这比「删掉第四部分」精确，也比「全留 R1」诚实。**

### D. 基础讲品循环前移 R1（K15 / U 的第 2 点）

前移的是**确定性脚本 + 规则**，不依赖工具规划：

- 商品卖点/规格/适用场景/售后说明的**段落编排**；
- 问答插入后**回到讲解位置**（检查点机制，§5.7 已有）；
- **重复冷却与段落切换**；
- 基于**有效事实**的行动提示，禁虚构优惠与承诺（与 M04、§45 禁用域同侧）。

### E. 版本减法纪律（K13）

变化表（§48.1 一类）增设 **「本版砍掉 / 延后 / 降级为能力包」** 栏，与新增项**同权重**评审。这是**机制**而非一次性动作。

### F. 决策日志责任再限定（K5 的合理部分 / U 的修正）

保留哈希链，但**限定它的宣称**：

- 「哈希链能发现**部分**改动；**不能**单独证明本机管理员未重写整条链」；
- **拆开验收**：「录制返回后的**确定性回放**」与「重新调用在线模型得到相同答案」是两回事，MUST 分开；
- **不要求全部业务状态由日志投影重建**——允许事务状态表 + 快照 + 关联日志；
- 真正要简化的是日志承担的**恢复与投影职责**，不只是删掉哈希计算。

### G. 补产品视角（K1 / K3 / K4 / K18）

新增用户画像与商业模式一节；把「10 分钟首句」**明确为演示体验目标**并注明是否已有 API 凭据（不与真实开播准备时间混谈）；补讲品与业务结果指标；把 §37 的非直播场景**明确标为需要新增接入器与合规评估**（§1619 已有此结论，只需在场景矩阵处显式重申）。

### H. 规范冲突就地订正（D1–D7）

V3.9 必须订正现行规范，不能只登记让开发者自行判断：§20.6 ↔ 能力目录；§47.6 的 W57 行与 §48.1 的 N3（冻结断言）；§47.6 的 W64 跨线；§4.5 ↔ §1.4 的 wasm；§48.5 的 A 行索引（补 A12–A14）；§48.6 与 §47.6 的轮次范围（W41–W55 ⇒ 按实测 W41–W57 除 W45）。**历史记录（`docs/reports/`、`docs/adr/`、归档变更）一律保留原文 + 追加勘误段**。
