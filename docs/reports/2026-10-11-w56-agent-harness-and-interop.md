## 一、判断：V3.7 有智能体，但智能体还不是工程化的

行业口径是 **`Agent = Model + Harness`**：harness 是模型**之外**、让智能体在**长时程、可执行、低容错**场景里
可靠工作的那一整套东西——上下文管理、工具接口、编排、状态与记忆、验证回路、约束与恢复。
本项目面向的正是**专业直播 + 实时互动**（低容错、长时程、可执行），所以 harness 不是可选项。

**缺口是实测出来的，不是印象**（对 V3.7 全文的命中数）：

| 能力 | V3.7 命中 | 位置与性质 |
| --- | --- | --- |
| `Harness` | **0** | — |
| `A2A` | **0** | — |
| `意图识别` | **0** | 且 §5.2 明写「不先做独立分类」——该取舍只对**实时路径**成立，却被写成全局结论 |
| `工具调用` | **1** | §987，且是 SSE 解析措辞（「工具调用增量」），**不是能力定义** |
| `语义缓存` | **3** | §1008（一句纪律）、§1480（§34.2 规则 1）、§1646（M04） |
| `MCP` | **4** | §1490「见 35.2」、§1515 表格一行、§1658「MCP 适配调研」、§1873 待确认 |

⇒ V3.7 有智能体的**零件**（决策循环、分级路由、守门、技能、知识），但**没有 harness**：
给模型看什么、按什么顺序、多少预算**没有定义**；记忆**没有写入门槛与读取过滤**；工具循环的**终止与失败无定义**；
缓存的**两类（音频 vs 文本）没有分开**；MCP 只被当作「技能的一种实现形态」，其 `resources`/`prompts`/`sampling`
与**远端服务端信任**未处置。

## 二、方法：为什么是「追加第四部分」而不是就地改

本仓库把基线**按行号引用**（`§655`、`§1328` 这类引用遍布 registry、ADR 与代码）。因此换基线**必须**保证行号对齐，
否则**引用失效不会被编译器发现**。

V3.6 → V3.7 之所以安全，是因为它的 8 处改动**全是 1:1 行替换**（总行数不变、行号一一对应）。
本轮沿用同一形状：**第四部分追加在文档末尾**。实测（`wc` / 逐行比对）：

```
V3.7.md = 1875 行 / 151,878 字节
V3.8.md = 2366 行 / 193,438 字节          →  新增 491 行 / 41,560 字节
前 1875 行（§1–§39）逐行比对：仅 8 行不同
```

## 三、交付：第四部分的六条不变量与五条纪律

新增 **INV-27 – INV-32**（§40.3，正本在第四部分；第 2 章的表按「只增不改」保持原文，增补索引见 §48.3）：

| 不变量 | 内容 |
| --- | --- |

| INV-28 | 记忆写入**有门槛**、读取**有作用域**；工具返回、评论原文、模型草稿 MUST NOT 写成事实或承诺 |
| INV-29 | 意图、置信度与分类**只作建议**，**绝不构成授权**；高风险意图不提升权限、不降低守门强度 |
| INV-30 | 缓存命中**不复制授权**；价格、库存、优惠、承诺、服务政策与个人承诺**禁入**语义缓存 |
| INV-31 | 外部工具、MCP、对端（A2A）返回一律按**不可信数据**；其自称「只读/已批准」**无任何效力** |
| INV-32 | 任何一层失败 MUST 产生**具名错误码**并按 §12.2 的降级顺序处理，**无静默降级** |

五条贯穿全篇的纪律（§40.4）：**装配胜过累积**（明确定义给模型什么，而不是把能塞的都塞进去）；
**建议 ≠ 授权**（模型输出与外部输入的效力边界）；**不可信必标注**（外部内容带来源与数据/指令标签）；
**一切有界**（步数、预算、deadline、并行度、结果大小）；**默认关闭**（新机制先演练、影子、人工辅助）。

## 四、关键取舍（逐条给理由）

**① 意图识别按路径拆，而不是推翻 §5.2。** §5.2 的「不先做独立分类」只对**实时路径**成立（它为了省延迟），
却被写成全局结论。第四部分改为**逐路径**：实时路径保持「无独立分类器」；辅助/影子/节目编排/入站外部路径
**可以**做显式意图。意图的**最小表示 = 封闭枚举 + 置信度 + 依据引用**，`unknown` 是**一等公民**——
只有分数或只有枚举都判**未定义**；低置信一律落 `unknown` 并转澄清或人工。
意图是守门**输入级**的一个输入，冲突**以守门为准**。

**② 两类缓存强制分开。** TTS 的**精确缓存**复用音频；**语义缓存只出文本/候选，绝不出音频**——
相似句复用音频会让观众听到与当前事实不符的话。键须包含嵌入模型与修订号、意图类别、场景与知识空间；
**命中 ≠ 可用**（仍要重跑证据复核）。禁用域即 §5.3 的一般化（与 M04 对齐）。
命中率**必须与误命中率一起报**——只报命中率会把「错得更多」读成「更快」。

**③ MCP 映射到既有契约，A2A 是独立入口。** MCP 的四面：`tools` → `skill.invoke@1`、
`resources` → `data.query@1`、`prompts` → 配置（**MUST NOT** 直接作系统提示）、`sampling` → **默认禁用**；
并新增**工具描述快照与漂移触发的重审**（描述是**攻击面**，改了必须重审）。
A2A 与此不同，必须写清：**对端会自己推理并行动**，所以 A2A 的输出是**另一个主体的结论**，
不是「本系统的观测」。故入站 A2A 是**独立入口**，其请求是**「外部请求」**——不是用户指令、不是授权、不是值守；
身份**本地推导**，默认只响应人工辅助模式；出站须声明目标、目的、数据范围与超时，
**不得**携带观众文本、知识文本或凭据，**不得**委派 `risk_2` 及以上，**委派链深度上限为 1**。

**④ 本轮不新增契约名，也不改能力目录。** 这是与 §37.4 的**有意差别**，理由三条：
(a) MCP 四面都能映射到**已有**契约或既有机制，不需要新契约；
(b) A2A 的协议版本与认证方式**待验证**——在一个还没有请求/响应形状的协议上先占契约名，
只会产生**半声明的 draft**，而 §4.1 与 W52 起的能力目录纪律明确禁止（它让 `stage` 字段失去意义，
把「未验证」伪装成「已登记」）；
(c) 故 A2A 的契约**待协议验证后**随 W62 入目录；本轮 H13/H14 在注册表里 `contract` **留空**（沿用 M10/M12 先例），
而不是引用一个目录里不存在的名字。

验证时还发现并**如实登记**了一处**基线自身的内部不一致**：§20.6 把 `memory.access@1` 列为保持 Draft，
而能力目录已标 `frozen`。第四部分**以目录为准**并显式记下这个不一致（§42.6、§46.5），
**不就地改写 §20.6 原文**——否则就是用一处无声改写掩盖一个应当被看见的不一致。

**⑤ 本轮不新增静态门控。** 无实现可门控，写了只能是**空洞门控**（恒真的「保证」比没有更坏）。
第四部分把「可观测、可评估、可爬坡、可降级」写成**边界**，其**唯一机器可判定**的部分——验收家族在册——
交给注册表门控（见 §五）。§47.6 定义工作项 **W56–W64**：V3.7 §39.6 的计划止于 **W40**，
而 **W41–W55 已被后续实际执行轮次占用**（见 `docs/development-plan.md` 与 `docs/reports/`），
故第四部分从 **W56** 起编号，**不重排既有编号**（该裁决在动手前已向用户说明，用户未反对）。

**⑥ 三处阈值一律不外推。** 意图置信度阈值、语义缓存相似度阈值、上下文利用率观测线，
全部写作「**待本场景回放实测**」，并明写 **MUST NOT** 直接采用外部观察值——
外部文献里的「利用率 40%」之类的数字来自别的场景，搬过来就是**把别人的约束当自己的约束**。

## 五、验收侧：把「规格早已要求却从未实现」的断言实现掉

本轮**最有价值的一步**不在新文档，而在**直接应用 ADR 0042 决策 4 留下的教训**。

ADR 0042 曾**刻意不登记** M01–M18，理由是「不愿用基线切换掩盖一个独立的登记缺口」。该缺口后来被判定为缺陷，
教训被记为：**在册与测得是两个不同的陈述——「尚未开始」MUST 以 `pending` 表达，MUST NOT 以之为由省略条目**，
否则「以注册表为准」这条规则会把整部分从验收视野里**抹掉**。

本轮的处置：

| 动作 | 事实 |
| --- | --- |
| H01–H18 **就地登记** | 注册表 **69 → 87** 条，18 条一律 `status: pending`、`automation` 为**规划意图**并在 notes 写明 |
| 家族分布 | **S12 / R11 / A14 / B6 / O5 / P1 / M18 / H18 / X2 = 87** |
| id 白名单 | `^(S\|R\|A\|B\|O\|P\|M\|H\|X)[0-9]{2}$`（`registry.mjs` + `registry.schema.json` 两处 pattern） |
| 既有 status | **一字未动** |

**更重要的发现**：`openspec/specs/admission-registry/spec.md` **早已写着**
「并 SHALL 断言 M 家族（§37.5、§38.10 共 18 条）全部在册」，而 `scripts/contracts/registry.mjs`
**从未实现这条断言**——这正是「门控只校验**已登记条目的合法性**、**不校验家族是否齐全**」的机制原因，
也是 W46 那类缺口能长期不可见的**根因**。本轮把它**实现**了，并把家族集合扩到 M 与 H：

```js
// 每个「基线已定义完整编号段」的家族逐号比对；缺号/越界都具名失败
for (const [family, {count, baseline}] of COMPLETE_FAMILIES) { ... }
```

**断言的非空洞性做了四组注入**（`tests/registry.test.mjs`，3/3 通过）：

| 注入 | 应当被抓到 |
| --- | --- |
| 删 `H05`（family 内**洞**） | 失败并**指名** `H05` |
| 整族删除 H | 失败并列出全部 18 条缺失 |
| 加 `H19`（**越界**） | 失败并指名 `H19` |
| 删 `M18` | 失败 ⇒ 证明 M 与 H **分别**计数、不能互相掩盖 |

## 八、方法论教训

**① `命令 | tail -N` 与 `命令 | tee f` 一样会吞掉退出码。** 本轮预热构建用的重试循环是
`for i in $(seq 1 8); do cargo … --no-run 2>&1 | tail -3 && break; done`——**管道让退出码变成 `tail` 的（恒 0）**，
于是第一次失败就 `break`，**重试从未发生**，而且**只留了 3 行、真正的错误被截掉**（本次只拿到
`error: could not compile nai-xtask (lib test) due to 1 previous error`，看不到原因）。
随后同一条命令单独执行**成功（EXIT=0）**，完整门控亦通过 ⇒ 该错误是**瞬时**的（与既有登记的间歇性
`LNK1104` 同族）。**修正**：预热循环必须 `set -o pipefail`，或干脆不接管道、把完整输出落盘。
> 这条与仓库既有的「`tee` 会吞退出码」是**同一个坑的第二个入口**：凡是 `cmd | 任何东西`，退出码就不再是 `cmd` 的。

**② 数字要么先测再写，要么不写。** 本轮自查时发现 ADR 0047 与四处文档都把第四部分写成「486 行」、
把 V3.8 写成「2361 行」（实测 **491 行 / 2366 行**）。成因是**写入前未跑 `wc`**——与 W55 那次
「17 个场景 vs 实际 14」是**同一类错误**。已按规则处理：ADR 0047 与 AGENTS.md、`docs/development-plan.md`、
`openspec/changes/w56-…/proposal.md` 是**本轮新写/未提交的文本**，**就地订正**；
`docs/adr/0042-…md` 的**勘误段**（本轮追加的新文本）同样订正，其**原文部分一字未动**。

**③ `validate --all --strict --archived` 不校验 `openspec/specs/`——本轮的真实发现（容易漏）。**

实测分类统计：

```
openspec validate --all --strict            → 42 条，全部是 spec/…     （规格）
openspec validate --all --strict --archived → 61 条，全部是 change/…   （已归档变更）
```

两者覆盖的是**不同对象**，**前者不能由后者代替**。而本仓历轮的闭环口径写的是后者
（W55 报告写「归档后 `validate --all --strict --archived` 60/60（41 specs + 19 已归档变更）」——
按本轮实测，该口径对**组成**的描述也不准确：那 60 条**全是已归档变更**，不含规格）。

后果本轮**真的发生过一次**：归档输出 `Specs updated successfully`、`--archived` **61/61 全绿**，
而 `admission-registry` 合并后的需求正文 **541 字符**（> 500）在 `--strict` 下**失败**——
靠**额外**跑一次不带 `--archived` 的命令才发现。更隐蔽的是：变更层的
`validate w56-… --strict` **通过**（同一段 541 字符文本），说明 **>500 字符这条规则只作用于 `specs/`、
不作用于变更的差量**；差量**原样**合并进规格后，它才**第一次**成为严格性失败。

**修法**：把细节从需求正文移进场景（需求文本 **541 → 336** 字符），规格恢复 **42/42**。
**可复用的闭环口径（建议后续轮次照此写）**：同时跑
`validate --all --strict`（规格）与 `validate --all --strict --archived`（归档变更），两者都要绿。

**④ 归档时有一条非阻断告警：`⚠ Consider splitting changes with more than 10 deltas`（本变更 11 条差量）。**
**未采纳**，理由是：本变更是**一个**连贯单元——新增 `agent-harness` 能力（10 条需求）
＋对 `admission-registry` 的**一条**治理性修正（家族在册断言），后者正是前者赖以被登记的前提。
拆成两个变更会让「新能力规格」与「它赖以生效的治理修正」分开评审，**削弱**而不是增强可评审性。
**登记为已评估的告警**，不改。
