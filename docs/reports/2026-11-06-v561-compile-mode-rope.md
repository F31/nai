# 768 四步编译模式与旋转位置编码探测

在 Windows RTX 5090 上保持用户认可的 768 原图构图、四步采样和 FlashAttention 2 社区隔离候选；用 E 盘独立 CUDA 驱动缓存和编译缓存。FlashAttention wheel 仅含 sm_89 机器码/PTX，首次算子调用经约 89 秒后成功，不等于已验证原生 sm_120 或正式分发条件。

默认编译模式的 6 个稳定块平均 1.160 秒／0.96 秒语音块。`reduce-overhead` 模式基线两块为 1.266、1.241 秒，stderr 提示位置编码张量由 CPU 搬到 GPU，部分 CUDA 图被跳过。首次图编译约 349 秒，两块不足以确定稳态分布。

另做诊断性预加载：将 `freqs` 在首次前向前从 CPU 移至同一 GPU，记录 dtype `complex128`、65536 个元素，并以 `torch.equal` 检查搬运前后值一致；默认关闭。该轮 stderr 未出现先前的 CPU 张量跳过提示，但日志缺失不等于证明所有图成功捕获；后两块 1.311、1.172 秒，没有建立可靠速度收益，仍高于 0.96 秒。两次运行不交错，温度与 GPU 负载未严格控制。

预加载加低开销模式与先前默认模式的无压缩帧抽样（第 0、12、24、36、48、60、71 帧）逐通道 8-bit 平均绝对差约 0.48–1.69，个别像素最大差 11–131；这只反映两次实际运行差异，可能包含随机状态与编译计算差异，不构成逐像素等价或用户画质通过。没有改变正式默认、没有实际播放、没有 OBS 或 Qwen 并发验收。

日志 `windows-768-flash-reduce-20261106.jsonl`、`windows-768-flash-rope-preload-20261106.jsonl` 及同名 stderr；后者无压缩帧也保存在 E 盘。下一步需要可重复对照并确认 CUDA 图实际状态，或探索经过验证的其他加速路径；不得以预缓冲掩盖四步 768 持续算力不足。实验选项保持诊断范围。
