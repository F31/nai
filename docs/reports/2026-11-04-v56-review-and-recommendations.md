## 0. 结论

**V5.6 的模型方向是对的，但架构仍然偏重。**

- **对的地方**：用 SoulX-FlashHead 1.3B 替换 MuseTalk+LivePortrait，单模型端到端，直接消除“双嘴/接缝/嘴部 owner 仲裁”这一整类复杂度；把 LiveAct 从对等引擎降为可选短时，并新增 M0-B 资源基线门；开始认真对待 32GB 内存、笔记本 TGP 和散热。
- **仍然过重的地方**：保留了双引擎、冷切换、过渡画面、切换回滚、双 venv、LiveAct 18B、EchoMimicV3 片段工坊、LLM 动作标签、资源仪表盘、8 小时目标。对当前“单人、单机、单形象、先跑通”的阶段，这些不是主线，而是把 V5.5 的复杂度整体继承了下来。
- **最关键的现实差距**：当前 nai 仍是 V4.8 基线、164 项 ACC 全 pending、公共输出 `builtin-2d`、没有生产写实渲染器、Qwen 当前不可达；V5.6 已经假设 FlashHead/LiveAct/Qwen3-TTS 可用并“继承 V5.5 全部机制”。**设计跑在实现前面太多。**

**建议：把 V5.6 收敛为“V5.6.1 单引擎精简版”**：

> **FlashHead Lite 为唯一主力引擎 + Qwen3-TTS + 预录动作片段 + 本机预览/OBS + 单操作员控制。**
> 删除 LiveAct、双引擎切换、热备、过渡切换、EchoMimicV3 主线、LLM 动作标签、RTMP 主线。
> 先做 30 分钟，再做 2 小时，最后再谈 8 小时。

如果“短时手势表演”是硬需求，把 LiveAct 放到 `experiments/liveact/`，单独做 M0-B 资源基线；通过后再以“外部独立模式”接入，不进入 V5.6 主线。

## 1. V5.6 做对了什么

必须肯定，V5.6 相比 V5.3/V5.4 有几处明显进步：

| 改进 | 价值 |
|---|---|
| 用 FlashHead 替代 MuseTalk+LivePortrait | 单模型端到端，消除双嘴/接缝/ROI 对齐/嘴部 owner 仲裁；这才是“本地数字人”的正确模型层 |
| FlashHead Lite 作为主力 | 官方称单 4090 96 FPS 或 3 路 25+ FPS；Lite 在 5090 Laptop 上更可能是舒适档 |
| LiveAct 降为可选短时 | 承认 18B 在 24GB/32GB 上贴顶；不再假装它是长播主力 |
| 新增 M0-B 资源基线门 | 先测 VRAM/RAM/温度/FPS，再决定是否深入；这是正确的前置验证 |
| 片段库提升为方案 A 主要动作能力 | 降低对 LiveAct 的依赖，动作可预录、可审核、可重复 |
| 系统内存 + 温度 + 功耗监控 | 针对 32GB 笔记本的真实约束，比只盯显存更准确 |
| 单操作员 / 无多工作区 | 延续 V5.3 的简化方向，没有被 V5.2 的治理体系拉回去 |

**模型选型方向值得保留。** 问题不在 FlashHead，而在“是否还需要 LiveAct + 切换”。

## 2. 与当前实现、目标机的差距

### 2.1 当前实现现状

| 项 | 当前状态 | 证据 |
|---|---|---|
| 执行基线 | V4.8 | `tests/registry.yaml` baseline |
| 验收 | 164 项全部 pending | registry 计数 |
| 公共输出 | `builtin-2d` | `crates/nai-media-core/src/character_workbench.rs` |
| 生产写实渲染器 | 无 | 最新报告明确“当前没有生产写实渲染器” |
| 形象能力 | 私有预览/许可/视频导入草稿；`realistic_drive=model_missing` | `docs/reports/2026-11-02-*` |
| Qwen | 当前不可达；历史曾成功 | `docs/v52-primary-composition.md` |
| FlashHead/LiveAct | 未集成 | 仓库中无对应 worker |
| 平台连接 | 无真实 connector | `plugins/platform-unavailable` |
| 文档链 | V5.6 → V5.5 → V5.4 → V5.3 → V4.8 | 各文档“沿用/继承” |

**结论：V5.6 不是“在当前实现上调整”，而是“另起一条新主线”。** 这本身可以接受（用户明确不考虑向前兼容），但必须显式写清楚“复用哪些代码、删除哪些代码、替换哪些模块”，否则实现者会再次在旧代码和新设计之间漂移。

### 2.2 目标机现实

| 资源 | 约束 | 影响 |
|---|---|---|
| RTX 5090 Laptop 24GB | 笔记本 TGP 95–175W，持续性能受温度/功耗限制 | FlashHead Pro 不一定能稳定 15–17 FPS；Lite 更稳 |
| 32GB RAM | Qwen + FlashHead + OBS + 系统 + 浏览器 | FlashHead 舒适；LiveAct offload 峰值可能接近 30GB，风险高 |
| 24GB VRAM | TTS 4GB + FlashHead 6.4–8GB + 输出 3GB | 舒适（约 13–15GB） |
| 24GB VRAM | TTS 4GB + LiveAct 12–16GB + 输出 3GB | 19–23GB，贴顶；切换瞬间更危险 |
| 散热 | 8 小时长播 | 必须降功耗/锁帧/温度墙；不能假设桌面 5090 表现 |

### 2.3 官方性能与 V5.6 文本的差异

FlashHead 官方 README：

- Lite：单 RTX 4090 96 FPS，或 3 路 25+ FPS；
- Pro：单 RTX 4090 10.8 FPS；双 RTX 5090 才 25+ FPS；
- Pro 的实时性明确依赖双 5090 + SageAttention。

因此 V5.6 中“Pro 约 15–17 FPS（可插帧）”**不是官方单卡数据**；在 5090 Laptop 上更可能低于 15 FPS，必须实测。**Lite 应是默认，Pro 只能是实测通过后的可选项。**

LiveAct 官方：

- 双 H100/H200 20 FPS；
- 单 RTX 5090 6 FPS（FP8 KV cache + CPU offload，质量略受影响）；
- 更新了 B 系列 FP4 GEMM。

V5.6 的“6–10 FPS + 插帧到 24 FPS”是合理估计，但**插帧会产生残影，不能当作真实时**；而且 32GB RAM 风险仍然存在。

## 4. 建议：V5.6.1 单引擎精简版

### 4.1 一句话目标

> **在 5090 Laptop 24GB/32GB 上，用 FlashHead Lite + Qwen3-TTS 完成 30 分钟可回放的本地数字人直播；能停、能静音、能接管；稳定后再做 2 小时/8 小时。**

### 4.2 精简架构

```text
nai-desktop（Tauri 2 + React）
        │
nai-engine（Rust：会话/LLM/互动/动作/输出门/日志）
        │
        ├── qwen3-tts（本地常驻，0.6B，流式）
        ├── nai-avatar-worker（Python/PyTorch，FlashHead）
        ├── clips/（预录动作片段）
        └── OBS（窗口捕获）
```

**只有 3 个自研进程 + Qwen + OBS。** 不设第二视觉 worker、切换控制器、热备、transition clip、资源仪表盘大屏。

### 4.3 保留 / 删除 / 延期

| V5.6 项 | V5.6.1 处置 | 理由 |
|---|---|---|
| FlashHead Lite | **保留，默认** | 单模型、实时、24GB 舒适 |
| FlashHead Pro | **保留为可选** | 仅在目标机实测 ≥15–20 FPS 且温度可控时开放 |
| Qwen3-TTS 0.6B 流式 | **保留** | 主 TTS；但先探测真实能力 |
| Qwen3-TTS 1.7B | **延期** | 显存/延迟/必要性未证明 |
| 预录动作片段 | **保留** | 比 LiveAct 简单、稳定、可审核 |
| LiveAct 18B | **移出主线** | 资源/许可/6FPS；只做实验分支 |
| 双引擎冷切换 | **删除** | 单人直播不需要；切引擎改为重启应用/开始前选择 |
| 热备模式 | **删除** | 24GB 不可用 |
| 过渡画面/切换回滚 | **删除** | 无切换则不需要 |
| EchoMimicV3 片段工坊 | **延期** | 离线生成重；先用真人预录片段 |
| LLM 动作标签 | **默认关闭** | 先做按钮 + 关键词 + 片段 |
| RTMP 直推 | **延期** | OBS 已够；平台合规未知 |
| 资源仪表盘 | **简化** | 只显示 VRAM/RAM/温度/FPS 四项 + 告警 |
| 8h 基线 | **改为阶段目标** | 30min → 2h → 4/8h |
| 多工作区/审批/账本 | **删除** | 延续 V5.3 简化 |

### 4.4 目标机资源预算（V5.6.1）

| 组合 | VRAM | RAM | 判定 |
|---|---:|---:|---|
| Qwen3-TTS 0.6B + FlashHead Lite + 输出 | ~13–14GB | ~12–18GB | ✅ 推荐 |
| Qwen3-TTS 0.6B + FlashHead Pro + 输出 | ~15–16GB | ~16–20GB | ⚠️ 需实测 FPS/温度 |
| + LiveAct | ~19–23GB | ~28–30GB | ❌ 不进主线 |
| 双引擎热备 | >24GB | — | ❌ 不可用 |

### 4.5 性能目标（分层，不是一次性承诺）

| 阶段 | 目标 |
|---|---|
| M0 基线 | FlashHead Lite 10 分钟：≥20 FPS、首帧 ≤1.5s、温度 <87°C、无 OOM |
| M1 可用 | 30 分钟：≥20 FPS、首音 ≤2.5s、AV 偏差 ≤120ms、停止 ≤200ms |
| M2 长稳 | 2 小时：无持续掉帧/泄漏/降频；温度曲线可接受 |
| M3 发布候选 | 4–8 小时：允许合理静默；记录失败；不承诺 24h |
| 可选 Pro | 仅在 M0 实测 ≥15–20 FPS 且温度可控时开放 |

### 4.6 易用性目标

- 双击启动 → 自动检查 Qwen/FlashHead/OBS → 进入待机；
- 默认自动选 FlashHead Lite；引擎/画质选择放“高级设置”；
- 主界面只有：预览、开始/停止、静音、接管、输入框、动作按钮；
- 状态只显示：`准备中 / 待机 / 直播中 / 降级 / 已停止`；
- 失败消息必须给“原因 + 一键修复/重试”；
- 资源/温度/许可放状态页，不占主界面；
- 首次使用 3 步：选形象 → 试听 → 预览。

## 5. 性能优化建议

### 5.1 视觉

1. **默认 Lite，不默认 Pro**；Pro 只在实测通过后开放。
2. 输出先 720p/25fps；不要同时追求 1080p/30fps。
3. 使用共享内存环形缓冲，避免帧 Base64/JSON。
4. 音频主时钟选帧；迟到帧丢弃；连续迟到 >200ms 切安全帧。
5. OBS 只做窗口捕获，不在 engine 里重复编码。
6. 如使用 FP8/FP4/SageAttention，必须在 sm_120 + Windows 上实测；不能直接套 Linux/4090 结果。
7. 长播锁功耗/锁帧，记录温度曲线；超过 87°C 自动降级或建议切 Lite。

### 5.2 TTS

1. 先探测 Qwen3-TTS 实际能力：是否真流式、首包、采样率、克隆、取消、并发。
2. 如果非流式：句级合成 + 预取 1–2 句；首句短；缓存命中。
3. 0.6B 默认；1.7B 只在延迟/显存实测可接受时开放。
4. 16k 口型特征与 48k 播放分支分离；不要混时钟。
5. 停止时清空待播队列 + 标记 epoch；服务端不能取消时明确记录。

### 5.3 系统/内存

1. 32GB RAM 下不要跑 LiveAct；FlashHead 是安全选择。
2. 监控 Qwen/worker/OBS/系统总 RAM；告警线建议 26–28GB。
3. 模型常驻；空闲卸载策略先不做，避免反复加载。
4. 关闭不必要的浏览器/后台；安装包不要带无用模型。

## 6. 易用性优化建议

1. **隐藏引擎概念**：普通用户只需要“开始直播”；FlashHead Lite 自动。
2. **一键准备**：检查依赖 → 加载 → 预热 → 可开播；失败给明确按钮。
3. **状态四态**：准备中/待机/直播中/降级；不要用十几个技术指标轰炸。
4. **停止/静音/接管**：固定位置 + 全局热键 + 不依赖 UI 焦点。
5. **动作**：只给 5–8 个按钮（挥手/点头/摇头/微笑/比心/思考/鞠躬）；不做 LLM 动作解析。
6. **错误文案**：说“Qwen 未启动，点此重试”，不要说“provider handshake failed”。
7. **许可**：首次导入形象/声音时勾选；状态页显示“已确认/未确认”。
8. **本场报告**：结束后自动生成时长、首音、帧率、掉帧、温度、错误；不需要用户手动整理。

## 7. 开发路线（建议 6–8 周）

| 阶段 | 时间 | 交付 | 退出条件 |
|---|---|---|---|
| P0 目标机基线 | 第 0–1 周 | FlashHead Lite/Pro + Qwen3-TTS + OBS 最小 demo；VRAM/RAM/温度/FPS/首帧 | M0 基线通过；确定默认 Lite/Pro |
| P1 单引擎骨架 | 第 1–3 周 | engine + worker + Qwen 适配 + 预览 + 停止/静音/安全帧 | 30 分钟 M1 录像 |
| P2 直播功能 | 第 3–5 周 | 讲解/问答/弹幕入口/预录动作/UI | 2 小时 M2 |
| P3 输出与打包 | 第 5–7 周 | OBS 指南/录制/错误恢复/安装包/许可门 | 4–8 小时 M3 + 安装包 |
| 可选 B | 独立分支 | LiveAct 资源基线/短时 demo | 仅 M0-B 通过且 64GB RAM；不进主线 |
| 可选 Pro | 实测后 | Pro 档开放 | ≥15–20 FPS、温度可控 |

**注意：P0 必须先在目标机跑通，再写 P1 代码。** 不要先写切换控制器，再发现 Pro/LiveAct 不达标。

## 11. 最终建议

**V5.6 应保留 FlashHead，删除 LiveAct/切换，做成 V5.6.1 单引擎精简版。**

理由：

1. FlashHead 已经解决了 V5.3 最复杂的“双模型拼接”问题；
2. LiveAct 在 24GB/32GB 笔记本上是“贴顶 + 6FPS + 许可不清”，不适合做主线；
3. 单人直播不需要 10s/90s 冷切换；切引擎应放到“开始直播前”；
4. 当前 nai 还没有一条真实可播链，继续加第二引擎只会推迟第一条链；
5. 先用预录动作片段满足“比心/挥手/点头”，成本远低于 LiveAct；
6. 30 分钟 → 2 小时 → 8 小时的分层目标，比直接承诺 8 小时更可信。

**如果只能做一件事：先在第 0–1 周用目标机跑通 FlashHead Lite + Qwen3-TTS + OBS 的 10 分钟基线，拿到 VRAM/RAM/温度/FPS/首帧数据，再决定是否值得保留 Pro/LiveAct。** 不要先写切换控制器，再发现第二引擎跑不动。
