# W46 报告：M01–M18 登记为 `pending`（注册表覆盖全部验收家族）

**提交**：见本轮 commit（`docs/reports/2026-10-11-w46-register-m-series.md` 随提交）。

**一句话**：注册表此前漏登记了基线定义的整个 M 家族（开放平台与技能市场，V3.7 §37.5/§38.10），
本轮把 **M01–M18 共 18 条以 `status: pending`（在册未开始）**补入，并顺带修好两处使它无法被登记、
也无法被工具发现的附带缺陷。

## 1. 缺口是什么，为什么它一直没被看见

`tests/registry.yaml` 是「唯一验收来源」，`admission-registry` 规格要求它「列出**全部**验收项」。
基线 §16 与汇总索引 §39.5 把 M01–M18 明确定义为「唯一验收编号体系」的一部分，§37.5 与 §38.10
给出逐条用例与所属发布线。但注册表里：

```
$ grep -cE '\{id: "M[0-9]' tests/registry.yaml
0          # 本轮之前
```

这个缺口长期不可见的直接原因是：**`cargo xtask check --registry` 只校验已登记条目的合法性
（id 家族、release_line、status、映射悬空），不校验家族是否齐全**。一个家族整体缺席时，
校验器看到的是「一份内部一致的注册表」，看不出它少了一整段。

后果不是「少几行字」：R1 的退出条件包含 `M01–M07、M13–M16、M18`，R2 包含 `M08–M12、M17`
（§37.5/§16）。项目规则是「验收与任务卡不一致时以注册表为准」——以一份不完整的注册表为准，
等于把 V3.7 第三部分（§33–§38、工作项 W26–W40）从验收视野里抹掉。

## 2. 为什么是 `pending` 而不是 `not_applicable`

映射段的回填规则写的是「本 profile 未启用或**尚未开始**的目标标 pending/not_applicable」。
M01–M18 属于哪一支，取决于它们是「不在当前 release 范围」还是「在范围内但没做」：

- 基线 §1.4 的 R1 行与 §16 **明写** R1 包含 `M01–M07、M13–M16、M18`，R2 包含 `M08–M12、M17`
  ⇒ 它们是 **R1/R2 的退出条件**，只是在册未开始 ⇒ `pending`。
- 对照 `X01/X02` 是 `not_applicable`：那是「Lite-Mobile 未立项」，**不在**退出条件内。

即：分界是「在不在退出条件里」，不是「做了没有」。

## 3. 顺带修的两处附带缺陷

### 3.1 id 家族白名单不含 `M`——想登记也登记不进去

`scripts/contracts/registry.mjs` 的 `ID_RE` 与 `schemas/tests/registry.schema.json` 的两处 pattern
都是 `^(S|R|A|B|O|P|X)[0-9]{2}$`。**M 不在其中**，直接登记 M01 会被判为非法 id。
正确做法是扩白名单（基线 §16 说这是「唯一的验收编号体系」，不能为了迁就校验器把 M 塞进别的家族）：

| id | 旧正则 | 新正则 |
| --- | --- | --- |
| `M01` | reject | **accept** |
| `M18` | reject | **accept** |
| `B01` | accept | accept |
| `B01a` | reject | **reject**（位数仍须恰好两位，W31 的拆分禁令不受影响） |
| `S12` / `X02` | accept | accept |

按 §39.5 顺序把家族表订正为 `S/R/A/B/O/P/M/X`。

### 3.2 活文档的家族简写本身就不准

`AGENTS.md`（含 id 正则那处）、`docs/design.md`、`docs/development-plan.md`、`openspec/config.yaml`、
`README.md` 都写「S/A/R/O/X」——而 B 与 P **早已有条目**（B01–B06、P01）。简写漏了它们，
再加 M 只会更不准。五处一并订正为准确全表 `S/R/A/B/O/P/M/X`。

## 4. 登记口径（防止把规划读成结论）

- `automation` 是 schema **必填**字段，设计 §16 亦要求每条验收登记「是否自动化」。
  对未开始的条目它只能是**规划意图**（按用例性质推断：纯校验/审计 ⇒ unit，跨进程 ⇒ integration，
  并发/降级 ⇒ fault，一致性套件 ⇒ contract）。**不是测得结论**，已在每条 notes 末句与
  `tests/registry.yaml` 的家族注释里写明。
- `contract` 是**可选**字段，规格措辞为「所属契约（**如适用**）」。故只在 §37.4 命名了契约时填：
  技能生命周期/调用类（M01–M03、M05–M08、M11）⇒ `skill.invoke@1`；数据接入类（M04）⇒ `data.query@1`；
  设备类（M09）⇒ `device.control@1`；市场客户端类（M13–M18）⇒ `market.catalog@1`。
  **M10（离线包安装/签名）与 M12（授权过期自动停用）留空**——§37.4 未为这两个流程命名契约，不臆造归属。
- `mapping.notes` 补一句边界：M 家族**不在** D01–D14 映射内（源自 W26–W40，无对应 D 任务，
  不由任何 D 回填产生）。

## 5. 验证

| 检查 | 结果 |
| --- | --- |
| `cargo xtask check --registry` | 通过（含家族守卫） |
| 家族分布 | `S12 / R11 / A11 / B6 / O5 / P1 / M18 / X2`，**共 66** |
| 既有 48 条 status | **一字未动**（implemented 27 / tested 10 / blocked 5 / not_applicable 3） |
| `pending` 计数 | 3 → **21**（新增 18 条即本轮在册未开始） |
| 正则负例 | `M01/M18` 仅新正则接受；`B01a` 新旧**均拒** |
| `openspec validate --all --strict` | 通过 |

### 5.1 家族守卫的非空洞性（反向自检）

新守卫若只是「永远为真」就没有价值，故做两步自检：

1. **删掉 M18 条目** ⇒ 测试 **失败**。但失败落在计数断言（65 < 66），**尚未**证明家族守卫本身有效。
2. **把 M18 改名为 M19**（计数仍 66，只有家族守卫能发现）⇒ 测试 **失败** 且信息精确：
   `error: 'baseline acceptance M18 is not registered'`。还原后通过。

第 2 步才真正证明守卫的判据有效——第 1 步被更早的断言短路了，这正是「一次自检不够」的例子。

## 6. 明确不做

- **不实现 M01–M18 任何一条**：W26–W40 未动工，本轮只补在册状态。
- **不把 M 家族并入 `check --profile portable`**：未实现的目标不应让工程门控变红。
- **不写通用的「家族齐全性」检查**（解析设计文档表格）：脆弱且易误报。本轮只对触发缺口的
  **M 家族**落一个确定的守卫；通用性等第二个家族真出现同类缺口时再评估——不为假想的通用性付复杂度。
- **不改任何既有 status**。

## 7. 与 ADR 0042 的边界

ADR 0042（V3.6→V3.7 基线切换）**明确声明不追认 M01–M18 已进入验收范围**，只裁决基线版本，
并把「登记缺口」留给了后续单独一轮。本变更就是那个后续动作：ADR 0042 管「基线是哪一版」，
本变更管「注册表是否列全」。两者互补、不重叠。
