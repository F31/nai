# 固定形状GEMM autotune：环境缺口已修，候选不激活

## 结论

候选实现完成；修复诊断子进程C编译链发现后，Triton实际参与选型。第二轮候选总墙钟1531ms、计算1344ms，对比前后基线1563/1609ms、计算1391/1375ms，含像素留存I/O，仅约2.0%–4.8%单轮总差异；本块音频1280ms，仍未达持续实时。输出非逐像素等价、未获新主观质量验收，因此拒绝默认激活，不重复此类小收益编译开关。

当前BF16/768/四步工作台默认、权重、协议和设备未改。本轮不是持续播放或性能闭环；34ACC/M0不变。

## 工程

作用域保存已有编译去噪块，基于_orig_mod设dynamic=False、max_autotune_gemm=True、TRITON/ATEN后端；VAE和eager SDPA边界不变。候选在维护/热测间保留同一wrapper，回归前和异常退出恢复原块。候选关闭本地autotune选择缓存以避免重用首轮无效选择，保留已有编译代码缓存。默认install不启用候选。

复用profile_avatar_gpu显式gemm-autotune参数。两次维护均沿配置240秒硬退出、业务45秒，没有延长；新图和生成内核数单独记录，不能把包装器或请求选项当作Triton执行证据。前后基线、候选保存BGRA以便不重生成而核对质量。

4项候选/恢复/编译器环境测试、6项维护期限与既有编译测试、3项算子摘要测试，共13项通过。先部分安装失败也恢复所有原块；未编译输入明确拒绝。OpenSpec严格校验通过。

## 首轮环境失败与修复

candidate-01虽产生新图，但Triton benchmark多次报Failed to find C compiler，选项中的ATEN仍能完成。不能称有效autotune收益。首轮文件完整保留；总墙钟1547/1641/1656ms，候选32帧均与基线不同，回归32帧完全相同。

原因是独立安装的Triton没有可见的bundled TinyCC，普通进程PATH没有cl.exe；Rust构建能由工具链找到link.exe，不意味着Python的Triton能发现C编译器。旧包自动发现未找到本机VS18。

新增avatar_windows_compiler通过vswhere和SDK注册表动态发现，未硬编码安装盘/版本。只在显式GEMM诊断进程设置编译环境：本机MSVC14.51.36231、4项include和3项lib目录；系统/用户持久环境、Python依赖和Windows安装均未修改。最小原生扩展经实际编译和加载通过，产物cc-probe-01/result.json。不是通过安装器或覆盖第三方包修复。
