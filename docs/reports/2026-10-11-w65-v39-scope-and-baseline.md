## 一、判断：问题不是「缺能力」，是「已设计被当成已承诺」

先说结论。V3.8 的第四部分（Harness 与开放互操作，§40–§48）在写进基线时，**整段被放进 R1 首版门槛**：
声明式技能与官方只读技能、市场客户端、意图识别、语义缓存、工具循环、MCP、A2A、harness 黄金集，**全部**是 R1 的一部分。

这不是「文档没意识到」——**§18.1 早已把「首版交付面过宽」登记为高**风险。要修的是**登记之后没有围绕它重排资源**：
**登记解决「可以说清」，不解决「按什么顺序做」**。而对开发者最有杀伤力的后果是：**「已设计」与「已承诺」在文档里长得一样**，
于是「压缩首版」只剩两条路——要么全留 R1（范围膨胀），要么整体砍掉（丢失边界）。

本轮的触发是一次**外部审视**（对 V3.8 的五维批评）与用户对它的**反批评**。两份主张都被逐条取证核实，
**不以任何一方的清单为准**——这恰恰是本轮最有价值的部分（见第二节与第四节）。

## 三、交付：一个机制、一套断言、一份可复核的不变量

### 3.1 基线文档 V3.9：本仓库**第一次**在升基线时「就地订正」

前两轮（V3.6→V3.7、V3.7→V3.8）采用**纯追加**，前提是「**无矛盾可订正**」。本轮前提不成立，
继续追加只会把同一条矛盾**登记第二遍**。故 V3.9 §56.2 确立一般规则：

| 对象 | 处理 |
|---|---|
| **活文档**（主规范当前有效内容、`docs/*.md`、`AGENTS.md`、`tests/registry.yaml`） | **就地订正** |
| **历史记录**（`docs/reports/`、`docs/adr/`、`openspec/changes/archive/`） | **保留原文 + 追加勘误段** |
| **版本专属陈述**（§39 是 V3.7 的、§48.1/§48.2 是 V3.8 的） | 保留原文；跨版本索引（§48.5、§48.6）除外 |
| **代码 doc-comment 的版本前辍** | 不随基线变（ADR 0015 先例） |

并给「就地订正」加**硬约束**：**MUST 是 1:1 行替换（不增删行）**。**实测**：

- 前 2366 行：**24 个 hunk / 42 行 / 全 1:1 / `a`、`d` 型 hunk 为 0**；
- 规模：**2366 行 / 193,438 字节 → 2647 行 / 216,450 字节**（新增 **281 行 / 23,012 字节**）；
- ⇒ **行号一一对应，全部既有 `§NNN` 引用解析结果不变**（这是「只增不改」那句话的**可复核替代品**）。

### 3.2 核心交付：第六条发布线 `capability_pack`（机制，不是措辞）

「降级」此前**无处表达**：发布线只有「承诺 / 不承诺」两态。新增第六条线后：

| 线 | 收缩后验收 |
|---|---|
| Slice-0 | S01–S04、R01–R03、R07、A01、A04（**10**） |
| **R1** | S05–S12；R04、R05、R08–R10；A02、A03、A05–A07、A12、A13；B01、B03、B05、B06；O01–O05；H01–H04、H15、H17、H18（**36**） |
| R2 | B02、B04；R06、R11；A08–A10、A14；P01（**9**） |
| R3 | A11 及各自认证项（**1**） |
| 实验 | X01、X02（**2**） |
| **能力包** | **M01–M18；H05–H14、H16**（**29**） |

计数：10 + 36 + 9 + 29 + 1 + 2 = **87**，**与 V3.8 相同**——**只改归属，不加条目，不改任何 `status`**。

**INV-33 / INV-34 是既有约束的可判定形式，不是新口号**：

| 用户约束 | 可判定形式 |
|---|---|
| **重点降低运行维护成本** | **INV-33**：轻量由**默认组合**定义，不由**能力上限**定义——R1 内每条验收 MUST 在**未安装任何能力包**时可判定 |
| **不降低扩展性和灵活性** | **INV-34**：降级是**排期**动作，不是**设计**动作——边界、信任域归属与不变量 MUST 保留，MUST NOT 使既有 `§NNN` 引用失效 |
| **三档共用稳定内核并支持平滑升级** | §51.4：加装沿用**同一条**升级与迁移图（**MUST NOT** 有第二条安装路径）；启用 MUST NOT 改变默认组合的行为、成本或既有降级顺序 |

**分界判据**（一句可判定的问句）：***「一个确定性的上下文装配函数能不能满足它？」*** 能 ⇒ 留在 R1；
只有建独立子系统才能满足 ⇒ 能力包。它比「删掉第四部分」精确，也比「全留在 R1」诚实——
**约束不随模块一起被删，模块可以后置。**

### 3.3 门控增量：能力包集合断言（本版唯一的机器可判定部分）

三向断言（`scripts/contracts/registry.mjs`）：

1. **集合完整**：`capability_pack` 恰为 M01–M18 与 H05–H14、H16（共 29 条）；
2. **无混入**：MUST NOT 有归属外的编号（如 `H17`）被标为能力包；
3. **不与首版门槛相交**：MUST NOT 有任一能力包 id 落在 `slice_0`/`r1`/`r2`——**即 INV-33**。

失败信息**同时给出 id 与当前所在线**（形如 `M01=r1`），否则「哪一条被提回首版」不可定位。
**非空洞守卫**用三种注入证明它确实会失败（把 `M01` 提回 `r1` / 把 `H17` 标为能力包 / 清空能力包线），
**4/4 通过**。只断言「集合非空」的守卫是**可被满足的空洞断言**。

`schemas/tests/registry.schema.json` 的**两处硬编码**（`release_lines` 的 `required` 与 `.properties`、
`acceptance.release_line.enum`）同改——同一取值出现在两处的教训（W46 的 id 正则）本轮再次适用。

## 四、关键取舍（逐条给理由）

1. **不整体移出第四部分**：其中多项是**调用 LLM 的基础纪律**（装配与预算、记忆写入门槛与作用域读取、观测、
   逐层具名降级、模式爬坡门控），删掉后默认组合**无法**正确调用模型。核心约束**不随模块一起被删**。
2. **不删 workspace 作用域**：Lite 用固定 `default` workspace，界面不展示多工作区管理即可；保留作用域字段与
   唯一约束比日后重编号更合理。后置的是**团队管理与分布式治理实现**。
3. **不删决策日志，只限定宣称**：真正应被简化的是它承担的**恢复与投影职责**，不是哈希计算本身。
4. **不停止内核开发**：平台准入是**独立成轨**，不是一切工作的前置。
5. **不新增契约名**（§56.3）：MCP 映射到既有 `skill.invoke@1`/`data.query@1`；A2A 协议版本与认证方式**待验证**，
   为未验证协议占契约名只会产生**半声明 draft**。⇒ 能力目录**零漂移**。
6. **§52 本轮不落规格**（design §7）：三条命题的证据是**书面确认与官方入口的存在性**，不是可执行检查；
   且注册表中没有与它们对应的验收 id（P01 语义不同）。为它们新造 id 牵动 P 家族定义，属**另一轮**的登记决策——
   本轮只做「拆开 + 设门槛」，并如实登记这一未落点。
7. **`memory.access@1` 的阶段以目录为准**（§56.3）：不追究其冻结轮次，只订正陈述。
8. **不重排 W 编号**：第五部分从 **W65** 起；既有编号一个不动（并订正 W45 的不实范围）。

## 五、验收侧：为什么 29 条能力包**保持 `pending`**

本轮**不实现任何代码**（Rust 侧仅 `xtask/src/registry.rs` 的一处输出串由 V3.8 改 V3.9），
故 M01–M18、H05–H14、H16 与 R1 的 36 条**全部 `pending`**，沿用 A12／O01／O05 与 W32–W36 判定骨架轮的先例。

**「降级」不改状态**：本轮只改 29 条的 `release_line`，**一条 `status` 都没动**。
把「不进首版门槛」写成 `not_applicable` 或删掉条目都是**错的**——「尚未开始」必须以 `pending` 表达，
**在册与测得是两个不同的陈述**（ADR 0042 决策 4 的教训，V3.9 §57.3 的正本口径）。

`generate.mjs` 内部的 `spawnSync(process.execPath, …)` 报 **`EBUSY`**；连最小复现也失败：
`node -e "require('child_process').spawnSync(process.execPath,['-v'])"` 在 **managed 与 system node 上都报 EBUSY**
⇒ 这是**主机/沙箱对「node 自旋 node」的限制**，不是仓库缺陷（本机无 `wsl.exe`、无 Docker，无法绕过）。

1. **结构性理由**（本机可判，充分条件）：生成器的输入只有 `schemas/catalog/capabilities.json` 与

   ⇒ **输入不变 ⇒ 生成物不可能漂移**。

## 八、方法论教训

1. **不要接受任何一方的清单**。本轮两份主张各有对有错：外部审视的**产品向批评成立、多项技术判断不成立**；
   而双方**都没发现**的 D1–D7 里，有两条是活文档里的硬矛盾（含一条**基线指针停在 V3.5** 的严重项）。
   **核实产出的问题比被核实的清单更多**——这本身就是「不以综述代仓库」的价值证明。
2. **「如实登记」不等于「已处理」**。D7 被两轮 ADR 记为遗留而带着矛盾继续存在；§18.1 早已登记「首版面过宽」
   却没有重排资源。**登记解决「可以说清」，不解决「按什么顺序做」，也不解决「开发者该读哪一段」。**
3. **同一条不实陈述会散落在多个活文档**（C6 实测四处）。订正时必须**全仓扫描同类陈述**，而不是只改主规范那一处。
4. **易漂移的计数与版本号 MUST NOT 写进活文档**（C8/C9）。写死篇数、写死「以 VX.Y 为统一基线」，
   都在制造下一轮的技术债。
5. **升基线不只有「纯追加」一种形状**。当矛盾已存在，追加只是把矛盾登记第二遍；**就地订正**才是可用的形状——
   但它的代价必须被**可复核地**钉住：**1:1 行替换、零增删**（本轮 24 hunk / 42 行 / `a`、`d` 型 hunk 为 0）。
6. **只断言「非空」的门控是空洞门控**。能力包断言必须是**三向**的（集合完整 / 无混入 / 与首版门槛不相交），
   并用**三种注入**证明它确实会失败；把一条能力包条目复制到别的线，集合计数不会变。
7. **数字口径要自己数**：cargo 的包装行会让测试目标数**多 1**（70 vs 69）；`cmd | tail`/`| tee` 会吞退出码。
8. **本机跑不了 ≠ 可以不写**。`cargo xtask schema --check` 在本机报 `EBUSY` 是**主机限制**（node 自旋 node）；
   正确做法是**写清限制**、给出**结构性理由**当替代取证、并**指到 CI 的对应步骤**，然后**真去看 CI 结论**。
   **不要把「跑不了」写成「已通过」**，也不要因为跑不了就把这条验证从报告里删掉。
9. **代码写完文档 ≠ 文档就对了**：本轮 ADR 先写、之后又在基线文档补了一处订正（§47.6 编号说明行），
   规模随之从 23 hunk / 41 行变成 **24 / 42**，而 ADR 里的三个数字**没跟着改**（已由后续提交 `0e938a9` 订正）。
   **凡文档内出现可实测的数字，改完后要重新数一遍**；ADR 的「可复核不变量」如果自己不自洽，就失去了意义。
