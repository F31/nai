## 一、勘定与现测

### 1.1 先量 W149 的残余，再决定立不立项

ADR 0123 残余第 1 条是「归档 `tasks.md` / `specs/` 的结构无判据」。W149 之后它是最顺手的下一轮，
所以先量：

| 事实 | 值 |
| --- | --- |
| 归档变更目录 | **146** |
| 有 `tasks.md` | **146**（缺 0） |
| 有 `specs/` | **146**（缺 0） |
| `specs/` 里没有 `spec.md` 的 | **0** |
| 每个变更的 delta 份数 | `1: 122 / 2: 17 / 3: 6 / 4: 1`（178 份，24 个多能力变更） |

结论：这一半今天**零信号**。照抄立项会写出一条必然全绿、且没有真实失效模式的判据——
「今天 146/146 都齐备」不是一条判据能守的东西，它只是在描述现状。于是转向同一份登记里更硬的那格。

### 1.2 「归档了」与「合入了」之间

`openspec archive` 做两件事：挪目录、把 delta 合进主规格。第二步在人的记忆里等同于第一步。
量出来是这样：

| 事实 | 值 |
| --- | --- |
| 归档 delta 文件 | **178** |
| delta 里的 `### Requirement:` | **539** |
| 主能力 / 主规格 `### Requirement:` | **43 / 497** |
| 段标记 | `ADDED Requirements` 164、`MODIFIED Requirements` 34、`REMOVED` **0**；非标记标题只有 `Purpose` 53 |
| 按标记计数 | `ADDED` 497 / `MODIFIED` 42 / `REMOVED` 0 |
| delta ⇒ 主规格 | 539 条全在主规格（缺 **0**） |
| 主规格 ⇒ delta | 497 条也全有出处（无出处 **0**） |
| 逐能力比对 | **43 / 43 相等**；`deltas_only []`、`main_only []` |
| 空 delta / 段外 Requirement / 重名 / 头部形态异常 | 0 / 0 / 0 / 0 |
| 代码围栏 | 主规格 0 份、delta 0 份 |

围栏那行不是凑数：W148 里围栏把标题行藏住过一次，所以本轮先量了它。两侧都是 0 ⇒ 不需要
围栏解析，省掉一整层复杂度（而 W148 必须解析）。

### 1.3 零信号的证明（本轮唯一的破坏性探针）

把 `openspec/specs/local-autonomy/spec.md` 里一条 `### Requirement:` 手工改名——等价于
「归档了但没合入」——然后跑两层现有校验：

| 命令 | 探针前 | 探针中（改名之后） |
| --- | --- | --- |
| `openspec validate --all --strict` | 43 passed / 0 failed | **43 passed / 0 failed** |
| `openspec validate --archived` | 146 passed / 0 failed | **146 passed / 0 failed** |

两层全绿。`--strict` 判主规格自身形状，`--archived` 判归档记录能不能解析，谁都不问两者**之间**。
探针后 `cp` 备份还原 + `sha256sum -c`：`openspec/specs/local-autonomy/spec.md: OK`
（基线指纹 `0538cdf9d5ba67e57737dc882ef2e86732e733c0a357bc3e44a7a63b3838f438`）。

### 1.4 `MODIFIED` 的先存性：必须先量，因为量完决定「不判」

42 条 `MODIFIED` 里 **40** 条改的是此前已被 `ADDED` 过的 Requirement，**2** 条改的是更早就存在的：

- `2026-10-08-w02-w03-admission-hardening` | `decision-log-integrity` |「Criticality-tiered writes with bounded buffer」
- `2026-10-09-engine-broker-frame-delivery` | `runtime-composition` |「Honest supervision boundary」

如果判「`MODIFIED` 的目标必须在此前的 delta 里出现过」，这两条合法历史会被判红。所以决定**不判**，
并把这两条的形状写成一个绿灯用例（`modifiedFirst`）钉住这个结论。

## 二、判据形态

`specMergeErrors({deltas, specs})` 是纯函数，域由调用方给；真实语料侧由测试从 `.git/index` 派生。

1. **顺序重放**（不是集合并集）：按归档目录名（日期前缀 ⇒ 字典序即时间序）依次作用——
   `ADDED` / `MODIFIED` 加入，`REMOVED` 删除。并集会把「加了又删」与「从没加过」变成同一件事。
2. **两方向各自具名**：`delta − 主规格` = 「归档了但没合入」；`主规格 − delta` = 「没有归档出处」。
   `REMOVED` 的另一方向单独措辞（「删了却没删」）——用「没出处」报它，那句话是假的。
3. **段标记闭世界**：`##` 标题只允许三类 mark 与 `Purpose`；不认识的标题、落在段外或 `## Purpose`
   之下的 Requirement，一律具名失败。静默跳过等于把那条 Requirement 藏起来。
4. **能力整体缺席只报一条**：逐条报会把「这份主规格不存在」稀释成 N 个数字。
5. **无法重放的能力跳过比对**：归档目录列出某能力但读不到 `spec.md` ⇒ 报一条然后 skip。
   拿残缺的重放集去比会造出「主规格里有一条没出处」的假结论——把「不知道」写成「没有」。

## 三、设计期的三次收缩（每一条都是「本来要写，量完决定不写」）

- **差一点写成 `deepEqual(重放, 主规格)`**：实测 43/43 逐能力相等，等式今天成立。但它把
  「补合入」与「补记录」两种失败压成一句，且未来任何合法的结构性重排都会把它判红 ⇒ 拆成两方向。
- **差一点判 `MODIFIED` / `REMOVED` 的先存性**：见 1.4，两条真实反例。
- **差一点判 Requirement 正文**：`MODIFIED` 改的正是正文。但那需要「哪一版正文算合入」的口径，
  本判据给不出。改成只判名字之后可验证：两次合法手改主规格（`971391d`、`a8a9a64`）都只动正文、
  没动名字 ⇒ 只判名字既够用、也不会误红它们。

## 四、判据与注入

**5 条用例、三层独立输入域**：真实语料基线（零错 + 非空洞五项 + 重放顺序）；合成样本（每条缺陷
各一个「只有它错时才红」的样本）；域本身（重放顺序与两个域只由归档布局决定）。

真实语料实测：`changesChecked 146 / deltasChecked 178 / capabilitiesCompared 43 /
requirementsReplayed 497`，`errors []`。**非空洞五项**里最关键的一项是：重放出来的 497 与
主规格里数出来的 497 相等——两个数字分别由 delta 侧与主规格侧独立算出，判据自己造不出这个相等。

**五组注入**（逐次 `sha256sum -c` 还原，基线 `c8109b2cd03866651568cc1b98c3da40d70064c7a6c9eab725aeceb5be87b4cd`）：

| 注入 | 效果 | 红的是哪条 |
| --- | --- | --- |
| W1 `REMOVED` 分支失效（退化成集合并集） | **2 红** | `#2`（加了又删）、`#3` |
| W2 去掉 `delta ⇒ 主规格` 方向 | **2 红** | `#3`、`#4` |

## 五、诚实边界

1. **`REMOVED` 分支在语料上零样本**（0 处）⇒ 只由合成用例覆盖，不由真实语料验证。判据仍要它，
   因为它是 delta 语义的一部分，代价只有一行。
2. **「主规格没有 `## Requirements` 段」也是零样本**（43/43 都有）⇒ 同样只由合成用例覆盖。
   它做的是一件事：把「每个 Requirement 各报一遍」压成一条。这条分支是防噪声，不是防漂移。
3. **判据只判 Requirement 名**，正文与 Scenario 的增删改不判（理由见三）。
4. **域边界**：未跟踪的归档目录不在域内（域来自 `.git/index`）——与 W135 的 `pending-registration`
   同一条边界，两者不互相替代。
5. **本轮的「零信号」结论只覆盖 Requirement 名**：探针改的是名字。改正文是否同样零信号**没量**，
   不声称。

   该通道本轮未被执行验证。故障归因能力在这一轮**未被证明**，只被证明「不需要」。
3. **`steps` 条数不是步骤数**：两平台各记录 **20** 条，编号 1–16 之后**跳到 30–33**

**一处订正**：既有纪律里「`if` 未触发的步**不生成记录** ⇒ 编号会跳」这半句与本轮实测**不符**——
被跳过的那几步**有**记录，`conclusion` 就是 `skipped`（上表第 8/11/14 行即从记录里读出）。
17–29 空号的成因本轮**没有确立**（不猜）。可用的结论只剩两条，与本轮一致：
`steps` 不能当计数用；不能由「编号跳」反推「有几步没跑」。

## 八、具名登记（本轮发现但不做）

1. **`archive.js` 的 non-blocking 语义仍在**：本轮在**提交后**补判，没有让归档动作本身阻塞。
   这与 W149 同一条处置（外部工具的退出码不在本仓库控制范围内）。
2. **归档 `tasks.md` 的段结构未判**：本轮只量了存在（146/146），**没量结构**，故不立项
   ——「没量过」不等于「量过且为零」，这两件事 MUST NOT 混同。
3. **主规格里 Requirement 重名未判**（今天 0 处）：重名会让集合比对静默塌缩。那属主规格自身形状，
   是 `--strict` 与 registry 的地盘，本判据不重复定义同一件事。
4. **`REMOVED` 的先存性未判**：语料 0 处，没有真值可校准。
5. **W147 §八第 1 条（`LNK1104` 宿主成因）仍未判**：需动宿主配置做对照实验。
6. **W148 / W145 / W146 §八其余若干条**仍在列，本轮没有接手。
7. **`steps` 编号 17–29 空号的成因未确立**（§七）：本轮只把「不能按数量断言」这条留住，
   没去查它为什么空。它不影响任何判定（观测是人工读的，不是脚本按编号对齐的），
   所以按「具名登记、不顺手修」处置。
