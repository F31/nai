## 二、技术架构现状

### 2.1 分层与规模

```
apps/     desktop · engine · output-keeper · render-worker      （4 个可执行体）
crates/   nai-kernel(21.5k)  nai-storage(9.7k)  nai-runtime(8.6k)
          nai-upgrade-core(7.3k) nai-media-core(5.9k) nai-provider-core(4.6k)
          nai-contracts(3.5k) nai-knowledge-core(3.0k) nai-control-api(2.5k)
          nai-plugin-sdk(2.1k) nai-plugin-hosts(1.9k) nai-budget-core(0.7k) nai-security(0.5k)
xtask/    门控、契约生成、SBOM、依赖边界、secrets
packages/ contracts-ts（由 proto 生成）
```

- Rust **83k 行** / TS+TSX **18.7k 行** / 文档 md **20.2k 行**
- 契约以 proto 为唯一事实源，`packages/contracts-ts` 是生成物——这是架构上最健康的一处，应保持。

### 2.2 三层判定模型（项目的核心设计纪律）

整仓反复出现的形态是「**判定面 → 执行体 → 调用方 → 真实产生者**」四环：

1. `nai-kernel` / `nai-knowledge-core` 出**判定面**（纯函数，无 IO）；
2. `nai-runtime` / `nai-storage` 出**执行体**（真实读写）；
3. `apps/*` 出**调用方**；
4. 外部事件源才是**真实产生者**。

`status` 只在四环都闭合时才升档——这是 `H17` 本轮接线后仍保持 `pending` 的原因，也是「不实声明零容忍」这条纪律的落点。**这个模型本身是对的，不要动。**

## 五、优化方案

### 5.1 敏捷：把「一条一轮」改成「一组一轮」（收益最大，零风险）

- **H 族 18 条按内聚度切成 4 组**，例如：
  - H01–H04：装配与记忆
  - H05–H08：意图、缓存与授权
  - H09–H12：工具与 MCP
  - H13–H18：A2A、观测、降级、爬坡
- **M 族 18 条同理切 4–5 组**。
- 一个 `openspec change` 覆盖一组（3–5 条），一次门控、一次提交、一次 CI。
- **预期**：42 轮 → 约 **9–12 轮**；每轮 token 增加约 40%，总量降约 **70%**。

### 5.2 高效：门控与 CI 分层

- 本机日常改动只跑**受影响 crate 的测试**；`--profile full` 只在一组收口时跑一次。
- CI：把 windows job 从「每次都跑全量门控」改为
  - `ubuntu` 跑全量门控（7.5 分钟，快反馈）；
  - `windows` 只跑**构建 + 平台相关测试**，全量门控按日/按 release 跑。
  - 或把 13 个 crate 分片到 3 个并行 job。
- 已加的 `RUST_TEST_THREADS=4` 是**环境适配**不是解法，分片才是。

### 5.3 轻量：文档产出减半

| 现状 | 建议 |
| --- | --- |
| 每轮写 ADR（110 篇） | **只在架构分叉时写 ADR**；例行轮次不写 |
| 每轮写报告（137 篇） | 保留，但**压到 5 节以内**；多条目合一轮后自然减少 |
| dev-plan + knowledge 双写 | 合并为一处：**dev-plan 只记「缝/改动/判据」三行**，细节进 knowledge |
| openspec proposal + design 两份 | 例行轮次合并为一份 `proposal.md`；`design.md` 只在有取舍时写 |
| 回填提交（docs-only） | **取消**：报告与提交在同一次提交里完成，省一次提交 + 一次 CI 观测 |

### 5.4 易用：降低「开工成本」

- 把「每轮必做的勘定动作」固化成一个 xtask 子命令（如 `cargo xtask next`），
  自动输出：候选族分组、条目原文与 notes、涉及的承载物文件——省掉每轮开头的探索式读取。
- 把 `registry.yaml` 的双引号转义坑、限并发、LNK1104 处置等写进 `xtask` 的错误提示里，
  而不是靠每轮重新踩。

### 5.5 保持不动的部分（重要）

以下三件事**是本项目的质量来源，不要为了提速牺牲**：

1. **四环判定模型**（判定面/执行体/调用方/真实产生者）与「`status` 只由证据决定」；
2. **非空洞注入验证**（每条新守卫必须被注入证明真红，基线必须是 fmt-clean 的最终字节）；
3. **契约以 proto 为唯一事实源**。
