# ADR 0115：utterance 取值域——一处声明、可用性白名单化、幽灵值具名不猜测

- 状态：已接受（W141，2026-10-18）
- 基线：`docs/直播数字人 + 智能体系统技术方案 V3.11.md`
- 相关：W139 勘定报告 `docs/reports/2026-10-18-w139-causal-chain-appraisal.md`（第 5 结论与 N1）、
  W140 报告 `docs/reports/2026-10-18-w140-media-causal-lineage.md`（N2 把这一项留给了本轮）、
  ADR 0114（W140 在媒体侧做同一件事：`NodeState` 终态由一处派生）、
  `crates/nai-storage/src/utterance_status.rs`

## 背景

`utterances.status` 在 `migrations/sqlite/0001-foundation.sql` 里是
`status INTEGER NOT NULL DEFAULT 1`：**没有 CHECK 约束、没有枚举、没有常量**。
它唯一的「定义」是散落在 SQL 字符串里的裸字面量，而且有**四套**互相不一致的集合
（本轮开工前逐条现测，与 W139 的计数全部吻合）：

| 集合 / 写入 | 处数 | 出处 |
| --- | --- | --- |
| `NOT IN(11,12,13,14,15)` 级联保护 | 6 | `store.rs` 4 + `knowledge.rs` + `publication.rs` |
| `NOT IN(12,13,14,15)` 可用性 | 3 | `store.rs` 三处 |
| `BETWEEN 1 AND 5` 待批准带 | 3 | `store.rs` 三处 |
| `SET status=N` 写入 | 9 | `1` / `6` / `12`（×6）/ `14` |
| 撤回审批时读取 | 3 | `approvals` 撤回语句里的 `status=12` |

分歧点只有一个值 **11**：它在级联保护集里（不被改写），却不在可用性黑名单里（被当成可用）。

W139 的阻断 ① 写得很直接：「`status` 是裸整数且三种终态口径互相矛盾 ⇒
在建关系之前先得有单一列举，而这本身是另一轮的活」。本轮就是那一轮。

## 决定

1. **取值域收成一处声明**：`crates/nai-storage/src/utterance_status.rs`。
   四个有写入者的具名取值（`1` 待批准 / `6` 已批准 / `12` 已失效 / `14` 已拒绝）+
   三条带（待批准带 `1..=5`、不可用带 `12..=15`、级联保护带 `11..=15`）。
   生产源码里的 status 数字全部由这些常量派生 ⇒ SQL 里不再有裸数字。
2. **分类闭世界**：`classify()` 对任意 `i64` 返回五格之一
   （`Pending`/`Approved`/`Unusable`/`ProtectedOnly`/`Unassigned`），`else` 落到 `Unassigned`。
   「不知道」有一个**可表示的取值**，调用方不必在「撒谎」与「不调用」之间选。
3. **可用性从黑名单改白名单**：`usable()` 只认 `Pending | Approved`。
   这是本轮**唯一**的行为变化：`11`、`7..=10`、`16..`、`0`、负数由可用变不可用。
   已写入的取值（`1`/`6`/`12`/`14`）判定完全不变。
4. **`11` 不裁定**：它留在 `ProtectedOnly`（只受级联保护、不是终态、也不是活跃），
   并具名登记为「语义未定、本仓零写入者」。

## 理由

- **为什么白名单而不是黑名单**：黑名单把「还没人声明过的取值」默认判成可用，
  而可用是危险方向。不对称时选安全一侧 —— 这是「两处口径不一致时选拒绝」的直接应用：
  本轮既**不合并**（保留保护带与可用集两个集合）也**不放宽**（不把 11 加进可用集），
  而是把两者的差异**归因**到一处声明。
- **为什么不裁定 11**：裁定需要它的写入者先存在，而它今天零写入者。
  把 11 并进终态是替它选了一边；给它编一个语义名字是把「不知道」写成「知道」。
  两者都是不实声明。本轮改为配一条**会过期**的断言：谁新写一句带 11 的 SQL 都会让判据变红。
- **为什么真实形状是「带 + 具名值」而不是枚举**：`BETWEEN 1 AND 5` 说明 `1..=5` 是一个**带**，
  不是五个枚举值。做成完整枚举会伪造出五个并不存在的状态名。
- **为什么 `usable_values()` 扫全域而不是只扫 `[1, 已批准]`**：注入验证实测到的盲区 ——
  区间窄时 `usable()` 退化成黑名单写法，`1..=6` 两种写法结果相同 ⇒ guard 一字不变 ⇒
  行为判据**不会红**。改为扫 `[0, 不可用带上界]` 后，同一注入让 4 条判据变红。
- **为什么 `classify` / `usable` 必须有生产消费者**：只被判据引用的判定面是装饰
  （`dead_code` 告警已经指出来了）。改为 `usable_values()` 由 `usable()` 派生，
  派生链真的通到 SQL。

## 后果

- 新增任何带 status 数字的 SQL MUST 先去声明处给那个值名字与归类，否则判据红。
- `utterances.status` 在**数据库层面**仍无 CHECK 约束 —— 本轮只锁住了**代码**这一侧。
  给列加约束需要迁移，属独立一轮（见报告具名登记）。
- 可用性判据变严 ⇒ 若将来有代码真的写入 7..=10 或 11，它会**静默变得不可用**而不再被播出。
  这是有意的（安全方向），但新写入者 MUST 同时更新取值域声明，否则会出现「写进去了却播不出来」
  而无人报告的情况。

## 验证

- `crates/nai-storage/src/tests/status_domain.rs`：扫描器自检、零裸字面量、
  SQL 守卫与 Rust 谓词逐值一致、白名单行为（走真实 `Store::approve`）、
  级联保护带行为（走真实 `store::recover`）。
- `utterance_status.rs` 模块内 3 条：闭世界与反方向、白名单、两带一致且不相交。
- 四组注入全部真红且可归因，随后逐字节还原（`sha256sum -c` 3/3 OK）。
