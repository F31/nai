## 背景

[ADR 0047](0047-design-baseline-v38.md)（2026-10-11）把唯一实现基线从 V3.7 升为 **V3.8**，理由是 V3.8 是 V3.7 的严格超集。
本轮（**W65**）面对的问题与上一轮**性质不同**：不是「基线缺了什么能力」，而是**范围与门槛**——

V3.8 把第四部分（Harness 与开放互操作，§40–§48）整段写进了 **R1 首版门槛**：声明式技能、官方只读技能、市场客户端、
意图识别、语义缓存、工具循环、MCP、A2A 与 harness 黄金集**全部**是 R1 的一部分。**「已设计」被当成了「已承诺」**。

本轮的起因是一次**外部审视**（对 V3.8 的五维批评：产品定位、过度设计、功能优先级倒挂、组件数失控、
「轻量 / 敏捷」自相矛盾）与用户对它的**反批评**（认定产品向批评成立、部分技术判断不成立）。
双方的主张都被逐条取证核实，裁定见 `docs/reports/2026-10-11-v38-review-adjudication.md`。本 ADR 只裁决**基线与机制**，不重复该报告的逐条裁定。

## 决策

### 决策 1：V3.9 升为唯一实现基线

V3.9 保留 V3.8 的全部条款（**新增**第五部分，**无删除**），并把默认运行范围收缩为可判定的形态。升基线**不损失任何既有条款**。

- `docs/design.md` 指向 V3.9；
- `README.md`、`AGENTS.md`、`docs/development-plan.md`、`docs/engineering.md`、`openspec/config.yaml` 同步；
- V3.8 降为**历史参考**（与 V3.7/V3.6 同等处置）：仅追溯，不自行拼接旧条款覆盖 V3.9。

### 决策 2：ADR 0047 的决策 1 被替代，决策 2–5 继续有效

ADR 0047 有五项实质决策，**只有决策 1（V3.8 升基线）**由本 ADR 替代：

- **决策 2（ADR 0042 的决策 2/3 继续有效）继续有效**；
- **决策 3（`§NNN` 只改版本前辍、代码 doc-comment 不订正）继续有效**——本轮的行号对齐事实（41 行全为 1:1）
  正是它的适用前提，故 `§NNN` 的**数字不作变更**；
- **决策 4（H 系列就地登记，不重复 ADR 0042 决策 4 的缺口）继续有效**——本轮只改 29 条的**归属**，**不改任何 `status`**；
- **决策 5（明确不改什么）继续有效**（不实现 harness 代码、不重排 W 编号、不扩张记忆字段集）。

ADR 0047 **保留原文不改写**，仅在末尾追加「勘误（ADR 0048）」段（历史记录追加勘误，不就地改写）。

### 决策 3：**首次**确立「就地订正」与「纯追加」的边界（V3.9 §56.2）

前两轮升基线采用**纯追加**，前提是「**无矛盾可订正**」：V3.6→V3.7 与 V3.7→V3.8 只补新内容，与既有条款不冲突。
本轮不同——D1–D7 是**已声明内容与已实现/已登记内容互相矛盾**。此时继续纯追加，只是**把同一条矛盾登记第二遍**，
把判断责任留给开发者。故本轮确立一般规则：

- **活文档**（主规范当前有效内容、`docs/*.md`、`AGENTS.md`、`tests/registry.yaml`）⇒ **就地订正**；
- **历史记录**（`docs/reports/`、`docs/adr/`、`openspec/changes/archive/`）⇒ **保留原文 + 追加勘误段**；
- **版本专属陈述**（§39 是 V3.7 的、§48.1/§48.2 是 V3.8 的「变化」与「阅读路径」）⇒ 保留原文；
  跨版本索引（§48.5、§48.6）除外，就地订正；
- **代码 doc-comment 的版本前辍** ⇒ 不随基线变（ADR 0015 先例）。

**这条规则同时是约束**：就地订正 MUST 保持 1:1 行替换（不增删行），否则会以「订正」为名破坏 `§NNN` 引用契约。

### 决策 4：新增第六条发布线 `capability_pack`，使收缩**可机器判定**（V3.9 §51.1、INV-33 / INV-34）

「已设计」与「已承诺」是两个不同的陈述，而此前只有前者有地方可写——**降级无处表达，只能删除**，
于是要么全留 R1（范围膨胀），要么整体砍掉（丢失边界）。本 ADR 新增第六条发布线解决这个二难：

- `tests/registry.yaml` 的 `release_lines` 增 `capability_pack`；**29** 条（M01–M18、H05–H14、H16）由 `r1`/`r2` 改为 `capability_pack`；
- 收缩后分布：`slice_0` **10** + `r1` **36** + `r2` **9** + `capability_pack` **29** + `r3` **1** + `experimental` **2** = **87**（与 V3.8 相同——**只改归属，不加条目**）；
- `scripts/contracts/registry.mjs` 增**三向断言**：能力包集合 MUST 恰为上述 29 条 / MUST NOT 有归属外的 id 被标为能力包 /
  **MUST NOT 有任一能力包 id 落在 `slice_0`、`r1`、`r2`**（后者即 **INV-33**）；失败时**指名 id 与当前线**；
- `schemas/tests/registry.schema.json` 的 `release_lines.required`、`.properties` 与
  `acceptance.release_line.enum` **两处**均加 `capability_pack`（同一硬编码出现两处，必须同改）；
- 非空洞守卫：`tests/registry.test.mjs` 以**三种注入**验证断言确实失败——把 `M01` 提回 `r1`（须报 `INV-33` 与 `M01=r1`）、
  把非能力包 id（`H17`）标为 `capability_pack`（须报「超出 §51.3 集合」与 `H17`）、清空整条能力包线（须报集合不完整与 `M01`）。

**配套不变量**（V3.9 §49.3）：**INV-33** = 默认组合不依赖能力包（R1 内每条验收 MUST 在未安装任何能力包时可判定）；
**INV-34** = 降级不删边界（边界、信任域归属与不变量 MUST 保留，且 MUST NOT 使既有 `§NNN` 引用失效）。
新增威胁 **T-25**（范围漂移：能力包被读成首版承诺，或默认组合暗中依赖能力包），控制即上述机器可判定分线。

**为什么这满足用户的既有约束**：INV-33 是「**重点降低运行维护成本**」与「轻量」的**可判定形式**（轻量由**默认组合**定义，
不由**能力上限**定义）；INV-34 是「**不降低扩展性和灵活性**」的可判定形式（降级是**排期**动作，不是**设计**动作）；
而「Lite/Standard/Pro 共用稳定内核并支持平滑升级」由 §51.4 保证——能力包的加装路径沿用**同一条**升级与迁移图（§14.3），
**MUST NOT** 出现第二条安装路径，且启用 MUST NOT 改变默认组合的行为、成本或降级顺序。

### 决策 5：本 ADR 明确不改什么

- **不改任何 acceptance 的 `status`**：87 条状态原样，本轮**只改 29 条的 `release_line`**；
- **不新增契约名、不改能力目录**：§56.3 沿用 §46.5 的三条理由 ⇒ `schemas/catalog/capabilities.json` 与全部生成物
  **零漂移**；`memory.access@1` 的阶段以目录（`frozen`）为准，本轮只订正 §20.6 的**陈述**；
- **不删除任何能力**：§57.1 明写「**本版砍掉的：无**」——本版是**范围重排**，不是能力删除（由 INV-34 保证）；
- **不实现任何代码**：W65 只动文档、注册表、门控脚本与 schema，**Rust 侧零改动**（`xtask/src/registry.rs` 仅一处输出串）；
- **不重排 W 编号**：第五部分从 **W65** 起编号（V3.8 计划止于 W64）；
- **不整体移出第四部分、不删 workspace 作用域、不删决策日志**（§57.1 的 M9 行）。

## 后果与实施

- 活文档的基线指针与 §-引用统一为 V3.9；除历史记录与代码 doc-comment 外，活文档不再出现 `V3.8` 作为**当前基线**的陈述。
- 后续开发按 V3.9 的六条发布线与 `tests/registry.yaml` 推进；**R1 收缩为 36 条 + Slice-0 10 条**，
  能力包 29 条**不进首版门槛**，但保留设计边界与不变量。
- 每版本的变化表**从此强制四栏**（新增 / 砍掉 / 延后 / 降级为能力包），四栏**同权重评审**；
  只有「新增」栏的版本 SHALL 被读作**未做范围评审**（V3.9 §49.2）。V3.9 是第一条适用记录（§57.1）。
- **已知代价（如实登记）**：本轮**首次**改动 §1–§48 的既有内容，因此本 ADR 提供的是
  「23 hunk / 41 行 / 全 1:1 / 零增删」这一**可复核的**不变量，而不是「只增不改」这句更容易的话。
  与之交换的是：既有 `§NNN` 引用全部继续有效（已由 `diff` 实测）。
- **两处易失效陈述已改为不写死的形式**（C8、C9）：`docs/control.md` 的 ADR 篇数、`openspec/specs/spec-driven-delivery/spec.md`
  的基线版本号。**易漂移的计数与版本号 MUST NOT 写进活文档**——这正是「文档一致性下降」的一个具体成因。
  该项同时关闭 ADR 0047 的遗留 5（该 ADR 曾把 V3.5 指针登记为遗留而**不**订正；按 V3.9 §56.2，遗留陈述
  MUST NOT 靠纯追加长期存续）。
- **遗留（不在本 ADR 范围）**：
  1. **能力包零实现**：M01–M18、H05–H14、H16 全部 `pending`，W58–W62 与 W64 未开始；
  2. **R1 仍有 36 条未实现**（§57.3 的正本口径）；
  3. **平台准入**（§52）三条命题的硬门槛**均未取得证据**：书面允许、事件稳定进入本机、官方输出路径——
     本 ADR 只把它们拆开并设为独立门槛，不宣称任何一条已成立；
  4. **产品视角未经验证**：§54.2 的用户画像初版**未访谈**，MUST 在 R1 实现期以真实使用者验证后才可作为档位依据；
  5. **D3 的 `memory.access@1` 阶段**以能力目录为准（`frozen`），本轮只订正陈述，不追究其冻结轮次；
  6. 能力包的**打包粒度**（市场客户端、MCP/A2A 是否各自独立成包）待实现轮裁定（§57.5）。

## 勘误

无。本 ADR 撰写于判决当日，尚无被后续证据推翻的陈述。
