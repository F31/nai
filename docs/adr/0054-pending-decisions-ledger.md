# ADR 0054：待裁定项的登记与寿命——悬空的问题也要有寿命

- 日期：2026-10-12（W76）
- 状态：已接受
- 相关：ADR 0051 决策 2（偏差台账的跨版不变式；本 ADR 沿用其「入参显式注入、缺即报错」的纪律）、ADR 0050（冻结基线与注册表的对账）、§56.2（活文档 vs 历史记录的分界）
- 依据章节：V3.10 §18.2、§39.7、§48.7、§57.5（四章待决策与待确认，一条累积链）、§52.1、§46.2、§46.3、§46.5、§51.3、§41.4、§5.5、§54.2

## 背景：四章「待决策」只有载体，没有台账

基线有四章「待决策与待确认」，它们是一条**累积链**：§39.7 沿用 §18.2 全部，§48.7 沿用 §39.7 全部，
§57.5 沿用 §48.7 全部。去重后的唯一集合是 **34 条**，分章新增数为 §18.2 **10**、§39.7 新增 **11**、
§48.7 新增 **10**、§57.5 新增 **3**。

这 34 条此前只有**载体**，没有**台账**。三类后果：

1. **「待裁定」读起来像「无人负责」。** 没有状态、没有依据、没有闭合条件 ⇒ 无法回答「哪几条其实已
   有答案」「哪几条卡在什么上」「哪几条只是等外部事实」。
2. **已有答案的条目会一直悬着。** 逐条核实发现 **4 条已由基线正文回答**：

   | 条目 | 基线已有的答案 |
   | --- | --- |
   | MCP `sampling` 是否存在可接受的启用场景 | §46.2：默认禁用；启用需本机管理员授权、计入预算、逐次记决策日志 |
   | 上下文利用率观测线 | §41.4：本轮**不设**告警阈值，只登记为观测项 |
   | `a2a` 相关契约名是否设立 | §46.5：**不新增** `a2a.*` 之类契约名（三条理由） |
   | 能力包的打包粒度 | §51.3：市场客户端（M01–M18）、MCP 适配（H11/H12）、A2A（H13/H14）**已是三行独立包** |

   它们留在「待裁定」里，等于把**已决议**的东西重新打开——与 W67 把「『通过 §47.2 的回归』是
   全六类还是相关类」核实为**不是偏差**同型。
3. **外部条件没有闭合条件。** §52.1 的硬门槛就是「书面确认」——取不到就是取不到；但「取到什么算
   闭合」没写下来，于是它可以无限期地既不算完成、也不算失败。

**这不是「新增约束」，是给既有事实一个可判定的载体**——与 W72 的 `baseline_deviations` 台账、
`baseline.mjs` 的对账同属一个模式：**登记解决「可以说清」，不解决「按什么顺序做」；
台账把前者变成后者。**

## 决策 1：五态处置，每态**一个必填字段**

处置是**封闭枚举**（理由与 `release_lines`／`status` 一致：枚举让「属于哪一类」可判定）：

| 处置 | 必填 | 含义 |
| --- | --- | --- |
| `answered_by_baseline` | `basis` | 基线正文已给出答案 |
| `decidable_in_repo` | `recommendation` | 仓库内可裁定，且给出推荐 |
| `needs_precondition` | `precondition` | 需具名前置 |
| `needs_external` | `closure` | 需外部事实，写「取到什么算闭合」 |
| `out_of_scope` | `note` | 明确在方案范围外，同样要付理由 |

**把「这条有没有人管」换成一个可判定的问题——「那个字段在不在」。**
一条 `needs_external` 若没有 `closure`，与一条空注释没有区别。

## 决策 2：依据 MUST 指回**真实存在**的章节

`answered_by_baseline` 的 `basis` 是**唯一一处「台账宣称基线已答」的地方**，故它必须被拴住：
台账里出现的**每一个** `§NNN`（含 `basis`、`introduced_in`、`also_in`）MUST 出现在基线文本的
章节标题集合里。

⇒ **写一个不存在的 `§99` 会立刻失败。** 这是判据的非空洞性所在（注入 F1 实测：报
`PD-25: references §99, which does not exist in the baseline`）。

**为什么不比正文措辞**：措辞会随行号契约漂移，而「章节号存在」稳定且是足够强的下界——它排除掉
「凭印象编一个章节」。**语义上是否真的回答了那个问题，由 ADR 与报告承载，不由脚本假装判定。**

## 决策 3：外部条件 MUST 写成「闭合条件」

`needs_external` 的 `closure` MUST 非空，且写的是**取到什么算闭合**，例如
「平台出具**可留存**的书面答复，确认该账号与该类目的数字人自动互动被允许」。
MUST NOT 写成「待平台确认」——后者与空注释没有区别。

同理 `needs_precondition` 的每个前置 MUST 是**真实存在**的东西：registry 里的验收 id，
或基线工作项表里的 `WNN`。**把待裁定项挂在不存在的东西上，等于把它挂在了空气上。**

## 决策 4：覆盖性与分布**逐章、逐类写死**

- `CHAPTER_COUNTS`：四章的**新增**条数（10／11／10／3），用于断言覆盖性；
- `DISPOSITION_COUNTS`：五态分布（4／5／4／20／1），用于断言**类别不被悄悄改**；
- `TOTAL_ENTRIES` = 34。

**这是对 W66 教训的直接应用**：只校验总数对「内容被改小／被改类别」是瞎的——实测悄悄删一个必需
字段，全部测试照样绿。注入 F2（改一条的首次出现章）与 F3（改一条的处置类别）分别实测：**只报总数
的实现看不见 F3**，故分布必须单独写死。

## 决策 5：与既有台账**不合并**

| 既有机制 | 关系 |
| --- | --- |
| `baseline_deviations`（W72/W73） | 那是**已发生的偏离**台账（现为空）；本台账是**未决的问题**。维度不同，**不合并** |
| `baseline.mjs` 的对账 | 管「基线 §57.3 ↔ registry」；本台账管「基线待裁定章 ↔ 处置」。同构而对象不同 |
| `tests/registry.yaml` | 验收条目；本台账**不动 registry**、不新增验收条目 |

## 后果与实施

- 新增 `tests/pending-decisions.yaml`（34 条）与 `scripts/contracts/pending-decisions.mjs`
  （`DISPOSITIONS`／`REQUIRED_FIELD`／`CHAPTER_COUNTS`／`DISPOSITION_COUNTS`／
  `validatePendingDecisions(ledger, deps)`），断言并入 **既有** `tests/registry.test.mjs`
  ⇒ 随 `check --registry` 执行，`xtask/src/lib.rs::engineering_checks` **零改动**（W74/W75 同一条处置）；
- **入参显式注入**：`{baselineVersion, baselineText, acceptanceIds, workItemIds}`，缺任一项即报错，
  MUST NOT 因入参缺失而恒真（ADR 0051 决策 2 对 `normalizeDeviations` 的原话）；
- `ledger.baseline` MUST 等于**当前基线版本** ⇒ 升基线后忘更新会红。这是刻意的：一份对着旧基线写的
  台账，其「§NNN 存在」的结论对新基线不成立；
- **不改基线正文**：§48.7 与 §57.5 是**版本专属陈述**（按 §56.2 情形③保留原文）。关闭已答项只发生在
  台账与 ADR 里；进入基线要等一次升基线轮次——与 W68 的 B07、W67 的「影子在 R1 无落点」同一处置；
- 不新增 xtask 子命令、不新增契约名（§46.5）、不新增证据目录（§30.1 的八个是闭合集）。

## 遗留

1. **台账的 34 条只登记「处置」，不替外部条件排期**：19 条 `needs_external` 的闭合仍取决于平台、
   供应商、市场项目与目标机；台账让它们**可追踪**，不让它们**可完成**。
2. **「已答」的语义判定仍靠人**：脚本只证「引用的章节存在」，不证「该章节真的回答了该问题」。
   这是一处**刻意留给人读**的边界，已写入决策 2。
3. **5 条 `decidable_in_repo` 的推荐尚未执行**：它们是推荐而非决定；采纳需要单独一轮
   （其中 PD-09 会触碰平台密钥后端、PD-22/PD-24 属 A2A 边界、PD-31 属 R3 前置、PD-34 需真实访谈）。
4. **`PD-23`／`PD-26`／`PD-27`／`PD-30` 四条前置跨到能力包与 W61**：能力包默认不装（INV-33），
   故这四条在 R1 内**不可裁定**是设计使然，不是遗漏。
5. **台账自身的形状契约未接电**：本轮的校验是**语义面**（在 Node 测试里），
   `tests/pending-decisions.yaml` 没有对应的 JSON Schema。是否需要，等它出现第二次结构变更再判
   （W73 的教训是「没人消费的契约会变假契约」，故此处**不预先**造一份 schema）。
6. **§58.6 的「需专门一轮」两处属于偏差门控，已由 W72 关闭**；本 ADR 不重复处理，
   也 MUST NOT 被读作把它们重新打开。

## 勘误（ADR 0066 追加；原文保留，不改写）

本轮（**W88**）采纳本 ADR 遗留 3 的第一条（`PD-09`），核实后改判了三处**计数与枚举**，
其余决策继续有效：

- **决策 1 的「五态」→ 六态**：新增 `decided_in_repo`（必填 `landing`，每个元素 MUST 是仓库
  **已跟踪**的路径）。理由不是「分类更细」，而是**五态回答的都是「何处能闭合」，没有一态表达
  「已经闭合了、落在哪里」** ⇒ 一个已结清的条目只能永远停在 `decidable_in_repo`（名为「**可**决定」）。
  故本 ADR 决策 1 的标题与表格**按现状读作六态**；「每态**一个**必填字段」这条不变式**不变**。
- **决策 1 的类别划分由三类扩为四类**：新增 `REPO_PATH_FIELDS`，与 `ID_LIST_FIELDS` **不合并**
  （解析器不同：登记 id vs 仓库成员路径）。四类 MUST 两两不相交。
- **遗留 3 的「5 条」→ 4 条**：`PD-09` 已由 W88 结清（决定已作出并已落地于
  `crates/nai-security` 与平台矩阵的 `secret-protection` 能力行）。**MUST NOT** 把它记作
  `answered_by_baseline`——基线 §11.5 明写「（具体机制待选型验证）」，是**仓库**回答了它。
- **遗留 5 的判决已经作出**：本 ADR 说「是否需要 JSON Schema，等它出现**第二次结构变更**再判」。
  W88 的人就是这次结构变更（6 态 + 1 字段 + 1 类别 + 1 依赖），判定为**不引入 schema**
  （理由见 ADR 0066 决策 7：会在同一件事上出现第二处定义）。
  （上句「W88 的**人**」应为「W88 **这一轮**」；该段已发布，按本 ADR §56.2 的边界**不改写**，在此说明。）
