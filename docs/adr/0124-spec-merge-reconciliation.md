# ADR 0124：归档增量与主规格的对账 —— 顺序重放、两方向具名、不判先存性

- 状态：已接受（W150，2026-10-18）
- 基线：`docs/直播数字人 + 智能体系统技术方案 V3.11.md`
- 相关：ADR 0123（归档记录的结构判据，本轮接手它的残余第 1 条）、
  `scripts/contracts/spec-merge.mjs`、`tests/contracts/spec-merge.test.mjs`、
  `scripts/contracts/test-reachability.mjs`（站点登记）、`xtask/src/lib.rs`（门控接线）

## 背景

`openspec archive` 做两件事：把变更目录挪进 `openspec/changes/archive/`，以及把 delta 的
Requirement 合进 `openspec/specs/<能力>/spec.md`。**第二步在人的记忆里等同于第一步**——
归档了就是做完了。仓库里这两步之间没有任何判据。

本轮把它量成数字（`openspec/` 实测）：

| 事实 | 值 |
| --- | --- |
| 归档变更目录 / 有 delta 的变更 | **146 / 146** |
| 归档 delta 文件 | **178**（每变更 1–4 份） |
| 主能力 | **43** |
| 主规格 `### Requirement` | **497**（重名 0、形态异常 0） |
| delta 的 Requirement | **539**（`ADDED` 497 / `MODIFIED` 42 / `REMOVED` 0） |
| 段标记 | `ADDED Requirements` 164 处、`MODIFIED Requirements` 34 处、`REMOVED` **0** 处；非标记标题只有 `Purpose` 53 处 |
| 重放 ⇔ 主规格 | 逐能力 **43 / 43 相等**；delta 缺 **0**、主规格无出处 **0** |
| 代码围栏 | 主规格 0 份、delta 0 份 ⇒ 标题行不会被围栏藏住 |
| `validate --all --strict` / `validate --archived` | **43 / 0** / **146 / 0** |
| 同一次探针：手工改掉一条 Requirement 名之后 | 仍 **43 / 0** / **146 / 0** |

最后一行是本 ADR 的前提：**这条缺口对两层现有门控零信号**。`--strict` 判主规格自身形状，
`--archived` 判归档记录能不能解析，谁都不问「归档的那条规矩进主规格了吗」。
探针用手工改名模拟「归档了但没合入」，两层全绿；探针后 `cp` 备份 + `sha256sum -c` 逐字节还原
（基线 `0538cdf9…f438`）。

## 决定

### 一、顺序重放，不是集合并集

delta 的语义是三类动作，不是三类名单。按归档目录名（日期前缀 ⇒ 字典序即时间序）依次作用在一个
集合上：`ADDED` / `MODIFIED` 加入，`REMOVED` 删除。

并集会把「加了又删」与「从没加过」变成同一件事——而 `REMOVED` 的存在正是为了区分它们。
今天的语料里 `REMOVED` 是 **0** 处，所以这条决定的代价必须如实写清：**`REMOVED` 分支只由合成
用例覆盖，不由真实语料验证**。判据仍要它，因为它是 delta 语义的一部分，且代价只有一行。

### 二、两个方向各自具名

`delta − 主规格` = 「归档了但没合入」；`主规格 − delta` = 「主规格里有一条从没经过归档的
Requirement」。合成一句 `重放 == 主规格` 会把两种失败压成一句话，而它们的处置完全不同：
前者补合入，后者补记录（谁、为什么）。

`REMOVED` 的落点单独措辞（「删了却没删」），否则反向检查会用「没有归档出处」把它再报一次——
那句话是假的：它**有**出处，只是出处的结论是删掉。读者看到「没出处」会以为文档写错了。

### 三、不判 `MODIFIED` / `REMOVED` 的先存性

实测 42 条 `MODIFIED` 里有 **2** 条改的是各自 delta 之前就存在的 Requirement：
`2026-10-08-w02-w03-admission-hardening`（`decision-log-integrity` / `Criticality-tiered writes
with bounded buffer`）与 `2026-10-09-engine-broker-frame-delivery`（`runtime-composition` /
`Honest supervision boundary`）。判先存性会把这两条合法历史判红，而它们改的确实是当时存在的
Requirement——只是那份出处更早、且不属于这两次变更。

处置是**不判**，并把两条样本写进用例（`modifiedFirst` 绿）。这属于「判据增强会让前提失效 ⇒
修前提、不关判据」的反面：这里的前提本身不成立，所以不加这条判据，而不是给它开例外。

### 四、能力整体缺席只报一条

「这份主规格根本不存在」与「这份主规格少一条」不是同一个量级的事。逐条报会让前者的数字变成 N
（N = 该能力重放出的 Requirement 数），读者看到的是 N，而不是「一个能力整个没合入」。
因此：能力级缺口一条消息，Requirement 级缺口逐条消息。

### 五、段标记是闭世界，放不进去就具名失败

delta 的 `##` 标题只允许 `ADDED` / `MODIFIED` / `REMOVED` Requirements 与 `Purpose`。
任何别的标题、以及落在第一个段标记之前或 `## Purpose` 之下的 `### Requirement:`，都具名失败。

静默跳过等于把那条 Requirement 藏起来：它读起来像生效了，而重放里没有它的位置。
「不认识」与「没有」在判定里是两件事——这与「不可解析 ⇒ 失败并分类，不静默降级」是同一条纪律。

主规格侧同理：只有 `## Requirements` 段里的 Requirement 参与比对，段外的一律具名失败。
`## Requirements` 段整个缺失时**只报一条**（否则每个 Requirement 都会各报一遍）。

### 六、无法重放的能力跳过比对，而不是拿残缺集去比

归档目录列出了某能力但 `spec.md` 读不到 ⇒ 该能力已在文件层具名报过一条。此时若继续比，
残缺的重放集会造出「主规格里有一条没出处」这种假结论——**把「不知道」写成「没有」**，
正是 W134 那个缺陷的形状。因此：报一条，然后 skip。

### 七、空 delta 用「全文件的 Requirement 行数」判，不用「已归属条数」判

第一版的空判定用的是「已归属到某个段的条数」。写用例时暴露：一份写着
`## CHANGED Requirements` 的 delta 会让「不认识的段」和「什么都没声明」**同时**报出——
而后者是假话，它声明了一条，只是放不进去。改成读全文件的行数后，同一条缺口只报一次，
且报的是真的那一条。

## 后果

- 门控多一步纯静态 Node 测试（读 `.git/index` 与 `openspec/` 文本，不需要 protoc、不编译）；
  站点登记 `xtask-spec-merge`，`tier: portable`（它跑在 `engineering_checks` 里）。
- **首跑为绿**：43 个能力、497 条 Requirement 今天全部对得上；判据不是「先制造红再修」。
- **规格文本零改动**：不改任何主规格、不改任何归档记录。
- **归档流程零改动**：不加 `archive.js` 的阻塞路径（外部工具语义不在本仓库）。
- **注入验证**（逐次 `sha256sum -c` 还原，基线 `c8109b2c…b4cd`）：集合并集代替重放 ⇒ 2 红；
  去掉 `delta ⇒ 主规格` ⇒ 2 红；去掉 `主规格 ⇒ delta` ⇒ 2 红；放宽段标记闭世界 ⇒ 只红 1 条；
  `REMOVED` 走通用措辞 ⇒ 只红 1 条。每条规则都有「只有它错时才红」的样本。

## 残余（具名，本轮不做）

1. **归档 `tasks.md` 的段结构未判**：本轮只量了存在（146 / 146 都有 `tasks.md`），没量结构
   ⇒ 「结构齐备」这一半今天零信号，但**没有量过结构本身**，故不立项。
   （ADR 0123 残余第 1 条的 `specs/` 半边由本 ADR 关掉；`tasks.md` 半边仍在。）
2. **Requirement 名之外的内容未对账**：本判据只判 `### Requirement:` 的名字。正文与 Scenario
   的增删改**不判**——`MODIFIED` 改的正是正文，判它需要「哪一版正文算合入」的口径，
   而那是本判据给不出的东西。两次合法手改主规格（`971391d` 修 W135 的 Scenario 正文、
   `a8a9a64` ADR 0042 改三个能力的正文）都只动正文、**没动 Requirement 名** ⇒ 只判名字
   既够用、也不会误红它们。
3. **主规格里 Requirement 重名未判**：今天 0 处重名；重名会让集合比对静默塌缩（两条变一条）。
   那属于「主规格自身形状」，是 `--strict` 与 registry 的地盘，本判据不重复定义同一件事。
4. **`REMOVED` 的先存性未判**：语料 0 处，没有真值可校准。
