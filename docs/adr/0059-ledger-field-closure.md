# ADR 0059：台账字段集的封闭性——「按清单扫」的盲区是清单的补集

- 状态：已接受
- 日期：2026-10-13
- 依据：ADR 0058（扫描域由单一清单派生）、W80（断言的「存在」≠ 断言的「覆盖」；
  「复述处可以随便编」这条推理适用面比当时想的更宽）、
  W73（假契约：每句「SHALL 被校验」都要能指出执行体）、W66（照抄表的常量要另有逐项写死的断言；
  条数对内容被改小是瞎的）、W79（搜索域 MUST 封闭：无界域会静默取到邻节）
- 影响：`scripts/contracts/pending-decisions.mjs`、`tests/registry.test.mjs`；
  **不改基线正文、不改 `tests/registry.yaml`、不改 `tests/pending-decisions.yaml`、不改任何 Rust、不新增依赖边**

## 背景

W80 把台账的引用扫描域收成**一份导出的单一清单** `CITATION_FIELDS`，并**遍历它**。这修掉了
「清单内字段整片漏扫」，但留下一个更根本的盲区——**开世界扫描**：

> 遍历一份清单的守卫，其**盲区恰好是清单的补集**。清单挡得住「清单上的字段被编造」，
> 挡不住**不在清单上的字段被新增**。

**实测（W81 探针，只用公开 API，不改被测文件）**：

```
=== 注入 UA：给 PD-01 加未知字段 rationale，内含 §99.9 ===
errors = []          ← 完全静默

=== 注入 UB：未知字段 rationale = "见 §40.4"（合法章节） ===
errors = []

=== 字段覆盖关系 ===
未覆盖字段 = id, question, disposition
```

同一探针还标出 **`question` 这个形状**：34 条条目**全部**带 `question`，而它**只有「非空」检查、
不扫引用**。它是**字面意义上的复述字段**（复述基线的提问）——W80 立的推理「复述处可以随便编」
对它**最直接适用**，却唯独漏了它。

**两个洞是同一个形状的不同层**：「有断言」与「断言有覆盖」是两件事（W80），而**覆盖对「新出现的东西」
永远需要一条闭世界断言来兜**。

## 决策

### 决策 1：`LEDGER_FIELDS` 逐字写死，MUST NOT 由三类派生

```js
export const STRUCTURAL_FIELDS = ['id', 'disposition'];
export const LEDGER_FIELDS = ['id', 'question', 'introduced_in', 'also_in', 'disposition',
                              'basis', 'recommendation', 'precondition', 'closure', 'note'];
```

派生写法（`[...A, ...B, ...C]`）会让「三类别之并 == `LEDGER_FIELDS`」成为**恒真式**——一个字都没说。
W80 §九结论 5 已立同型裁定：**只钉「关系」不够，要逐字钉内容**。三份声明各有职责且必须互相印证：
`LEDGER_FIELDS` 说「**允许出现**哪些字段」，三个类别说「每个字段**由谁负责**」。

### 决策 2：闭世界断言**只看字段名、不看值**

报错 MUST 在**仅凭字段名**时触发（`PD-01: unknown field rationale — a field the checker does not
know can carry §NNN unchecked`）。若写成「未知字段**且**其值含 `§NNN`」才报，一个含引用的字段会在
将来某次被扫到时**无声通过**。**判据的输入 MUST 等于被断言的对象**——这里断言的是「字段集封闭」，
不是「这条引用坏不坏」。⇒ 注入 MUST 含一次**值干净**的未知字段（`rationale: "见 §40.4"`），
**它同样必须失败**。

### 决策 3：`question` 纳入引用扫描（`CITATION_FIELDS`）

- 实测**当前 0 条** `question` 含 `§` ⇒ 纳入**不引入红**；
- 方向为**安全侧**：将来某条 `question` 引用了不存在的章节会被抓，而不是放行。
- **为什么不选「结构字段 + 禁含 `§`」**：那条路会**禁止**一个合法引用（假阳性方向）。
  **假阳性与假阴性不对称 ⇒ 永远选安全方向**，且这两条路的失败面不同：纳入扫描后，失败的都**真是缺陷**。

### 决策 4：三类 MUST 两两不相交

`shapeErrors()` 新增：任一字段同时被两类认领（如把 `id` 也塞进 `CITATION_FIELDS`）⇒ 具名失败。
否则「这个字段由谁负责」不再是单一回答——两个检查都以为对方在管它。

### 决策 5：并集断言是**内容断言**，且两侧都要能开火

`shapeErrors()` 断言「三类别之并 **恰等于** `LEDGER_FIELDS`」，两个方向都具名：
①允许出现却无人认领（⇒ 数据侧可以带一个不受检的字段）；
②被分类却不在允许集（⇒ 那份分类永远打不到东西，闭世界断言会先拒掉数据）。

## 后果

- **台账数据一字未改**：实测当前字段集**恰好**等于 `LEDGER_FIELDS`、`question` **0 命中** `§`
  ⇒ 基线**保持全绿**（这正是「本轮不引入红」的判据）。
- 新增 3 类具名失败：未知字段（报条目 + 字段名）、字段被两类认领、并集与 `LEDGER_FIELDS` 不符（两个方向）。
- **不改基线正文、不改任何 Rust、不新增依赖边**（`pending-decisions.mjs` 无 import，
  表级注入用的临时副本因此可独立 import）。
- **这不只是「再加一条断言」**：它把 W80 的纪律从**单层**推到**两层**——清单要**单一来源**（W80），
  而清单**本身是边界**、边界之外 MUST 被显式拒绝（W81）。凡「按清单扫」的守卫，MUST 同时问：
  **这份清单的补集，谁来管？**

## 遗留

1. **仍不判语义**：脚本只证「引用的章节号存在」，**不证该章节回答了该问题**（沿用 ADR 0054 决策 2）。
2. **`note` 的处置归属不校验**：一条 `note` 可挂在任何处置上（实测如此，5 条里 4 条是注解），
   本轮不要求它与处置相称（沿用 ADR 0058 遗留 2）。
3. **闭世界只对「条目内部」成立**：`entries` 之外的顶层键（`schema_version`／`baseline`／`entries`）
   由各自的具名检查判定，**不**进 `LEDGER_FIELDS`。新增顶层键同样 MUST 被显式处理。
   > **追加（W82 / ADR 0060）**：本条登记的形状**已被一轮闭合**——「顶层键各有具名检查」实际是
   > 「**已知键各有人管 ≠ 键集封闭**」：实测顶层加 `revision: "见 §99.9"`（以及值干净的
   > `"见 §40.4"`、以及把条目字段名 `question` 写到顶层）三例**全部返回空错误**。
   > 处置：`TOP_LEVEL_FIELDS` 逐字写死 + 信封闭世界断言 + 信封字段必需 + 两层级字段名集不相交。
   > **原文保留**（历史记录按 §56.2 不就地改动）；本条的边界由此转入 ADR 0060 遗留 3。
4. **`question` 从此必须「引用可解析」**：若将来出现合法的 `§` 指代（如指代非当前基线的版本章节），
   必须落在一个真实章节号上，或改由别的字段承载。
5. **`CAPABILITY_PACK_IDS` 仍手写**（沿用 ADR 0056 遗留 4）。
6. **§56.2 归档边界仍未写死**（W78 §八第 8 / W79 §八第 6 / W80 §八第 4 未变）。
7. `cargo xtask schema --check` 本机仍跑不了（宿主对 node 派生任何子进程 `EBUSY`）；本轮未改任何
   schema 与生成器输入 ⇒ 零漂移由结构性理由 + CI 独立步骤兜底，**未写成「已通过」**。
