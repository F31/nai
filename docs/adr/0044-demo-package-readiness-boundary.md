# ADR 0044：演示包就绪判定的边界——未声明即条件化、「授权的」是要求、连通不等于达标

- 日期：2026-10-11
- 状态：Accepted
- 基线：V3.7 §15（易用性与运营：§612 可用性目标、§615 演示包）、§16（O01 验收）、§30.1（测试分层）、§1261（未运行的验收记 Blocked）
- 变更：`openspec/changes/w49-demo-package-and-cost-display/`
- 判据：`tests/registry.yaml` O01「可用性：约 10 分钟首句演练语音；约 30 分钟完成真实输出验证」

## 背景

O01 的**真值**（一次真实的约 10 分钟首句演练与约 30 分钟真实输出验证）需要人工与真实端点，本轮不可达，
O01 保持 `pending`。但 §615 对「演示包」有**可判的构成要求**，此前全库没有任何落点——
`preset`/`演示包` 两个词在 `crates/`、`apps/`、`schemas/` 里一次都没有出现过：

1. 「演示包未建」该怎么表达——缺陷，还是一种诚实状态？
2. §615 的「**授权的**演示形象」——形容词，还是一条可判要求？
3. 「一键连通测试」怎么落成一条可判规则？冒烟与验收是什么关系？
4. §612 的两条时间目标（10 分钟 / 30 分钟）怎么判？没演练过算什么？
5. 判定放进哪一层？会不会把纯判定绑到某个宿主？

## 决策

### D1 放进 `crates/nai-kernel`（`demo.rs`）

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 放进 `nai-engine`／`nai-runtime`（与装配同住） | 贴近运行时 | **否决**：会拉入宿主与监督，portable 下无法单独测；判定是策略，不是运行时状态。 |
| B. 放进 `nai-upgrade-core`（与 `CostEstimate` 同住） | 贴近成本口径 | **否决**：升级器不认识「演示包」；且会把 §615 的构成绑到一个 shared 层的升级 crate 上。 |
| C. 放进 `crates/nai-kernel` | 与 `monitoring.rs`／`device.rs` 同 crate | **采纳**：复用 `golden::Finding`（同一报告词汇），依赖方向不变，portable 全覆盖。 |

### D2 未声明 ⇒ 条件化：未建演示包审计为空、`Blocked`

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 未建即缺陷 | `Defective` | **否决**：与 O03/O04 的既有纪律冲突——「未声明某职责时不得按缺陷计」。尚未交付的东西不是**违规**，是**未开始**。 |
| B. 未建即 Ready | 乐观 | **否决**：会把「未开始」读成「已就绪」。 |
| C. 空描述符审计为空，readiness = `Blocked` | 条件化 | **采纳**：与 `DeviceHost::empty()` 同形。 |

一旦**声明了**演示包（任一部分存在），§615 的其余部分即成为**欠项**，缺项逐条具名
（`demo_avatar_missing` / `demo_knowledge_missing` / …）。半份演示包是**缺陷**，不是「未开始」。

### D3 「授权的」是要求，不是形容词

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 只判「有没有形象」 | 一个存在性检查 | **否决**：§615 的字面是「**授权的**演示形象」；一个没有授权引用的形象正是这条要求要拦的东西。 |
| B. 有形象但无授权引用 ⇒ 缺陷 | 独立标记 `demo_avatar_without_license` | **采纳**：「有形象」与「有**授权的**形象」是两件事，各自可判。 |

### D4 连通 ≠ 达标：真实探针与冒烟结果分开判

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 只判「有没有连通测试」 | 存在性 | **否决**：常量桩也能满足存在性，但它什么都没测。 |
| B. 探针种类与结果声明分成两条规则 | `connectivity_probe_is_stub` + `smoke_claims_acceptance` | **采纳**：前者判「测没测」，后者判「有没有把冒烟当验收」——与 W36/W37 已固化的纪律一致。 |

### D5 成本预估：未知 MUST 说明原因

§615 的演示包含「成本预估」。判据沿用 `upgrade-transaction` 已固化的口径（未知 ≠ 0）：

- 缺整份预估 ⇒ `demo_cost_estimate_missing`；
- 某分项声明为未知却未给出原因 ⇒ `cost_unknown_without_reason`。

### D6 §612 的两条时间目标是**演练记录**的判定

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 无记录即缺陷 | `Defective` | **否决**：尚未演练是 §1261 明说的「未运行」状态，应记 `Blocked`。 |
| B. 无记录即 Ready | 乐观 | **否决**：会把设计值当实测值。 |
| C. 记录缺项/时间线不自洽/超目标 ⇒ 缺陷；无记录 ⇒ `Blocked` | 条件化 | **采纳**：记录是**一份声明**，声明的自洽性与目标达成度可判。 |

时间目标取 §612 的字面值（10 分钟、30 分钟）为设计值；判据是「记录的耗时 ≤ 目标」，**不**由本模块测量。

### D7 三态且 `Defective` 优先

`DemoReadiness = Blocked | Defective | Ready`，先取审计、再看是否演练完成。
`Defective` 优先——一份违反边界的声明不得因子项未演练而被读成 `Blocked`。

### D8 审计是描述符的纯函数

与 W30/W32/W33/W34 一致：对描述符自身字段做纯函数，报出**全部**命中项，每条标记可构造；
干净描述符审计为空；并以「构造描述的审计并集**恰为**这些标记」断言，防止未登记标记混入。
本模块**不**触碰真实端点、不联网、不读文件。

### D9 不新增 xtask 命令与证据目录

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 新增 `check --demo --dir tests/demo` | 仿形式 | **否决**：§30.1 为 UI / RAG / 升级 / 媒体 / 故障 / 契约 / 集成 / 性能各指定了目录；演示包与可用性目标的真值来自**真实演练与真实端点**，不是仓库载荷。臆造目录属过度绑定。 |
| B. 只落判定骨架，载体由未来的真实交付提供 | 无新目录 | **采纳**。 |

## 否决方案

| 方案 | 否决理由 |
| --- | --- |
| 未建演示包即缺陷 | 尚未交付不是违规；与 O03/O04「未声明即条件化」冲突 |
| 未建演示包即 Ready | 把「未开始」读成「已就绪」 |
| 只判形象存在性 | §615 要的是**授权的**形象 |
| 只判连通测试存在性 | 常量桩也满足存在性，但什么都没测 |
| 把冒烟结果当验收达标 | 与本仓库 W36/W37 固化的纪律冲突 |
| 无演练记录即缺陷 | §1261：未运行的验收记 Blocked |
| 由本模块测量演练耗时 | 会使便携层依赖时钟与真实端点 |
| 落进 `nai-engine`／`nai-runtime` | 拉入宿主与监督，portable 不可测 |
| 落进 `nai-upgrade-core` | 升级器不认识演示包，且绑到 shared 层 upgrade crate |
| 臆造 `tests/demo` 证据目录 | §30.1 未指定；真值来自真实演练而非仓库载荷 |

## 后果

- §615 的**构成要求**与 §612 的**时间目标**有了单一落点：给定一份声明的演示包与演练记录，
  如何判齐备、如何判诚实、未演练如何表达，都可执行、可测试（`crates/nai-kernel/tests/demo.rs`）。
- registry 的 **O01 保持 `pending`**——判定机制已交付，但**授权的演示形象内容、示例知识/场景正文、
  真实人工演练**是外部真值；其 notes 追加本轮成果与剩余项。
- 遗留：真实演示包内容、一键连通测试的真实接线（本模块只判描述符，不做连通）、
  约 10 分钟首句演练与约 30 分钟真实输出验证的人工执行。
