# ADR 0119：`blockedBy` 的取值由路由器自己作证 —— 声明面收口之后，执行面怎么接上

- 状态：已接受（W145，2026-10-18）
- 基线：`docs/直播数字人 + 智能体系统技术方案 V3.11.md`（§30.1 第 4 条 / §662 O02）
- 相关：ADR 0118（作业面闭世界）、W144 报告（§五第 1 条 / §八第 2 条）、
  `tests/job-surface.json`、`scripts/contracts/job-surface.mjs`、
  `crates/nai-control-api/src/tests.rs`

## 背景

W144 把 15 条「声明了 `202 + JobAccepted` 却不铸 `job_id`」的作业面收成了闭世界：每条在册，
在册项 MUST 恰有 `kind`（真能被 `/jobs/{id}` 轮询）或具名 `blockedBy`（今天不铸 id 的理由）。
那一轮把自己的边界写进了报告 §五第 1 条：

> **`blockedBy` 的取值本身仍是声明。** 锚点只证明「那句源码还在」，不证明「这条路由真的没有分支」。

本轮把那条边界量清楚了：

| 事实 | 实测 |
| --- | --- |
| 在册项 | 15（13 × `no_handler`、2 × `refuses_without_installer`） |
| 路径字面量出现在 `crates/nai-control-api/src/tests.rs` 的在册项 | **1**（`/api/v1/upgrades/execute`，且那条用例的意图是「拒绝」，不是「分类」） |
| 路由器实际分支 | 10 个权限条件 / 13 条路由形状 |
| 「分类」与「行为」之间的连接 | 仅 `JOB_BLOCKERS[*].anchor` 的**文本**锚点 |

也就是说：13 条 `no_handler` 从来没有被任何执行面判据碰过，而这 13 条恰恰是「这条路由不存在」
这一断言的全体。锚点不会因为「路由被接上了分支」而变红——它守的是另一件事。

## 决定

### 决定 1：分类由**行为**作证，不由源码解析作证

判据是：把每条的 `(method, path)` 打进**真实的路由器**，看响应。

被否决的是「解析 `handle()` 的 if/else 链，把路径字面量抽成一个集合」。理由不是「难写」，而是：

1. **它仍然是推断**。`path == "..."` 只是一段条件文本；它是否被执行、执行后到哪一步，
   正是「有没有分支」这个问题本身。用条件文本回答条件问题，等于把同一个不确定性读了第二遍。
2. **链子有两处**。权限链（`:508–:539`）决定 `(method, path)` 有没有被认领，派发链（`:621–:653`）
   决定认领后做什么；两处都靠 `starts_with` / `ends_with` 拼路径。文本解析要把两处拼起来，
   而拼接规则本身是新的、没人验证过的判定。
3. **失败信号的质量不同**。行为探针红的时候直接给出「期望 404，得到 503」以及响应体；
   文本解析红的时候给出的是「集合不等」——排查者还得回去确认是哪一侧错了。

一条真实的 `(method, path)` 请求就是「接线真的发生了」的证据，符合本项目「已接线 MUST 由调用
证明」的一贯纪律。

### 决定 2：登记表挪成两侧共读的单一枢纽 `tests/job-surface.json`

执行侧要判「分类 ⇔ 行为」，就必须知道分类；而分类是**契约侧**的声明。三种放法里选第三种：

| 放法 | 问题 |
| --- | --- |
| Rust 侧另写一份 15 条 | 同一件事的第二处定义 ⇒ 迟到必漂移 |
| Rust 侧解析 JS 字面量 | 解析规则与格式强耦合；格式一改就静默少数，而「少数」在两侧都不红 |
| 两侧读同一份 JSON | 一份数据、两个结构化读取器（`JSON.parse` / `serde_json`），格式变化会**报错**而不是少数 |

`JOB_REGISTRY` 因此不只记路径，还记**执行侧逐字嵌入的那一句**
（`include_str!("../../../tests/job-surface.json")`）。只判「有个 `include_str!`」是不够的——
指向别的文件同样满足「读了个文件」，而两侧各自全绿、判的却是两份数据，是比任何一处锚点断裂都
安静的一种坏法。

配套：`jobSurfaceErrors(documents, surfaces)` 的 `surfaces` **去掉默认值**。有默认值时，
「没给登记表」会静默变成「用仓库里那份」；去掉之后它落到既有的缺参分支上，与「空登记表」分开报。

### 决定 3：判据没有行为期望的类别 MUST 硬失败

`match` 的兜底分支不写「其余跳过」，而写具名 panic：

> `{key}: JOB_BLOCKERS names {other}, and this probe has no behavioural expectation for it —
> a new class MUST arrive with the response shape it promises, otherwise the classification is
> only declared, never judged`

这条今天**打在 `kind` 上**（`kind` 意味着「真能被轮询」，正面样本数 = 0）。本可以写一条
「`kind` ⇒ 不得答 404」的宽松期望让分支看起来完整，但那是一条**没有样本的期望**：它永远绿，
永远不证明任何事。硬失败把「第一次真正接上作业状态」变成一笔必须付的账——那天作者要同时写出
202 与可轮询 id 的期望，否则红。

### 决定 4：只钉「这是哪一类拒绝」，不钉文案

- 兜底 404 的措辞（`control operation not implemented`）由 JS 侧锚点守；
- `refuses_without_installer` 的措辞（`UpgradeHost` / `no job id is minted`）由
  `execute_and_rollback_refuse_by_name_and_mint_no_job_id` 守。

执行侧探针只钉状态码、错误码、`category`、以及「没有 `job_id`」。同一句话不在第三处定义。

## 被否决的方案

1. **给 15 条各写一条独立用例**：15 个硬编码路径就是第二份清单，与登记表并存必然漂移；
   且新增第 16 条 202 操作时，没人会记得补第 16 条用例。
2. **只判「在册项都不得答 202」**：这条对今天的 15 条恒真，却分不清 404 与 503——
   而「有分支但拒绝」与「根本没有分支」正是两个 `blockedBy` 值的全部区别。
3. **在 Rust 侧造一条合成路由来验证 `kind` 分支**：等于本轮顺手引入一个真实作业（迁移 + journal），
   超出「关掉一条残余」的范围，且会让 `JobAccepted` 从「零生产者」变成「一个生产者」——
   那是一件需要单独设计的事。
4. **把登记表写进 Rust 常量、让 JS 去解析 Rust**：方向反了。分类是契约侧的声明，
   契约侧判据（`jobSurfaceErrors`）要以它为输入；让契约侧去解析执行侧源码，会把
   「谁声明、谁作证」的关系倒过来。

## 具名残余

1. **`kind` 那一半仍无真实样本**。执行侧对 `kind` 是**硬失败**，不是通过；第一次接上真实作业
   时它才会第一次生效。这一点与 W144 §五第 3 条一致，没有被本轮改变。
2. **探针证明的是「今天的路由器这样处理」**。将来注入平台安装器后，`upgrades/execute` 若开始
   铸 id，探针会先红（期望 503 得到 202/200）——那时该条目应从 `refuses_without_installer`
   改成 `kind`，这是设计意图，不是缺陷。
3. **`no_handler` 的兜底措辞仍由文本锚点单独守**。执行侧只钉 `CAPABILITY_ABSENT`；
   措辞改名不会让 Rust 侧红（JS 侧会）。这是「同一件事不在第三处定义」的代价，已知且具名。
4. **符号迁移的账**：`JOB_SURFACES` 这个名字在 W144 的 ADR / 报告 / 归档变更里继续存在
   （历史记录不就地改）；活规格已 1:1 订正，代码里不再有该符号。
