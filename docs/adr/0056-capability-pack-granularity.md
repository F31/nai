# ADR 0056：能力包的打包粒度——清单式散文需要一个划分断言

- 状态：已接受
- 日期：2026-10-12
- 依据：ADR 0050（基线 ↔ 在册对账）、ADR 0051（重叠允许、漂移不行）、
  W66（「完整性守卫」要问：钉住的是条数还是内容）、W72（对账门控的落点）、
  W76（§51.3 已答「打包粒度」这一问）、W77（本轮的前身）
- 影响：`scripts/contracts/baseline.mjs`、`scripts/contracts/registry.mjs`、
  `tests/registry.test.mjs`；**不改基线正文、不改 `tests/registry.yaml`、不改任何 Rust**

## 背景

W76 把「能力包的打包粒度」登记为一条**已答**的事实，并在规格里写下：

> 某条待裁定项在基线正文里已有答案（如打包粒度已由 §51.3 的能力包清单回答）

这句话是对的，但它只是**一句真话**，不是**一条判据**。核实后的图景是：

| 现有断言 | 它读什么 | 它读不到什么 |
| --- | --- | --- |
| `registry.mjs` 的 `CAPABILITY_PACK_IDS` ↔ registry 的 `capability_pack` 行 | **手抄的常量** 与 YAML | 常量是否仍然如实抄自 §51.3 |
| `baseline.mjs::reconcile` 的 §57.3「能力包」行 ↔ registry | §57.3 与 YAML | §51.3 的**表内结构** |
| 同上，§48.5 家族索引 ↔ registry | §48.5 与 YAML | 同上 |

⇒ **§51.3 的表格从未被任何断言读过。** 两个后果：

1. 把 `M13–M18` 从「市场客户端」挪走、或把 `H16` 并进别的包，只要 §57.3 的能力包行不动、
   常量不动，**全部现有断言照绿**。这正是 W66 的教训第二次适用：
   **「完整性守卫」要问：钉住的是条数，还是内容？**
2. §51.3 的八行说的**不是**「这些编号属于能力包线」（那是 §57.3 的活），
   而是**每一个编号属于哪一个包**——那是一个**划分**。而现有断言全在**集合**层，
   集合层对划分是瞎的。

## 决策

### 决策 1：判据的来源是 §51.3 的表格原文，而不是那个常量

`CAPABILITY_PACK_IDS` 是**手抄的镜像**：它写得对，但它**无法证明自己仍然对**。
判据必须读正文。故新增 `parseCapabilityPacks(text)`（复用既有的 `sectionTable` 与 `expandIds`
——后者本就覆盖 M 与 H 家族），并把该常量**接到解析结果上**（决策 5）。
常量因此从「独立的第二处事实」变成「被正文钉住的一处镜像」。

### 决策 2：划分与并集是**两条**判据，不能互相代替

设 `R` = §51.3 的八行，`U = ⋃ Rᵢ`：

- `U` 正确 **不蕴含** `R` 是划分。反例：`R = {M01–M12, M05–M08}` ⇒ `U = M01–M12` 不变，
  而 `M05–M08` 同属两包，打包粒度已破。
- `R` 是划分 **也不蕴含** `U` 与在册一致。

两者的错误形态不同（「同一编号两个包」vs「集合两侧不符」），故**必须并列具名**，
不能用一个总账数字代替——**总数对「被改类别」是瞎的**，这是第三次适用。

### 决策 3：分界判据由「两侧都非空 + 互斥」构成，**不写死任何集合**

§51.3 表后那段「保留在 R1 的基础纪律」列出 `H01–H04、H15、H17、H18`，与能力包清单**互补**于
harness 家族的「已设计」部分。这就是 §51.3 自己写下的分界判据：

> *「一个确定性的上下文装配函数能不能满足它？」* 能 ⇒ 留在 R1；否则 ⇒ 能力包。

可判定形式是**两侧都非空且互斥**。这里**刻意不写死** `{H01,H02,H03,H04,H15,H17,H18}`：
两侧的数据都直接来自正文，断言因此**不需要一份手抄**——这比 ADR 0055 决策 5 那种
「照抄某张表」的情形更干净，因为没有中间副本可漂移。

**「非空」那半条是必须的**：解析恒为空会让「互不相交」**恒真**，
而一条因为什么都没解析出来而通过的断言，比没有断言更坏（ADR 0051 的同一精神）。

### 决策 4：表形状 MUST 逐项写死，而不是只数行数

`CAPABILITY_PACK_ROWS` 把八行的**标签与编号**都写下来。理由是 W66 的原话：
把 `M01–M12` 改成 `M01–M02` 而行的数量不变时，**只数行的断言照样通过**。
写死的常量在这里是**断言**（与正文比对），不是**镜像**（供别处读取）——
这个区分正是本轮全部工作的要点。

### 决策 5：三向一致——常量从此接在正文上

`§51.3 的并集` == `registry 的 capability_pack 行` == `CAPABILITY_PACK_IDS`，
三处重叠**是允许的**（ADR 0051 决策 1），**漂移不是**；任一侧不符 MUST 具名给出
**差异编号与差异所在的那一侧**。

### 决策 6：「依据非空」逐行判、与行数无关

依据列是「这个包为什么可以后置」的那句话。它按**行**判定，因此**不许**被塞进
「行数相符」的分支里——短路会让「未被检查」看起来像「已通过」（W77 门控排查的同一教训：
**果与因要分开**）。

### 决策 7：不把包归属搬进 `tests/registry.yaml`

registry 记的是**发布线**；「属于哪一个能力包」只存在于 §51.3 这一处。
把后者也写进 registry 会产生**第二个写下来的地方**——正是本轮要消除的东西。

## 后果

- §51.3 的表**从散文变成可判定**：改小一行、改标签、把编号放进两个包、
  把 `H18` 从保留段挪进包行、常量漏项、在册漏项、依据置空、章节号被改 —— 各自具名失败。
- **零行为变化**：本轮**不改基线正文、不改 registry、不改任何 Rust**；只新增解析与断言。
- 判据并入 `reconcile` 的第 ④ 区块 ⇒ 既有的 `against()` 助手与**全部既有用例自动带上它**，
  `engineering_checks`（它逐个显式列举 Node 测试文件）**零接线改动**。
- `CAPABILITY_PACK_IDS` 由 `registry.mjs` 导出，`baseline.mjs` 多 import 一项 ⇒
  **不新增依赖边**（`registry.mjs` 不 import `baseline.mjs`，无环）。

## 遗留

1. **判据边界如实登记**：只读 §51.3 与 §57.3、§48.5。若将来有人把包归属搬到别处
   （例如新起一节「能力包索引」），本轮的断言**抓不到**那处的新事实——**这是边界，不是缺陷**。
2. **§51.2 刻意未读**：§51.2 是散文、没有表格，而 `sectionTable` 取的是「标题之后第一张表」
   ⇒ 对 §51.2 调用它会**静默取到 §51.3 的表**。分界判据的 R1 那一侧因此取自 §51.3 自己的尾段。
   这条限制写在这里，而不是靠记性绕开。
3. **不改 `registry.mjs` 的既有三条断言**（成员漏项 / 归属外编号 / 首版线泄漏），
   它们在 W65 立、W68 扩，各自具名失败，继续有效。
4. `CAPABILITY_PACK_IDS` 仍是**手写**的数组（未改为从正文生成）。理由是生成方向反了会引入
   依赖环，且「断言 ≠ 生成」——本轮的判据正是拿它与正文比对。若将来要真正生成，
   **MUST** 先解决 `registry.mjs` ↔ `baseline.mjs` 的依赖方向。
