# ADR 0037：平台生命周期的边界——职责封闭、转换清授权、陈旧房间抑制与能力最严格交集

- 日期：2026-10-10
- 状态：Accepted
- 基线：V3.7 §3.3（进程拓扑：platform-bridge）、§9.2（桥接与能力快照）、§27.1（SDK 桥接）、§347（伴侣生命周期与七类需处理）、§349（能力快照最严格交集）、§119（平台事件中断三态）、§1075（SDK 加载与握手）、§1261（交付与 CI）、§30.1（测试分层）、§1328（P01 验收）
- 变更：`openspec/changes/w35-platform-lifecycle/`
- 判据：`tests/registry.yaml` P01「平台生命周期：伴侣启动、退出、重连、切场次不产生旧房间播报；权限撤销停止相关功能」

## 背景

P01 的**真值**（官方 SDK 认证、生产 composition root 平台宿主接线、真实启动/退出/端口冲突/网关）需要外部条件，本轮不可达，P01 保持 `blocked`。

D13 已交付 `nai-kernel::platform::PlatformLink`，但那判的是**事件准入**——一个事件能不能进。§27.1/§347/§349/§119 对**桥接进程的生命周期**另给了一组很密的判据，此前**全库没有落点**（`grep bridge` 在 `crates/nai-kernel/src/` 内为空）：

1. 落进哪个 crate，与既有 `platform.rs`/`session.rs` 怎么划界？
2. 「桥接只做四项」怎么表达，越界怎么报？
3. 四类生命周期转换的「明确处置」怎么表达，「清授权」怎么判？
4. 「不产生旧房间播报」判到哪一层？
5. 「引擎转待机」与「重连不恢复旧自动权限」怎么判？
6. 能力快照三态怎么取最严格，「只关闭对应功能」怎么判到**两个方向**？
7. 平台中断的三态（撤自动/保手工/保回放）怎么判，非平台中断怎么办？
8. 七类情形怎么表达与检查？
9. SDK 信任检查与「无 SDK 时不冒充」怎么共存？
10. 未接入官方 SDK 时 readiness 是什么？
11. 审计会不会被判定函数架空？

## 决策

### D1 落 `crates/nai-kernel`（`bridge.rs`），与 `platform.rs`/`session.rs` 划界

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 并进既有 `platform.rs` | 与 `PlatformLink` 同文件 | **否决**：`PlatformLink` 判**事件准入**，本模块判**进程生命周期与播报抑制**；混在一起会让两面互相污染，且 `platform.rs` 已有自己的 `Connection`/`fail` 词汇。 |
| B. 并进既有 `session.rs` | 与会话状态机同文件 | **否决**：`session.rs` 的 `SessionLifecycle`/`SessionMode`/duty lease 是**会话**面，P01 是**伴侣桥接**面；实体与不变量都不同。 |
| C. 放进 `nai-plugin-hosts`（桥接是宿主） | 贴近宿主 | **否决**：plugin-hosts 判 IPC/ACL/边界，且会把 kernel 的报告词汇拖进宿主层。 |
| D. 新增 `crates/nai-kernel/src/bridge.rs` | 与 `golden.rs`/`realistic.rs`/`monitoring.rs`/`device.rs` 同 crate | **采纳**：复用 `golden::Finding`（同一报告词汇），依赖方向不变（kernel 只依赖 contracts）。 |

> §119「platform-bridge（C++）」说的是**运行时的进程与语言**；kernel 放的是**判定策略**。二者不矛盾：本模块不启动伴侣、不加载 SDK、不建连接。

### D2 桥接职责是**封闭四项**，越界逐条指名

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 只记「职责清单」不判越界 | 一个列表 | **否决**：§27.1 的「只做」是一条**否定式**，不判越界等于没落。 |
| B. 只报「有越界」不指名 | 一个布尔 | **否决**：不知道越在哪，修法不同。 |
| C. `duties` 四项之内 + `extra_duties` 逐条指名报出 | 封闭集 + 逐条 | **采纳**：`duty_outside_bridge_scope`。 |

### D3 四类转换各处置、各清授权、各记录，但以「声明了桥接」为前提

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 无条件要求四类转换齐备 | 一刀切 | **否决**：尚未实现官方 SDK 的桥接不欠四条转换处置；读成四个缺陷是「不适用⇒不合规」（同 W33 预览未启用、W34 纯 `Sense` 不要求联锁）。 |
| B. 都不要求 | 宽松 | **否决**：§1328 明列四类。 |
| C. 以「声明了桥接职责」为门控，门控内四类齐备 | 条件化 | **采纳**。 |

### D4 「不产生旧房间播报」判**两个面**

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 只判「每类转换都清授权」 | 处置面 | **否决**：清授权之后仍可能**存在**一份与当前连接不符的授权（恢复路径漏挂）。 |
| B. 只判描述符级授权是否一致 | 状态面 | **否决**：会漏掉「某类转换根本没清授权」。 |
| C. 处置面 `transition_keeps_stale_broadcast` + 状态面 `stale_room_broadcast_permitted` | 双角度 | **采纳**：与 W34 的「处置面 + 结果面」同形。`covers` 同时比对**房间**与**连接代次**。 |

**状态面不受门控**：尚未实现的桥接若仍挂着已离开房间的播报授权，那是实打实的缺陷，不能被「还没做」冲淡。这是 `Defective` 优先于 `Blocked` 的第一根支点。

### D5 退出转待机、重连不恢复旧自动权限——都落在转换处置的声明上

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 描述符级另设「当前引擎状态」+「最近一次转换」 | 判实际状态 | **否决**：会把「运行中的桥接也带着退出处置声明」误读成「已退出却仍在运行」；要修得再引入一个「最近转换」字段，得不偿失。 |
| B. 只判「退出处置存在」 | 过松 | **否决**：判不出「退出时转没转待机」。 |
| C. 在转换处置里声明 `leaves_engine_in_standby` 与 `restores_previous_auto_authority` | 局部声明 | **采纳**：与 `clears_broadcast_authority` 同构，两点都可直接构造。 |

### D6 能力快照 `unknown` 取最严格；功能开关判**两个方向**

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 只判「功能不该开着却开着」 | 单向 | **否决**：§349「**只**关闭对应功能」的另一半是**不得**越界关闭；只判单向等于允许「撤销 A 权限顺手停了 B 功能」。 |
| B. 让 `unknown` 参与「已授予」判定 | 宽松 | **否决**：§349 明说取**最严格交集**——「不知道」不能被读成「可以」。 |
| C. `unknown` 视为未授予；`unknown` 读作已授予 ⇒ 报出；欠关闭 ⇒ 报出；**因能力变更**的过关闭 ⇒ 报出 | 三态 + 双向 | **采纳**。第三条带前置条件 `stopped_by_capability_change`，避免误报用户主动关闭的功能。 |

### D7 平台中断三态，条件化于「确为平台中断」

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 所有降级都要求撤自动 | 一刀切 | **否决**：Provider 不可用等降级不欠此规则，会与 §21 冲突。 |
| B. 只判「降级都记了日志」 | 过松 | **否决**：§119 的三段式（撤自动/保手工/保回放）是硬要求。 |
| C. `bridge_lost` 为真时判三条状态 + 记录；否则不判 | 条件化 | **采纳**。 |

### D8 七类情形取 §347 **原文七类**

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 自拟一份「常见故障」清单 | 便利 | **否决**：规格说的是哪几类，代码判的就该是哪几类；自拟会悄悄漏掉一类。 |
| B. 只判「有处置」不逐类 | 过松 | **否决**：缺哪类不可知。 |
| C. `MultipleStarts`/`PortConflict`/`SdkLost`/`DuplicateMessages`/`StaleRoomEvent`/`TimeDrift`/`PermissionRevoked` 逐类判处置与记录 | 原文七类 | **采纳**：门控同 D3。 |

### D9 SDK 信任检查条件化于「声明 SDK 已核验」

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 无条件要求全部握手校验 | 一刀切 | **否决**：与 D10 冲突——如实声明**没有**官方 SDK 时，不该同时被要求校验签名。 |
| B. 都不要求 | 宽松 | **否决**：§27.1「官方 SDK 库不能从任意路径加载」是硬要求。 |
| C. `Verified` 时逐项检查；`UnverifiedExternalDependency` 时不判 | 条件化 | **采纳**：`sdk_loaded_without_trust_check` 逐项指名。 |

### D10 `UNVERIFIED_EXTERNAL_DEPENDENCY` 是诚实状态，冒充才是缺陷

§27.1 末句是一条明确的否定式：「**不用 fake connector 冒充真实能力**」。落成 `uses_fake_connector_claimed_real`；该状态下冒充 ⇒ `fake_connector_claimed_as_real_capability`，**如实记录则不报**。这与 W32「不以 CUDA EP 注册宣称全 GPU」、W33「如实披露中继可读而不宣称端到端加密」同形：**判的是「宣称」，不是「能力」**。

### D11 回调不同步等待 LLM 或磁盘

§27.1「SDK 回调快速入队，不同步等待 LLM 或磁盘大事务」是一条可判字段（`awaits_llm_or_disk`），门控同 D3。

### D12 readiness 三态，`Defective` **优先**于 `Blocked`

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 无声明即缺陷 | 一律 Defective | **否决**：P01 尚未实现官方 SDK 是**计划内**的诚实状态（§1261「无法执行就标 Blocked，不写成 CI Passed」）。 |
| B. 无声明即 Ready | 乐观 | **否决**：把「尚未接入」读成「已就绪」。 |
| C. 先取审计（非空即 `Defective`），再按是否声明了桥接职责 | 审计优先 | **采纳**。支点是三条**不受门控的独立判据**：陈旧房间授权（状态面）、伪造替代、功能开关双向。 |

### D13 审计是描述符的纯函数

与 W30/W32/W33/W34 一致：**十九条**标记逐条可在测试里直接构造；干净描述符审计为空；构造描述的审计并集**恰为**这十九条（既证每条可构造，也防未登记标记）。

### D14 不新增 xtask 命令与证据目录

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 新增 `check --lifecycle --dir tests/lifecycle` | 仿 W31 的形式 | **否决**：§30.1 为升级指定 `tests/upgrade`、为 RAG 指定 `tests/rag-golden`、为 UI 指定 `tests/ui`；平台生命周期**没有**证据目录约定，其真值来自官方 SDK 与真实账号。臆造目录属过度绑定。 |
| B. 不加载体，只落判定骨架 | 由未来的真实平台轨提供 | **采纳**：待真实平台轨立项后再补载体，**无需改本模块判定**。 |

## 否决方案

| 方案 | 否决理由 |
| --- | --- |
| 并进 `platform.rs` | 事件准入与进程生命周期是两面，混住会互相污染 |
| 并进 `session.rs` | 会话状态机与伴侣桥接是不同的实体与不变量 |
| 落进 `nai-plugin-hosts` | 会把 kernel 报告词汇拖进宿主层 |
| 只记职责清单、不判越界 | §27.1「只做」是否定式，不判等于没落 |
| 越界只报不指名 | 不知道越在哪，修法不同 |
| 无条件要求四类转换齐备 | 未接入官方 SDK 的桥接被读成四个缺陷（不适用⇒不合规） |
| 只判「每类转换都清授权」 | 漏掉「清授权后仍挂着不一致授权」的状态面 |
| 只判描述符级授权一致 | 漏掉「某类转换根本没清授权」的处置面 |
| 另设描述符级「引擎状态」+「最近转换」 | 会把运行中的桥接误读成「已退出却仍在运行」 |
| 只判「退出处置存在」 | 判不出「退出时转没转待机」 |
| `unknown` 参与「已授予」判定 | §349 要求取最严格交集 |
| 只判单向功能开关 | 「**只**关闭对应功能」的另一半是不得越界关闭 |
| 过关闭不加 `stopped_by_capability_change` 前置 | 会误报用户主动关闭的功能 |
| 所有降级都要求撤自动 | Provider 等降级不欠此规则，与 §21 冲突 |
| 自拟「常见故障」清单 | 应取 §347 原文七类，避免悄悄漏类 |
| 无条件要求全部握手校验 | 与「无 SDK 时如实记录」冲突 |
| 无官方 SDK 时也判信任检查 | 要求校验一个并不存在的签名是惩罚诚实答案 |
| 无声明即缺陷 / 即就绪 | §1261；且「尚未接入」不应被读成「已就绪」 |
| 只靠判定函数、不做审计 | 描述符字段公开，可被拼装绕过判定路径 |
| 臆造 `tests/lifecycle` 证据目录 | §30.1 未指定；真值来自官方 SDK 与真实账号而非仓库载荷 |

## 后果

- §27.1/§347/§349/§119/§1328 的**平台生命周期口径**有了单一落点：给定一份声明的桥接生命周期，如何判职责越界、转换处置与清授权、陈旧房间播报、退出转待机、重连不恢复旧自动权限、能力快照最严格交集、功能开关双向、平台中断三态、七类情形处置、SDK 信任与不冒充，都可执行、可测试（`tests/bridge.rs` 44 项）。
- 「桥接只做四项」成为一条可判**封闭集**；「不产生旧房间播报」成为一条绑定**房间与连接代次**的可判状态；「缺失能力只关闭对应功能」成为一条**双向**可判事实；`UNVERIFIED_EXTERNAL_DEPENDENCY` 从一条从未使用的错误码变成一处可判的**诚实路径**。
- registry 的 **P01 保持 `blocked`**——判定机制已交付，但官方 SDK、生产宿主接线与真实生命周期演练是外部真值；其 notes 保留两条验收口径并记明**与 D13 已交付的事件准入**（`nai-kernel::platform`）的边界。
- 遗留：官方 SDK 加载与真实握手、生产 composition root 平台宿主接线、真实启动/退出/端口冲突处置、网关与回调服务、真实账号与房间切换演练，全部待外部投入与后续里程碑。
