# ADR 0031：运营度量的边界——端到端分位不与阶段相加、窗口是下界、缺测不是零

- 日期：2026-10-10
- 状态：Accepted
- 基线：V3.6 §12.5（可靠性指标设计值）、§5.9（评估与运营闭环）、§5.4（守门）、§30.4 B04/R06/B06；承接 ADR 0026（升级核心）、ADR 0029（多会话隔离）、ADR 0030（真人接管）
- 变更：`openspec/changes/w29-operations-review/`
- 判据：`tests/registry.yaml` B04「整链路延迟分位」、R06「长播无资源增长」、B06「场次复盘报告」

## 背景

B04 / R06 / B06 三项的**真值**需要真实设备、真实长时运行与真实场次数据，本轮不假装有。但它们的**判据口径**此前没有落点，
于是「设备里程碑」被当成了「不用做」。口径不落地会有三个具体后果：

1. §12.5 明写「整条路径实测分位数，**不把各阶段 P95 相加**」。不把它写成代码，报告里就会出现「阶段相加」这个
   诱人而错误的数字——阶段分位不在同一次请求上发生，相加系统性**高估**。
2. R06 说「无持续资源增长」却没说**怎么判**。RSS 从 300MB 爬到 310MB 是稳定还是增长？末点一个尖峰算不算？跑 40 分钟
   能否得出 2 小时的结论？没有规则，只能人眼看曲线。
3. B06 依赖的 R07（决策日志哈希链）**已 implemented**，数据源就位，缺的是投影规则与「缺测怎么标」。

七项决策必须先回答：落**哪个 crate**；分位**怎么定义**；端到端与阶段**什么关系**；样本不足**给不给数字**；
长播**怎么判**；缺测**怎么表达**；审计**怎么才不成为死代码**。

## 决策

### D1 放进 `crates/nai-kernel`（`metrics.rs` + `review.rs`）

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 放进 `nai-upgrade-core`（shared） | 与升级核心同住 | **否决**：语义无关；且「评估与运营闭环」§5.9 紧跟 §5.8 决策日志，相关内核在 kernel 的 `evaluate/`。 |
| B. 新增 `nai-operations-core` | 独立成包 | **否决**：改动 workspace 组成（18 包）与依赖方向，而本模块只依赖 `ErrorCode` 与 `std`。 |
| C. 放进 `nai-kernel` | 与 `multiplex.rs` 并列，只依赖 contracts | **采用**：18 包不变；`xtask test --suite kernel` 在 portable 下可测。 |

代价：kernel 只能依赖 contracts，故自带 `MetricsError { code, reason }`（`review.rs` 复用），与 `UpgradeError`/`MultiplexError` 同形。

### D2 分位用 nearest-rank，不插值

| 方案 | 结论 |
|---|---|
| 线性插值（曲线更平滑） | **否决**：报告要可复现；插值返回一个报告里不存在的值，复核时对不上任何一条样本。 |
| nearest-rank `ceil(p/100·n)` | **采用**：返回的永远是真实样本，报告与原始数据可逐条对照。 |

### D3 端到端与阶段分离，阶段之和**存在但被标注**

| 方案 | 结论 |
|---|---|
| 只给端到端，不给阶段之和 | **否决**：报告仍想知道时间花在哪，阶段数据被浪费。 |
| 提供「取端到端或阶段之和」的开关 | **否决**：开关迟早被拨到错的一边；§12.5 要的是不混为一谈，不是禁止观察。 |
| 两者都提供 + `stage_sum_gap()` | **采用**：阶段之和只作为具名对照出现，差距被算出来而非被解释掉。 |

### D4 样本门槛，`Err` 而不是低置信标注

| 方案 | 结论 |
|---|---|
| 有多少算多少 | **否决**：10 条样本的「P95」就是最大值，却读作「P95 达标」。 |
| 返回 `Ok` 但标低置信 | **否决**：标注会被忽略，数值不会。 |
| 低于门槛 `Err(CAPABILITY_NOT_READY)` | **采用**：没有数字可误读。 |

### D5 长播判定：双半中位数 + 窗口下界

| 方案 | 结论 |
|---|---|
| 首尾两点 | **否决**：一个末端尖峰判成增长，一个末端低值掩盖增长。 |
| 线性回归斜率 | **否决**：对离群点敏感，且「多少算大」缺自然阈值。 |
| 窗口按名义标签 | **否决**：窗口是**下界**——不足即 `Insufficient` 并如实报出真实跨度。 |
| 双半中位数 + `max_drift_pct` + `min_samples` | **采用**：抗噪、可解释、可测。 |

### D6 报告是投影；缺测进 `unmeasured`，未知成本是独立状态

| 方案 | 结论 |
|---|---|
| 任意计数直接构报告 | **否决**：回答多于入选的报告会一路印到最后。 |
| 比例算成浮点百分数 | **否决**：无法复核分母，也无法表达「分母为零」。 |
| `Ratio{numerator,denominator}` + `Option` + `unmeasured` | **采用**：分母为 0 → `None` 并列入清单；成本缺失 → `CostView::Unknown`。 |

### D7 审计必须可构造

W25 的教训：审计写在对内部状态的访问上时，多数违规**不可达**（已被上游校验挡住），规则成了死代码。

| 方案 | 结论 |
|---|---|
| 只靠 `build` 校验，不做审计 | **否决**：字段公开后仍可被直接构造，没有最后一道防线。 |
| 审计读私有状态 | **否决**：规则不可构造，测试只能「相信它不会触发」。 |
| `SessionReview` 字段公开 + `audit_review` 纯函数 | **采用**：十条规则全部可在测试里直接构造，规则是活的。 |

## 后果

- 「整链路分位」「无持续增长」「报告含 §5.9 字段」三条分别落成：端到端样本 + 阶段对照、窗口下界 + 双半中位数、投影 + 自洽校验 + 缺测清单。
- 代价：`max_drift_pct`、`min_samples`、`MIN_PERCENTILE_SAMPLES` 都是常量或调用方参数，不是从真实数据学来的——真值需要设备。
- kernel 增加两个模块，依赖方向不变（仍只依赖 contracts）。

## 验证

- `cargo test -p nai-kernel --test metrics --test review`。
- `cargo clippy -p nai-kernel --all-targets --locked -- -D warnings`。
- `cargo xtask check-deps`（18 包与依赖方向不变）、`cargo xtask check --registry`、`cargo xtask check --profile portable`。
- `openspec validate w29-operations-review --strict --no-interactive`。

## 未做边界

- 不采真实指标、不跑长播；样本与时间戳由调用方提供。
- 不做报告 UI（属 UI 验收，保持 pending）、不做模型质量评测（B01 独立主线）。
- `automation: manual` 的真机验收（真实设备时延分位、2h/8h/24h 长播、真实场次数据）属设备里程碑，registry 保持 `implemented` 而不标 `tested`。
