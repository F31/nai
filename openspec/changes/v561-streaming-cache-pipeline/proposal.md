# V5.6.1 流式生成与分层缓存优化

## Why

当前新线LLM整段返回、本地Qwen整段WAV、形象模型每轮诊断加载，已有TTS缓存和两槽预取尚未接入新主链。真实768四步短句已实现独立音频时钟驱动160帧窗口提交，但每1.6秒语音的视频生成约2.7秒，预缓冲无法支撑持续实时。必须分别处理首响、持续算力和内容复用，不能以缓存命中或等待音效隐藏未缓存回答的延迟。

## What Changes

- 统一阶段测量及冷/热/缓存分类；接入已有TTS缓存、字节配额与连接复用。
- 按独立安全语句提交LLM增量，接真实增量PCM服务和常驻音频环。
- 固定实际服务能力，优先顺序验证0.6B/1.7B；不自动修改ADR0194默认或用户配置。
- 常驻FlashHead/形象准备、共享GPU资源调度、有界预取与自适应缓冲。
- 建立精确文本、PCM、音频特征、形象准备、合法完整音画片段和编译缓存的不同边界。
- 将缓存/分块与当前任务、许可、事实版本、独立执行范围及音频主时钟结合；生产者认证与常驻输出缺口仍需实现。
- 给出8个可交付纵向包、性能硬门及真实联合验证矩阵。

## Impact

本变更是原`v561-flashhead-single-engine`的同基线性能/可靠性扩展，不替代原执行契约，不采用V4.8 ACC/INV。详细方案见[优化方案](../../../docs/v561-streaming-cache-optimization-plan.md)。

既有验收映射：ACC-V561-TTS-01/02/03，HEAD-01/02/03，PIPE-01/02/03/04，LIVE-01/02/05，REL-01/02/03，RES-01/02，OUT-02/03，UX-02/03（上述省略项均沿用ACC-V561前缀）。仅补充工程场景，不修改34项注册表状态/命令；独立模拟、微基准或缓存命中不能授整项通过。

当前M0未通过，执行限于测量、瓶颈整改与必要输出安全；业务扩展和正式启用仍受原M0/许可/输出门约束。

依赖保持Rust引擎、Tauri/React、LLM API、本地Qwen API及独立Python/PyTorch FlashHead。无默认新增常驻依赖；流式服务候选须隔离评估并冻结版本，禁止覆盖现有环境。无Redis/Kubernetes/云向量库，不切LiveAct/双视觉引擎/ONNX主线。

本轮仅完成提案、设计和任务，所有运行时优化仍未因此实现，不下载模型、不调用服务、不更新安装。
