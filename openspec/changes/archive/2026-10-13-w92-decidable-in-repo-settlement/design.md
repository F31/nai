# w92 设计：清空 `decidable_in_repo`

## 一、问题形状：这个态是哪一类，为什么三条会悬着

`tests/pending-decisions.yaml` 的处置是**六态封闭枚举**，每态对应一个**必填字段**（W88 补齐第六行）：

| 处置 | 必填字段 | 它回答的问题 |
| --- | --- | --- |
| `answered_by_baseline` | `basis` | 基线哪一节回答了它 |
| `decidable_in_repo` | `recommendation` | **建议怎么做**（暗示：还没做） |
| `decided_in_repo` | `landing` | **已落地在仓库的哪里** |
| `needs_precondition` | `precondition` | 等哪些前置 |
| `needs_external` | `closure` | 外部闭合条件 |
| `out_of_scope` | `note` | 为什么不在范围 |

`decidable_in_repo` 的必填字段是 `recommendation`——**"建议"**。一条停在这里的条目，其判据只钉住
「有一个建议」，**不钉**「这个建议落地了没有」。这正是它作为**过渡态**的位置：W88 立第六态的动机
就是 PD-09「推荐早已落地、台账里却没有可结清的状态」，但**当时只处理了那一条**。

⇒ 剩余 3 条不是"被遗忘"，而是**第六态出生时没有回头扫**。这是一次**结清**，不是新设计。

## 二、核实：三条各自的真实状态

| PD | 问题 | 现在登记 | 核实的落地面 |
| --- | --- | --- | --- |
| PD-22 | A2A 入站入口是否对第三方开放 | `decidable_in_repo` | 活规格 `agent-harness` 的 A2A 条（§46.3 转写处） |
| PD-24 | A2A 委派深度上限是否可配置 | `decidable_in_repo` | **同一段**活规格 |
| PD-34 | 用户画像的验证方式 | `decidable_in_repo` | **无**（闭合在仓外） |

核实用到的实测事实：

- `grep` 「委派链深度」在 **Rust 零命中**（无 `DELEGATION_DEPTH` / `delegation_depth` / `max_delegation`）
  ⇒ 深度上限**没有实现**；H14 登记为 `capability_pack` + `pending`，与之一致。
- 活规格 `openspec/specs/agent-harness/spec.md`（line 208–229）该条正文已写
  「委派链深度 MUST 有上限（**初值 1**）」；Scenario `Outbound delegation escalates` 已写
  「或委派链已达深度上限 ⇒ 拒绝并记录」。
- 基线 §46.3（line 2164）原文：「委派边界：…**委派链深度上限初值 1（不得再委派）**」。
- 基线 §40.4（line 1930）：「**有界**：循环步数、并行度、结果大小、缓存条目、委派深度全部有界，
  **越界具名终止、不静默截断**。」
- 基线 §54.2 标题即「用户画像（**初版，未经验证**）」；§57.5（line 2647）：「**用户画像的验证方式**：
  §54.2 初版未经访谈，**MUST 在 R1 实现期以真实使用者验证后才可作为档位依据**」。

## 三、决定 1：PD-22 落到规格（入站来源限定）

**采纳的建议原文**：「首版**默认不对第三方开放**，只响应本机与本地信任配置中已登记的受信对端；
开放第三方入站 MUST 作为一次**显式的版本决策**（INV-31 与 T-24 的威胁面：对端自报无任何效力）」

**落到规格的句子**：`**R1 首版入站只响应本机与本地信任配置中已登记的受信对端**；对第三方开放
MUST 作为一次**显式的版本决策**，MUST NOT 因请求自称可信或自称已获授权而放行。`

**为什么必须落规格而不是留在台账**：该条与 Threat T-24（对端冒充）直接对应，而规格里原来只有
「对端身份 MUST 由本地信任配置**派生**」——它约束的是**已到达的请求**如何取身份，**没有**约束
**谁可以到达**。两者是不同的断言：前者是"身份从哪来"，后者是**可达集**。只写前者，实现完全可以
"接受任意第三方入站、再从本地配置里查它的身份、查不到就当作匿名外部请求处理"——**规格允许这样的读法**。

**为什么新增 Scenario 用"具名拒绝"**：沿用本仓库对降级/拒绝的一贯纪律（§40.4「不静默截断」、
§44「无静默截断」）——「无响应」与「拒绝」在**类型上**不同，前者不可区分于"服务没起来"。

## 四、决定 2：PD-24 落到规格（深度不配置化）

**采纳的建议原文**：「首版**固定为常量 1、不提供配置面**；配置化 MUST 推迟到 A2A 协议验证之后，
且引入时必须同时给出上限校验与「越界具名终止」（§40.4 的「有界」纪律）」

**落到规格的句子**：`**R1 首版委派链深度上限 MUST 为常量、MUST NOT 提供配置面**。`

**为什么不把"配置化前置条件"也写进规格**：那两句（协议验证之后 + 引入时的两项要求）是**前瞻条件**，
不是 R1 可判定的规范；写进规格会让正文膨胀且**不可判定**（"协议验证之后"没有仓库内的判据）。
它们留在台账的 `recommendation`（注解性留存，先例 PD-09）与 ADR 里。

**为什么改动是"收紧"而不是"改口"**：见第六节。

## 五、决定 3：PD-34 订正为 `needs_external`

**先排除另两个候选**：

- **不是 `decided_in_repo`**：该态要求「决定**已作出**且**已落地**」（W88 定义）。PD-34 的闭合条件
  是**真人访谈记录**——仓库里既没有访谈、也没有记录 ⇒ "已落地"不成立。
- **不是 `answered_by_baseline`**：§57.5 确实写了"以真实使用者验证"，但它**没有**给出
  recommendation 里的颗粒度（**三个画像各做访谈**、产出「画像-档位映射已验证」记录）。
  更关键：`answered_by_baseline` 的语义是"基线正文回答了它"，而 §54.2 的自我声明恰恰是
  **"未经验证"**——把一条"基线说它没验证"的项记成"基线回答了它"，是**不实声明**。
  （W88 对 PD-09 排除了同一个陷阱：§11.5 明写"具体机制待选型验证"，故 MUST NOT 记作
  `answered_by_baseline`。）

⇒ 剩下 `needs_external`：`closure` = 「三个画像各产出一份**真实使用者访谈记录**
（画像-档位映射已验证）；在此之前 §54.2 MUST NOT 被用作「Lite 该多 Lite」的论据」。
引用的 `§` 号（`§54.2`）会被 `CITATION_FIELDS` 的引用扫描解析为**基线实有章节** ✓

**`recommendation` 字段保留**：它是**被采纳的那份建议**——删掉就丢了"决定了什么"。这与 PD-09 的
处理一致（`decided_in_repo` 的必填字段是 `landing`，`recommendation` 是**注解性留存**）。

## 六、不越权：基线的"一般描述"与规格的"R1 具体化"分层

PD-24 会让人担心"是否改了正本"。判据是**对象性质**，不是章号：

| 载体 | 句子 | 对象 |
| --- | --- | --- |
| 基线 §46.3 | 委派链深度**上限初值 1**（不得再委派） | 该协议的**一般描述**（"初值"= 起点值） |
| 规格（本轮） | **R1 首版**委派链深度上限 **MUST 为常量、MUST NOT 提供配置面** | **R1 首版**的具体化 |

两者**不矛盾**：基线说"初值是 1"，规格说"R1 首版把它钉成常量、不给配置面"——后者是前者在
**首版范围内的取值决定**。这正是 PD-24 要裁的那个自由度（"初值"是否可调）。
⇒ 规格是对基线的**具体化**，MUST NOT 读作"规格推翻正本"。**基线正文本轮一字不动**；若将来该
决定需要进正文，走升版收录（与 W65/W87 的既有节奏一致）。

PD-22 同理：基线 §48.7 把"入站入口是否对第三方开放"**登记为待决策**（line 2362）⇒ 规格补上
是从"待决"变"已决"，不改基线。

## 七、清空一个态暴露的守卫隐含依赖（本轮的技术核心）

把 `decidable_in_repo` 的计数从 3 改成 0 之后，**两处测试用例会失去其作用对象**：

1. `tests/registry.test.mjs` 的 §NNN 注入用例（约 line 744）：

   ```js
   const item = stray.entries.find(entry => entry.disposition === disposition);
   assert.ok(item, `${disposition} must be represented in the ledger`);
   ```

   它用**处置**定位"一个含 `recommendation` 的条目"。态一空 ⇒ `item === undefined` ⇒
   `assert.ok` **失败**（比静默好——但它失败的原因是"找不到样本"，不是"守护的东西坏了"）。

2. 同文件「each disposition has to pay for itself」用例（约 line 961）的 `cases` 表里
   `['decidable_in_repo', 'recommendation']` 一行，同样是按处置定位。

**危险的修法**（MUST NOT 采用）：加一句 `if (!item) continue;`——那会把"该态没有实例"与
"该字段的引用不再被扫"**混为一谈**，正是 W66「删字段照样绿」的同族形状。

**采用的修法**：把样本定位从**处置**改为**字段存在**：

```js
const item = stray.entries.find(entry => Object.hasOwn(entry, field));
```

理由与本仓库既有的纪律同源：「**触发条件 MUST 只由「字段存在」决定**」（W80/W83/W88 三次确立）。
测试要断言的是"`recommendation` 里的 `§NNN` 被扫"，样本就该按"**谁有 `recommendation`**"选，
而不是按"谁现在是某个处置"选——后者让**一个合法的数据变更**（清空某态）**改变判据的覆盖**。

**空态的显式处理**：`decidable_in_repo` 计数为 0 时，数据侧确实无实例可注入。这不是静默跳过，
而是**被断言的事实**——用例断言「`DISPOSITION_COUNTS` 说 0 时，数据里 MUST 确实没有该态条目」
（计数与数据**双向一致**），并另加一条**本轮的成果断言**：`decidable_in_repo` 计数 == 0。

`DISPOSITION_COUNTS` 是**逐项写死**的分布表（W66 教训：「总数对『被改类别』是瞎的」）。
改任何一个处置都会被它抓住；本轮必须**同步**它，否则判据**红**（这是想要的）。
`CHAPTER_COUNTS`（各章新增条数）**不动**——条目数没变。
