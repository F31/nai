## 1. 本轮判定的到底是什么

H18 的原文只有两句，但两句的主语不同，必须分开落：

1. 「harness 新机制**默认只在演练、影子与人工辅助下启用**」⇒ 这是**默认启用集合**，
   可判定形式是 `RampStage::enabled_by_default()`：**只有 `AutoSupervised` 为假**。
2. 「进入受监督自动 MUST 先通过 §47.2 的回归，并在决策日志留下启用记录」⇒ 这是**晋升门控**，
   两个条件**同时**满足才允许，缺一个都要**具名拒绝**。

把它们合成一个函数会让「这次拒绝是因为默认不启用，还是因为条件没过」重新不可判定——
这正是 W66 不复用 `bridge::Degradation` 的同一条理由。

## 2. 为什么是 `evaluate::ramp` 而不是并入 `evaluate::harness`

`harness.rs` 已经是 §47.1（观测）与 §47.4（降级）的家。§47.3 是**第三块**，维度不同：
观测与降级判的是**一次调用**，爬坡判的是**一个机制 × 一个阶段**。
放进 `harness.rs` 会让「这次拒绝属于哪一类」重新不可判定，也让该文件同时承载三个互不相同的输入形状。

也**不**复用 `session::change_mode`：那个判的是**会话维度**（值守租约、二次确认、`actor_allowed`），
且已实现 `AutoSupervised → Assisted` 的回落；本模块是**机制维度**——同一个会话里，
不同 harness 机制可以处于不同爬坡阶段。两者互补，不重叠。

## 3. 四条阶段与一个必须写下来的发现

§5.9 与 §47.3 的爬坡是**四段**：演练 → 影子 → 人工辅助 → 受监督自动。
但契约 `SessionMode`（`crates/nai-contracts`）只有**三个**取值：`Rehearsal`、`Assisted`、`AutoSupervised`
——**没有 `Shadow`**；而 §1.4 与 §17.3 把「影子模式」列在 **R2（Standard）**。

⇒ **H18 的默认启用集合里有一个 R1 阶段在 R1 里没有契约落点**。本轮的处理是**照实建模、不掩盖**：

- `RampStage` 是 kernel 内部的四值枚举，**含 `Shadow`**；
- `RampStage::session_mode()` 返回 `Option<SessionMode>`：三个有落点，**`Shadow` 返回 `None`**；
- 测试把这条**钉死**（恰三个 `Some`、`Shadow` 为 `None`），使「影子在 R1 内**有名无实**」成为机器可见的事实，
  而不是一句注释。

不在本轮改基线文本（改基线是升基线轮次的事，且 MUST 是 1:1 行替换）；
本轮把它作为**待确认项**登记进报告，交下一轮基线修订裁定。

## 4. 「通过 §47.2 的回归」的两种读法，以及本轮的选择

§47.2 列了**六类**必须进黄金集的回归：装配回归、意图拒识、工具失败恢复、缓存误命中、
MCP 工具描述漂移、A2A 越权委派。§47.2 的措辞是「修改 harness 的提示词、装配顺序、阈值、路由或技能清单后，
MUST 通过**相关**回归才生效」，而 §47.3 只说「通过 §47.2 的回归」。

两种读法：

- **(A) 全六类** —— 字面最严；但会让「改一行提示词也要跑 A2A 越权委派回归」成为常态，且与「相关」二字冲突。
- **(B) 相关类别** —— 与 §47.2 的「相关」一致，但需要调用方**声明**受影响的类别。

本轮取 **(B)**，并要求 `touched` **非空**：一个机制若声明「我不影响任何类别」，
则「相关」二字无从判定，门控会被一段空声明绕过 ⇒ 具名拒绝 `regression_scope_undeclared`。
**这是解释，不是基线原文**，已作为待确认项登记；若下一轮裁定为 (A)，只需把 `passed ⊇ touched`
改成 `passed ⊇ REGRESSION_CATEGORIES`。

## 5. 回归失效（`regression_stale`）不是新增要求

§47.2 的「通过相关回归**才生效**」已经蕴含：回归结论是**相对某个 harness 状态**的。
提示词、装配顺序、阈值、路由、技能清单任一项变化 ⇒ 先前的「通过」不再使这次晋升生效。

可判定形式：晋升请求带 `passed_at_revision: Option<u64>` 与 `harness_revision: u64`，
两者不等（或前者缺失）⇒ `regression_stale`。**不放宽**为「通过过就行」。

## 6. INV-33：为什么这条 R1 验收不依赖能力包

§47.3 要求「通过 §47.2 的回归」，而承载六类回归的**黄金集（H16）在 V3.9 §51.3 属能力包**。
这不构成对 INV-33（默认组合不依赖能力包）的违反，理由必须写清楚：

- **门控判定的是「回归是否已被记录为通过」**，不是「跑一遍回归」。
  判定面只消费一份已声明的 `passed` 集合，**不执行**任何黄金集用例；
- 因此 H18 在**未安装任何能力包**时可判定（INV-33 满足）；
- **产生**那份证据的执行体是能力包里的 H16 —— 这是「判定面在 R1、证据生产在别处」，
  与 W66 的 H15/H17 完全同构（判定在 kernel，接线在 runtime）。

## 7. 启用记录：校验什么，不校验什么

§47.3 的「在决策日志留下启用记录」落成 `EnablementRecord`：

- **校验**：存在、指名同一机制、指名目标阶段、值内不得含明文凭据（INV-11，
  复用 `evaluate::harness::CREDENTIAL_MARKERS`，**零重复**）。
- **不校验**：记录**是否真的已追加进哈希链**——那是 `nai-storage` 的只追加写入，
  属 runtime 接线。允许时门控给出 `record_to_append`，由调用方去追加。

凭据判定沿用 W66 的**扫值不扫字段名**：字段名含 `key` 而值干净 MUST 放行。

## 8. 取舍

- **不改 `status`**：H18 保持 `pending`（沿用 W57/W66 口径：机制交付 ≠ 验收达标）。
- **不新增契约名**：`RampStage` 是 kernel 内部枚举，能力目录零漂移。
- **零新增依赖**：只用 `std` + 既有 `nai_contracts::v1::SessionMode`。
- **不改基线文本**：本轮无基线升版。
- **不加新开关**：`RegressionCategory` 与 `RampStage` 直接照抄基线，不参数化。

## 9. 验证方式与非空洞守卫

- `cargo xtask check --profile full`（含新增的 `tests/ramp.rs` 目标）。
- **集合守卫**：构造出的拒绝集合**恰为** `RampRejection::ALL`（既证每条可构造，也防未登记名字）。
- **内容守卫**（W66 教训：条数守卫对「内容被改小」是瞎的）：
  ①六类回归的标签逐项写死；②四段顺序与「默认启用集合恰为前三段」逐项写死；
  ③`session_mode()` 的映射逐项写死。
- **非空洞守卫**（每组都要注入验证真会失败）：
  ①门控忽略回归 ⇒ 失败；②忽略启用记录 ⇒ 失败；③忽略修订失效 ⇒ 失败；
  ④凭据判定改成扫字段名 ⇒ 名为 `key` 而值干净的记录被误拒 ⇒ 失败；
  ⑤只报第一个缺失类别 ⇒ `missing_categories` 必须含全部 ⇒ 失败。
