# Design: W127 — 从决策日志重建装配，以**条目**为单位

## 决策 1：口径来源是 registry 的 H02 标题，不是对 §41.5 散文的外推

先把「凭什么说跨行合并**不达标**」钉死，因为这决定了本轮的合法性。

- 基线 §41.5（`docs/直播数字人 + 智能体系统技术方案 V3.11.md:1971`）原文：
  「装配 MUST 落决策日志：进入的片段标识、各段预算占用、裁剪项与原因、本次调用的模型与提示词版本。
  装配记录 MUST NOT 含明文凭据（INV-11）。验收 H01、H02。」
  —— 它**没有**明文写「单个日志条目」。若只有这句，「跨行合并」是否达标是可争的。
- 唯一验收来源 `tests/registry.yaml` 的 **H02 标题**：
  「装配可重建：由决策日志的片段引用重建**同一**上下文，不依赖当时内存」。
  「**同一**上下文」是登记在册的验收口径 ⇒ 由两行拼出的、从未被装配过的上下文**不是**「同一上下文」。

⇒ 本轮是**按已登记口径收紧实现**，不是新增需求、不是改基线。报告与 ADR MUST 如实写出这条依据链，
MUST NOT 把结论说成「§41.5 要求单条目」。

## 决策 2：条目就是装配，因为**写路径**就是这么写的

`record_assembly` 的载荷把 §41.5 的四项**一起**落进**一条** `assembly` 条目；而
`ordered_fragments` 是**按 `record.fragment_ids` 逐项**在素材里找并写出 id／来源标识／**字面正文**。
两条推论直接支撑本轮的形状：

1. **一条已被真实写入的行，其片段标识序列 == 那次写入的 `record.fragment_ids`**（含重复项）。
   ⇒ 对任何**真的被记录过**的记录，按条目选择必然找到它自己那一行，逐条目判定与池化判定**结论相同**。
   本轮的收紧**不为合法用例引入假阴性**。
2. 反过来，池化才引入**假阳性**：记录 `[A, B]` 而链上只有 `[A]`／`[B]` 两行时，
   并集能拼出 `[A, B]`，但**没有任何一条装配曾经持有它**。

## 决策 3：选行规则用**标识多重集**，且**不计顺序**

三个被否掉的备选，各自失败的理由不同：

| 备选 | 否掉的理由 |
| --- | --- |
| 按确切顺序选行 | `rebuild.order_differs` 会**不可达**：顺序不同的行只是「不被选中」，于是「顺序不符」被悄悄换成更模糊的 `not_in_one_entry`。一条具体的拒因失去唯一覆盖，而守卫看不出（它只问「名字在不在被观察集合里」）。 |
| 按集合（忽略重复）选行 | 「集合层对划分是瞎的」：记录 `[f1, f1]` 会被 `[f1]` 一行承载，而那一行只装配过一次该片段。 |
| 按「超集即可」选行 | 超集条目是**另一次**装配。用它重建较窄的记录＝凭历史改写出一个不曾发生的上下文。 |

⇒ `entry_carries_assembly` = 长度相等 **且** 逐一配对（`taken` 数组，一对一），
等价于「多重集相等」，顺序不参与。

## 决策 4：跨条目的结论是**存在性**的，失败时的原因取**并集**

- **存在一个**承载条目能重建 ⇒ 可重建。否则后一个「顺序不同」的条目会把前一个**正确**的条目否掉，
  而那与事实相反（链确实能重建它）。
- 一个都不行时，拒因取**所有承载条目**的**并集**（`refuse` 已去重）——每个名字都至少对**某一个**
  承载条目为真，只报第一条会把真实原因藏起来。而 `rebuilt` 与三类 id 清单取**第一个**承载条目的：
  序列必须说清是**按哪份顺序**读出来的。
  这一条不是审美选择：既有用例 `the_logs_own_order_decides_and_a_difference_is_named` 断言
  拒绝时 `rebuilt` 仍等于**日志自己的顺序**（`[frag-a, frag-b]`）。若失败分支把 `rebuilt` 置空，
  该用例立刻变红 —— 它正是「失败≠什么都没有读到」的守卫。

## 决策 5：没有任何条目承载时，`unlogged_ids` 必须对**整条链**重新派生

朴素写法是对空池跑一遍 `rebuild_assembly(record, &[])`，于是每个标识都被报成「未落日志」——
在 `[A]`／`[B]` 两行的链上，`A` 与 `B` **都在链上**，这句话是**假**的（不是保守的）。
⇒ 该分支只对「**在整条链的任何一行里都不出现**的标识」报 `fragment_not_logged` ＋ 入 `unlogged_ids`，
并**始终**追加 `not_in_one_entry`。两条原因互不短路：一个标识可能既没落日志、又不存在承载条目。

## 决策 6：写路径**不改**，且这不构成「同一件事两处定义」

`record_assembly` 仍调 `rebuild_assembly(record, fragments)`。它的输入是**本次要落盘的素材**，
不是「链上的一个条目」：素材的标识多重集可能与记录不同（既有的
`a_referenced_fragment_absent_from_the_log_is_refused_by_name` 正是给记录 `[a, b]`、素材 `[a]`，
期望的是 `fragment_not_logged`）。若把写路径也改成 `rebuild_assembly_from_entries(record, &[fragments])`，
该用例的拒因会被换成 `not_in_one_entry` ⇒ **一次「统一」把一条具体原因换成了更笼统的**。

⇒ 两条路径都调**同一个** `rebuild_assembly`（判定只有一处）；区别只在**传给它的池怎么来**，
这是输入形状的差异，不是判定规则的第二处定义。「版本齐备」这 3 行抽成 `version_rejections`
由两条路径共用，正是为了不出现第二份。

## 决策 7：非空洞守卫必须按**面**取样，并写明这一不对称

既有守卫 `every_rebuild_rejection_is_reachable_through_the_runtime` 原先对每个变体都构造一次
`record_assembly` 调用。`not_in_one_entry` 是**链级**事实：写路径一次只交**一个**条目，
结构上产生不出它。⇒ 该变体改走**读回面**（两次 `offer` 造两行，再 `rebuild_assembly_from_log`）。

把守卫改成「一个入口能产出全部拒因」是**做不到也没必要**的；真正的风险是**悄悄换成一个恒真的样本**。
所以：注释里写明这处不对称是**结论**（链级 vs 单次写入级），并保留「每个变体各有其独有场景」这层要求。

## 决策 8：一处测试失败的性质判定（`DeadlineExceeded`）

全量跑 `cargo test -p nai-runtime --test assembly` 时，`every_row_comes_back_with_its_own_usage_and_crops`
在 `tests/common/mod.rs:118`（`open_store`，用 `bringup()`）报
`StorageError{DeadlineExceeded, "operation stopped"}`。判**非代码缺陷**，依据是四条替代判据中的三条：
①错误类与位置都在**夹具/bring-up**，且该文件上方注释**已具名记载**同一现象
（默认并行测试下多个数据根同时建库、迁移输掉磁盘竞争 ⇒ 夹具里随机 `DeadlineExceeded`）；
②失败集合**不绑定**本轮改动的领域（该用例只读 `read_logged_assemblies`，与本轮改动无交集）；
③同一份代码在**限测试线程**（`--test-threads=2`）下 **27 passed / 0 failed**。
⇒ 处置 = 限并发，**不改代码**。
