# 设计：档位驻留、空闲回收与部署迁移

## 背景与约束

W15 交付的 `nai-upgrade-core` 已经回答了「一个升级包能不能装」：清单解析、`verify_package` 全链校验、撤销列表、预检、九步事务与 journal、会话门控、成本分项。本变更在同一 crate 内回答它之后的三个问题——**装完占多少**（A08）、**闲置怎么放手**（A09）、**离线与换部署形态怎么办**（R11）。同一 crate 的理由是判据同源：§14.4 末句「未启用的能力不占用进程、端口、显存或云请求」既是 A08 的验收，也是 A09 的前提，把它们放进两个 crate 会让同一条不变量有两个真相。

仓库既有的三条硬约束继续适用（V3.6 §20、`xtask/src/deps.rs`）：

1. `nai-upgrade-core` 在 `shared` 层，MUST NOT 依赖 `plugin`/`runtime`/`app`/`tool`；
2. `shared` 层 MUST NOT 引入平台 SDK（`tauri`/`windows`/`ort`/`cuda`）或 HTTP 客户端；
3. portable 检查 MUST NOT 包含某台机器的资源假设。

第 2 条在本变更是**承重**的：crate 没有 HTTP 客户端，「离线安装不会偷偷下载」就不是靠一个 `offline: bool` 开关维持的，而是编译期性质。

## 关键决定

### 决定 1：驻留足迹是声明式的，且只在 enable 时物化

`ResourceClaim { kind, name, amount }`，`kind` 是**封闭四族** `Process | Port | Vram | CloudRequest`——正好是 A08/A09 原文列的四样。

`ResidencyLedger` 里每个能力有两份足迹：`declared`（安装时登记）与 `held`（启用时物化）。于是：

- 未安装 ⇒ 账本无此条目；
- 已安装未启用 ⇒ `held` 为空**且不可能非空**（只有 `enable` 写 `held`）；
- `disable`/`uninstall` ⇒ 清空 `held`。

「禁用即零占用」因此是账本的**结构性质**。`audit(now)` 把它变成可检出的断言：任何「未启用却持有资源」「未安装却持有资源」「排他资源被两个启用能力同时持有」「超过 TTL 仍未释放」都是违规标记，而不是一句文档承诺。

**否决方案 A：把足迹写成配置里的注释/文档表格。** 那份表格不会被任何测试读到，忘记关闭的预览轮询进程照样存在。判据必须是可执行值。

**否决方案 B：让 `held` 由外部宿主上报（「你告诉我现在占了什么」）。** 那样「禁用即零占用」就退回成对宿主的信任：宿主漏报就永远看不见。声明式 + 物化把断言留在核心侧；真实配额（显存）确实只能由宿主测量，但那是**预检/成本**要用的**输入**（`preflight` 已按可注入探针处理），不是驻留账本的真相来源。

### 决定 2：排他性只对进程名与端口成立

`Process` 与 `Port` 在操作系统层面天然排他：同名进程只会有一个，端口绑定第二次必然失败。`Vram` 与 `CloudRequest` 不排他——两个能力可以各自加载同一模型、可以各自轮询同一 API。因此 `enable` 只对前两族做冲突检查（`CONFLICT` 拒绝，而不是覆盖或静默取其一）。

把四族一律做成排他会凭空造出「同一模型不能被两个能力使用」这种不存在的限制；一律不排他则会让「端口已被占用」在启用时静默通过、在运行期炸掉。

### 决定 3：空闲释放按 TTL，且分族

A09 的原文是「按 TTL 卸载模型、结束临时 worker、关闭未用预览」——**三件事、三种节奏**。TTL 因此是分族数据（`IdlePolicy`），默认：临时 worker 30s、未用预览的云请求 60s、模型显存 300s。方向的理由是**重载代价**：worker 重启很便宜，先走；模型重载最贵，留到最后。端口跟随其进程（同为 30s），因为「进程还在、端口先放手」不是一个可达状态。

`reclaim(now)` 的行为被刻意限制为**只释放 TTL 到期的**，并报告 `held_back`（仍保留的声明数）。**否决方案 C：场次一结束就全部释放。** 看起来更「干净」，但代价是下一句要付一次完整模型重载（§14.2 的 Hybrid/Distributed 形态下更贵）。规格写的是 TTL，不是立即释放。

时间以参数进入（`enable(…, now_ms)`、`session_ended(…, now_ms)`、`reclaim(…, now_ms)`），核心内部不取墙上时钟——与 `verify_package(now_ms)`、`preflight` 的取向一致，也是这些判据能在 portable 下被确定性地测出来的前提。

### 决定 4：档位迁移图是两段差集的并，不是一张全连接表

`tier_plan(from, to)`：`install` = 从 from 到 to 沿途档位增量的并；`remove` = 反向的并；`from == to` ⇒ 双空。

于是「Lite → Pro 不要求先装中间档」不是特例分支，而是并集运算的必然结果；`tier_plan(Standard, Lite)` 与 `tier_plan(Lite, Standard)` 互为逆序，不需要第二张表。集合是 `&'static str` 常量，天然不可能含内核——**否决方案 D：把档位差异做成「安装内核的不同编译配置」**，那正是 A08 明文禁止的「重装内核」。

### 决定 5：离线是编译期性质，缺件是显式拒绝

`offline.rs` 只做一件事：**在进入 `verify_package` 之前**确认清单声明的每个文件都在本地工件集合里；缺则 `CAPABILITY_NOT_READY` 并指出路径。

之所以要单独前置，是因为 `verify_package` 对缺件报的是「missing package content」——那对在线路径是准确的（内容还没到），但对离线路径不好：运维需要知道的是「这个包不可能离线装，因为还差一个文件」，而不是「内容不完整」。两种拒绝都正确，但**拒绝的原因不同**，报告要能分开。

**否决方案 E：给 `verify_package` 加一个 `allow_fetch` 开关。** 一个恒为 `false` 的开关是伪保证；真正的保证是 crate 没有 HTTP 客户端，任何「抓取」都必须先加依赖，那是个显眼的、需要评审的动作。

### 决定 6：迁移的三种拒绝先于任何搬动

`plan_migration` 在产生计划之前拒绝三件事：

1. **有活动会话** ⇒ 拒绝（§14.3「实时链路留在原部署，在维护窗口切换」）；
2. **分布式目标 + SQLite 写者 > 1** ⇒ 拒绝（§14.3「SQLite 不挂多节点写」）；
3. **权限在目标形态无映射** ⇒ 拒绝（§14.3「权限映射」；静默丢弃权限是安全缺陷，不是便利）。

`verify_migration` 再复验三项一致：权限集合（映射后的期望值，顺序无关）、**证据版本**、数据哈希。证据版本与哈希用**不同错误码**（`VERSION_INCOMPATIBLE` / `INVALID_ARGUMENT`）区分——「版本对不上」和「数据被改过」是两个不同的故事，报告要能分开。

`OutputSwitch` 用 key 幂等：`switch(key)` 第一次 `Announced`、重复 `Duplicate`。key 由调用方给（典型是 `session/epoch`），因为「同一次切换」的身份只有调用方知道；核心只需要保证同一个 key 不会被宣告两次。

**否决方案 F：让 `verify_migration` 只比哈希。** 哈希一致能证明字节没被改，但证明不了**权限被正确映射**——把 `admin.team` 悄悄降成 `viewer` 之后哈希照样一致。三者必须分开验。

## 与既有 capability 的关系

- `upgrade-transaction`：不改。它管「包能不能装、装了怎么回滚」；本 capability 管「装完的占位、闲置的释放、离线与迁部署」。两者的接缝是**已通过校验的包**：`offline.rs` 复用 `verify_package`，`residency.rs` 消费的是安装结果。
- `local-persistence`：不改。迁移的导出/导入与哈希一致**判据**在本 capability，真实的库与工件搬动仍归 storage。SQLite 单写者因此是**拒绝条件**而不是本层要去实现的能力。
- `plugin-hosts-and-ipc`：不改。「未启用插件无后台进程」由驻留账本断言，宿主的真实进程管理仍是 hosts 的职责。

## 未做边界（必须如实记录）

- `Vram` 是**声明式索赔**，不是真实显存配额；真实 GPU 探测仍需宿主注入（与 `preflight` 的探针一致）。
- R06（2h/8h/24h 长播无资源增长）、B04（整链路延迟分位）需真实设备与长时运行，本轮**不做**；A08/A09 的 `automation: manual` 与 R11 的真实轻云实例同理。
- A10（云断连不伤本地链路）与 A11（Pro 多会话隔离）是独立主线，本轮**不做**。
- 真实 Windows 安装器、update-helper、代码签名链（W15 遗留）仍不在本轮范围。
