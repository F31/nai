# 设计（w65 V3.9 范围重排与升基线）

## 1 为什么「就地订正」终于成为必做项

前两轮升基线（V3.6→V3.7、V3.7→V3.8）采用**纯追加**，前提是「**无矛盾可订正**」：只补新内容，与既有条款不冲突。
本轮前提**不成立**——核实过程中查出 7 处「已声明内容与已实现/已登记内容互相矛盾」：

| # | 矛盾 | 性质 |
|---|---|---|
| D1 | `A12/A13/A14` 在基线正文**零命中**（只存在于注册表与几份活文档） | 基线对 A 系列的索引比注册表少 3 条 |
| D2 | §47.6/§48.6 称「已执行轮次 W41–**W55**」，而 **W45 全仓无任何记录** | 轮次断言与仓库不符 |
| D3 | §47.6 的 W57 行与 §48.1 的 N3 称「冻结 `memory.access@1`」，而 W57 **未改能力目录** | 未兑现且被后续轮次证伪 |
| D4 | §47.6 的 W64 标线 R2，却同时交付 H16（R2）与 **H18（R1）** | 单行跨两条线 |
| D5 | §23.2 的表数被外部审视误传为 44 | 数字错误 |
| D6 | `docs/control.md` 写「44 篇 ADR 中首条桌面壳条目」 | 易漂移计数写进活文档，撰写时即已失效 |
| D7 | `openspec/specs/spec-driven-delivery/spec.md` 仍写「以 **V3.5** 为统一设计基线」 | **自 V3.6 起即不成立**，两轮登记为遗留而不订正 |

此时继续纯追加，只是把同一条矛盾**登记第二遍**，把「该读哪一段」的判断责任留给开发者。故本轮确立：
**活文档就地订正 / 历史记录保留原文 + 追加勘误段**（V3.9 §56.2），并给就地订正加**硬约束**——
**MUST 是 1:1 行替换（不增删行）**，否则会以「订正」为名破坏 `§NNN` 引用契约。

实测：前 2366 行 23 个 hunk、41 行、**全 1:1、零增删**（`diff` 中 `a`/`d` 型 hunk 为 0）。

## 2 三个维度必须拆开

此前文本把 **R1** 同时当作「首版范围」与「Lite 的永久能力」，于是「压缩首版」看起来像「阉割 Lite」。
V3.9 显式拆开三个正交维度：**发布阶段**（§51，硬门槛，不因档位而变）/ **产品档位**（§14.1，预设、可加装）/
**部署配置**（§14.2，与档位正交）。

⇒ **R1 = Lite 的默认组合**；Lite 仍可加装能力包（§14.1 末尾「矩阵是默认预设，不是禁止加装」继续有效）。
**轻量是默认组合的性质，不是能力上限的性质**——这是用户三条约束中「降低运行维护成本」与「不降低扩展性」同时成立的形式。

## 3 为什么是「能力包」而不是「删掉第四部分」

外部批评建议把整个第四部分移出 R1。不采纳，理由：第四部分里**多项是调用 LLM 的基础纪律**，不是可选子系统——
上下文装配与分段预算（H01、H02）、记忆写入门槛与作用域读取（H03、H04）、harness 观测入决策日志（H15）、
逐层具名降级（H17），以及 §5.9 既有的模式爬坡门控（H18）。删掉它们，默认组合就**无法**正确调用模型。

也不全留在 R1（那就是范围膨胀）。分界判据取一句可判定的问句：

> **「一个确定性的上下文装配函数能不能满足它？」** 能 ⇒ 留在 R1；只有建独立子系统才能满足 ⇒ 能力包。

它比「删掉第四部分」精确，也比「全留在 R1」诚实——**约束不随模块一起被删，模块可以后置**。

但「降级」此前**无处表达**：发布线只有「承诺 / 不承诺」两态，于是降级只能表现为删除。本轮新增第六条发布线
`capability_pack` 解决这个二难：保留设计边界、信任域归属与不变量，但不进首版门槛。

## 4 能力包集合断言为什么必须是**三向**的

只断言「能力包集合恰为 29 条」是不够的——把一条能力包条目复制一份改成 `r3`，集合仍然完整。
故断言必须三向：

1. **集合完整**：`capability_pack` 条目 MUST 恰为 M01–M18 与 H05–H14、H16（共 **29** 条），缺一条即失败并指名；
2. **无混入**：MUST NOT 有归属外的 id（如 `H17`）被标为 `capability_pack`；
3. **不与首版门槛相交**：MUST NOT 有任一能力包 id 落在 `slice_0`/`r1`/`r2`——**这就是 INV-33 的机器形式**
   （默认组合不依赖能力包：R1 内每条验收 MUST 在未安装任何能力包时可判定）。

失败信息 MUST 同时给出**id 与当前线**（如 `M01=r1`），否则「哪一条被提回了首版」不可定位。

非空洞守卫用**三种注入**验证（`tests/registry.test.mjs`）：把 `M01` 提回 `r1` / 把 `H17` 标为 `capability_pack` /
清空整条能力包线——三种都必须被抓到。**只断言「非空」的守卫是可被满足的空洞断言。**

## 5 发布线语义的三处边界

- **启用即验收**（§51.4）：能力包 MUST NOT 在通过其验收之前进入自动模式；§5.9 的模式爬坡（演练 → 影子 → 人工辅助 →
  受监督自动）对能力包同样适用。**启用是排期动作，不是权限动作。**
- **单一路径**：能力包的加装路径沿用**同一条**升级与迁移图（§14.3），**MUST NOT** 出现第二条安装路径——
  否则「降低运行维护成本」被第二条路径抵消。
- **不改变默认组合**：启用 MUST NOT 改变默认组合的行为、成本或 §12.2 的降级顺序
  （§14.3「未启用的能力不占用进程、端口、显存或云请求」是同一命题的既有表述）。

## 6 决策日志：限定宣称，而不是删掉它

外部批评建议简化决策日志。不采纳删除，采纳**限定宣称**（§55）：

| 容易被读成 | 实际成立 | 对规格的要求 |
|---|---|---|
| 哈希链能证明未被篡改 | 能发现**部分**改动；**不能**单独证明本机管理员未重写整条链 | MUST NOT 对外宣称「防篡改证明」 |
| 「回放与原决策一致」是一件事 | **确定性回放**（同一录制输入）与**重调在线模型**（结果本可不同、且要花钱）是两件事 | MUST 分开验收，R07 的验收项 MUST 指明是哪一种 |
| 全部业务状态可由日志投影重建 | 允许**事务状态表 + 快照 + 关联日志**的混合 | 恢复设计 MUST NOT 绑定单一机制 |

⇒ 真正应被简化的是日志承担的**恢复与投影职责**，不是哈希计算本身。**R07 保持在 Slice-0，线不变。**

## 7 平台准入为什么本轮**不落规格**

§52 把此前压在一个「桥接 PoC」上的三件事拆成三条**互不替代**的命题：平台规则准入（需**书面确认**允许该账号与该类目的
数字人自动互动）、平台事件接口可用（桥接 PoC）、画面进入直播（官方输出路径确认）。

本轮**不为它写规格需求**，理由如实登记：这三条命题的证据形态是**书面确认与官方入口的存在性**，
不是可执行的检查；且注册表中**没有**与它们对应的验收 id（P01 是「伴侣启动/退出/重连/切场次不产生旧房间播报」，
语义不同）。为它们新造 id 会牵动 P 家族的编号定义，属**另一轮**的登记决策。
本轮只做两件可做的事：把它们**拆开**并设硬门槛（§52.1 的表），以及把「技术能退回 ≠ 商业上成立」写进 §52.2。
