# 设计

live-session JSON Schema新增必填tts_warmup_text（1–64字符、非空白），配置不满足时拒绝，不加旧配置兼容路径。live_session.proto Event新增tts_prepared，代表本次准备真实预热完成，不代表永久服务健康或设备输出成功；Prepared须语音与视觉均完成。先生成Rust/TS/Python/C++，再实现消费者。

root顺序准备：进入TTS_PREPARING→等待本地服务空闲→一次配置短句合成并丢弃PCM→确认适配器真实EOS/样本和父取消→记录tts-warmup.json→VISUAL_PREPARING→现有视觉准备。顺序降低共享GPU争用；复用已加载视觉时不重新加载。模型子操作deadline=min(配置,父剩余)，≤45秒；父准备总期限仍≤240秒。失败/停止不签发Prepared，停止输入线程仍不等待模型锁。服务不支持GPU抢占时仍只承诺客户端取消交付。

预热不播放、不持久化音频，不计作正式讲解的缓存命中；固定文本来自配置而非代码。报告记录成功/失败、耗时、实际样本和尝试次数，语音失败不冒充视觉失败。GUI明确语音已预热、画面已准备，设备在开始时另验。Start必须同时具备两个事实，重复Prepare只复用本会话完成事实，不能当服务持续健康保证；真实业务请求仍独立核对服务响应与EOS。

理论范围：上一轮首句TTS比后续慢约3.6秒，预热只能将冷路径提前到显式准备，不能消除热态约3.1秒或句间1.2–1.7秒；必须原样报告准备+正式调用总数和新体验门结果，不声称3秒已达标。

验证：Schema边界、Protobuf跨语言、取消/长度/样本/失败静音预热CPU测试、Prepared双事实/Start准入/UI状态、Windows真实预热+同四句及准备中停止。只定向验证，不跑旧全量。
