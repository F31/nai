# 设计 · W78 打包粒度

## 1. 判据来源与边界

§51.3 的表格有三个列：`能力包 | 验收 | 依据`。本轮的判据**只**取自这张表 + 它后面那一段
「保留在 R1 的基础纪律」。

- 第一列 = **包的标签**（`扩展与技能（含声明式技能）`、…、`harness 黄金集`）。
- 第二列 = **该包声明的编号**（`M01–M12`、`H05、H06`、…、`H16`）⇒ `expandIds` 展开。
- 第三列 = **依据**（非空即可；它是「这个包为什么可以后置」的那句话）。

**为什么不读 §51.2 的退出条件**：§51.2 是散文、没有表格，而 `sectionTable` 找的是「标题之后
第一张表」——对 §51.2 调用它，取到的是 **§51.3 的表**。⇒ 对无表章节调用同一工具会**静默取错**，
故本轮不碰 §51.2。（这条限制写进报告的遗留，而不是靠记性绕开。）

## 2. 为什么「划分」必须单独断言

设 `R` = §51.3 的 8 行，`U = ⋃ Rᵢ`。

- `U` 正确 **不蕴含** `R` 是划分。反例：`R = {M01–M12, M05–M08}` ⇒ `U = M01–M12` 不变，
  而 `M05–M08` 同时属于两个包，打包粒度已破。
- 反过来，`R` 是划分 **也不蕴含** `U` 与 registry 一致。

两个方向都要断言，且错误形态不同（前者是「同一编号两个包」，后者是「集合两侧不符」），
所以**必须并列**，不能用一个总账数字代替。

## 3. 五条判据（全部具名）

| 编号 | 判据 | 非空洞性从哪来 |
| --- | --- | --- |
| G-A | §51.3 的行数与**逐行标签+编号**等于 `CAPABILITY_PACK_ROWS` | 写死的是**内容**而不只是条数 |
| G-B | 每行的「依据」非空 | 空依据若允许，则「为什么后置」无人复核 |
| G-C | **无编号同时属于两个包**（划分） | 见 §2 的反例 |
| G-D | 表后「保留在 R1 的基础纪律」的编号集合**非空**且与 `U` **不相交** | 「非空」挡住解析恒空即恒真的空洞写法 |
| G-E | `U` == registry 的 `capability_pack` 行 == `CAPABILITY_PACK_IDS`（**双向**） | 常量从此接在基线正文上 |

## 4. 落点与依赖方向

- `CAPABILITY_PACK_IDS` 由 `registry.mjs` **导出**；`baseline.mjs` 已在 import `RELEASE_LINES`，
  再加一项即可，**不引入新依赖边**（`registry.mjs` 不 import `baseline.mjs`，无环）。
- 断言并入 `reconcile` 的第 ④ 区块（前三块分别是 §57.3 自洽、§57.3↔在册、§48.5↔在册），
  于是既有的 `against()` 助手与全部既有用例**自动带上它**，`engineering_checks` **零改动**。
- Rust 侧**零改动**。

## 6. 门槛与显式不做

- 门槛：`cargo xtask check --profile full` 必须绿；两条 `openspec validate` 必须绿。
- **不做**：把 §51.3 的行归属写进 `tests/registry.yaml`。registry 记的是**发布线**，
  而「属于哪个能力包」是 §51.3 的内部结构；把后者搬进 registry 会产生**第二个写下来的地方**，
  正是本轮要消除的东西。
