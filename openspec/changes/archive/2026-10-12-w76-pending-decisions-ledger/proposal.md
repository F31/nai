# 提案（w76 待裁定台账：悬空的问题也要有寿命）

## Why

基线有**四章**「待决策与待确认」（§18.2、§39.7、§48.7、§57.5），它们是一条**累积链**——
§39.7 沿用 §18.2 全部，§48.7 沿用 §39.7 全部，§57.5 沿用 §48.7 全部。去重后共 **34 条**。

这 34 条目前只有**载体**（散在四章里），没有**台账**。后果与 W73 发现的形状契约问题同型：

1. **「待裁定」读起来像「无人负责」。** 没有状态、没有依据、没有闭合条件 ⇒ 无法回答
   「哪几条其实已经有答案」「哪几条卡在什么上」「哪几条只是等外部事实」。
2. **已经有答案的条目会一直悬着。** 逐条核实发现 **4 条已由基线自身回答**：
   MCP `sampling`（§46.2）、上下文利用率观测线（§41.4）、`a2a` 契约名（§46.5）、
   能力包打包粒度（§51.3）。它们留在「待裁定」里，等于把**已决议**的东西重新打开。
3. **外部条件没有闭合条件。** §52.1 的硬门槛是「书面确认」——取不到就是取不到，
   但「取到什么算闭合」没写下来，于是它可以无限期地既不算完成也不算失败。
4. **前置项指向空气。** 「阈值三件待 §47.2 实测」是有效的；但同类条目若写成
   「待后续处理」，没有机器可判定的前置，就退化成了注释。

**这不是新机制，是给既有事实一个可判定的载体**——与 W72 的 `baseline_deviations` 台账、
`baseline.mjs` 对账是同一个模式：**登记解决「可以说清」，不解决「按什么顺序做」；
台账把前者变成后者。**

## What Changes

1. **新增 `tests/pending-decisions.yaml`**：34 条唯一待裁定项，每条有
   `introduced_in`（首次出现处）、`also_in`（复述处）与一个**封闭枚举的处置**。
2. **新增 `scripts/contracts/pending-decisions.mjs`**：纯函数 `validatePendingDecisions(ledger, deps)`，
   deps 显式注入（基线文本、验收 id 集合、工作项编号集合）——**缺任一项时判据必须失败**，
   MUST NOT 因为入参缺失而恒真（W72 对 `normalizeDeviations` 的同一条纪律）。
3. **五态处置**，每态对应**一个必填字段**：
   | 处置 | 必填 | 含义 |
   | --- | --- | --- |
   | `answered_by_baseline` | `basis` | 基线正文已给出答案；`basis` 里的 `§NNN` MUST 真实存在于基线 |
   | `decidable_in_repo` | `recommendation` | 仓库内可裁定，且给出推荐 |
   | `needs_precondition` | `precondition` | 需前置；每个前置 MUST 是**真实存在**的验收 id 或工作项编号 |
   | `needs_external` | `closure` | 需外部事实；MUST 写「取到什么算闭合」 |
   | `out_of_scope` | `note` | 明确不在本方案范围内（基线自述），同样要写下理由 |
4. **覆盖性逐章写死**：基线四章的「新增条数」写成常量表（§18.2 = 10、§39.7 新增 = 10、
   §48.7 新增 = 11、§57.5 新增 = 3，累计唯一 = **34**），台账少一条即失败。
   **照抄基线某张表的常量，必须另有一条把表逐项写死的断言**（W66 教训）。
5. **断言并入既有 `tests/registry.test.mjs`** ⇒ 随 `check --registry` 一起跑，`engineering_checks` 零改动。
6. **附带修复（阻塞本轮门控的既有缺陷）**：`crates/nai-runtime/tests/common/mod.rs` 的
   `open_store`／`provision` 复用产品侧**唯一**的 `nai_runtime::BRINGUP_OPERATION`，不再自造 5 s 副本。
   夹具做的正是「全新数据根 + 全链迁移」——那是 **bring-up** 的工作量，此前却被套进一份**逐次调用**的
   预算；默认并行跑下多个数据根同时建，输掉磁盘竞争的迁移就以随机的 `DeadlineExceeded` 冒出来。
   这是 **W75 §八第 9 条登记的遗留在本机复现**（W75 只在 CI 上见过它），且与 W70 在产品侧修过的是
   **同一族**问题，根因同样是「预算与工作量不匹配」。
   **为什么这不是「放宽断言」**：失败发生在**测试前置准备**（`Store::open` 与批量 `set_permission`）
   上，**不在被测路径**上——`--test-threads=1` 能过恰恰证明它是并发争用（而 W70 §3.2 已明确否决
   「靠串行」与「只在夹具里等」两种处置）。修法是把**已经存在**的那份定义拿来用，而不是新造一个数。

## 范围

外加**一处测试夹具的预算**（What Changes 6，不改任何产品代码）。
**不改基线正文**（§48.7 与 §57.5 是**版本专属陈述**，按 §56.2 情形③保留原文；
关闭已答项只发生在台账与 ADR 里，进入基线要等一次升基线轮次）。
**不改任何 `acceptance`、不改 schema、不改产品 Rust、不新增 xtask 步骤、不新增契约名**（§46.5）。
