# 设计 · W80 待裁定台账的引用完整性

## 1. 问题：一条断言的两个洞，形状相同

W76 的判据「引用 MUST 可解析」是对的。洞不在断言本身，在**它的覆盖**：

| 洞 | 形状 | 危险方向 |
| --- | --- | --- |
| **字段级** | 扫描域手写三个字段 ⇒ `recommendation`／`closure`／`note` 整片漏扫（17 条引用） | 新增/复述处的引用**永不被解析** |
| **表级** | `REQUIRED_FIELD` 与 `DISPOSITIONS` 无一致性约束 | 新增处置会**没有必填字段**地通过 |

两者是同一个病因：**一份会漂移的手写清单**。字段级的清单写死在循环里，表级的清单根本没写。
所以修法不是「再补三个 `sectionRefs(...)`」，而是**把清单变成单一来源 + 让清单本身被断言**。

## 2. 决策

### 决策 1：扫描域取一份**导出的**单一清单

```js
export const CITATION_FIELDS = ['basis', 'introduced_in', 'also_in',
                                'recommendation', 'closure', 'note'];
export const ID_LIST_FIELDS = ['precondition'];   // 承载 id，不承载 §NNN
```

引用扫描**遍历 `CITATION_FIELDS`**。导出它有两个理由：①判据可以直接断言它**逐字**含哪些字段
（钉内容，不只是关系）；②它是「有哪些字段会被扫」的**单一回答**——与 `AJV_SOURCES` 对
「有哪些 schema」是同一形状（W72）。

**为什么 `note` 也在里面**：`note` 不是 `out_of_scope` 的专属字段——实测有 5 条 `note`，
其中 4 条挂在**别的**处置上（PD-23／PD-26／PD-27／PD-30 是注解）。它承载 4 条 `§` 引用。
⇒ **扫描按「字段是否存在」触发，不按「处置是不是 out_of_scope」触发**——后者会漏掉注解型的 `note`。

### 决策 2：错误具名到字段

原来报 `${id}: references §${ref}, …`。同一个 `§99.9` 若在多个字段里出现（如同时改坏
`recommendation` 与 `closure`），措辞无法定位是**哪一处**。改为**条目 + 字段 + 章节号**三件齐：

```
PD-24: recommendation references §99.9, which does not exist in the baseline
```

**这不只是「更精确」**：W79 已立过一条同型的裁定——*错误的措辞会把定位引向错误的方向*。

### 决策 3：校验器自身的两张表必须互相一致

新 `shapeErrors()`（导出，并被 `validatePendingDecisions` 无条件并入返回值）：

1. `REQUIRED_FIELD` 的键集 MUST **等于** `DISPOSITIONS`（双向：少了会「无必填字段」，
   多了会「为一个不存在的处置定义字段」）。
2. `CITATION_FIELDS ∩ ID_LIST_FIELDS` MUST 为空（一个字段不能既是引用域又是 id 域）。
3. 每个处置的必填字段 MUST ∈ `CITATION_FIELDS ∪ ID_LIST_FIELDS`
   ⇒ **新增处置的字段不可能在两个检查之间落空**。

**为什么这不算「自检的装饰」**：它挡的不是「常量表写错」这种一次性错误，而是**未来某次合法编辑**
（加一个处置）导致的**静默失去覆盖**——那正是 W73「假契约」与 W66「悄悄删字段照样绿」的同一族形状：
**断言还在，覆盖没了，且没有任何信号。**

### 决策 4：非空洞注入必须**字段级**逐个开火

只验「`recommendation` 的坏引用会被抓」不够——要**每个**此前未扫的字段各来一次，且**要求指名该字段**。
另外，表级那两条要**真的把清单改坏**来验证：把 `CITATION_FIELDS` 换回旧的三个字段，
`shapeErrors()` 必须指出 `note`（`out_of_scope` 的必填字段）失去了覆盖。

## 3. 不改什么

- **不改台账数据**（`tests/pending-decisions.yaml`）：本轮是「让既有 17 条引用**开始被核**」，
  不是改它们。实测 17 条**全部已可解析** ⇒ 基线**保持全绿**（这正是「本轮不引入红」的判据）。
- **不改基线正文、不改任何 Rust、不新增依赖边。**
- **不与 `baseline.mjs` 的引用检查合并**：那边的域是 §48.5／§51.3／§57.3 的**表格**，
  这边是台账的**字段**；两者共享的只有 `sectionRefs` 这个正则本身（已复用）。
