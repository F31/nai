# 设计

## 1. 为什么是 `pending`，不是 `not_applicable`

映射段的回填规则写的是：**「本 profile 未启用或尚未开始的目标标 pending/not_applicable」**。
M01–M18 属于哪一类，取决于它们是「不在当前 release 范围内」还是「在范围内但还没开始」。

基线给的是后者：§1.4 的 R1 行与 §16 都**明写** R1 包含 `M01–M07、M13–M16、M18`，R2 包含 `M08–M12、M17`。
即这些验收**是 R1/R2 的退出条件**，只是对应工作项（W26–W40）尚未动工。这正对映射规则里
「**尚未开始**的目标标 pending」那一支 ⇒ 全部 `pending`。

> 对照：`X01/X02` 是 `not_applicable`，因为它们属「Lite-Mobile 未立项」——**不在当前 release 范围**。
> 二者的区别是「在退出条件里、但没做」与「不在退出条件里」，不是「做了没有」。

## 2. 为什么必须扩 id 家族白名单，而不是复用别的前缀

`scripts/contracts/registry.mjs` 的 `ID_RE` = `^(S|R|A|B|O|P|X)[0-9]{2}$`，`M` 不在其中。
把 M01 记成别的家族（例如塞进 A 或 O）是**改写基线的编号体系**——基线 §16 说这是
「唯一的验收编号体系」，M 是其中一个家族。故正确做法是**扩白名单**，而不是迁就校验器。

顺带：这一条与 W31 的教训同形——那次有人想把 B01 拆成 `B01a/B01b`，被同一个正则挡住；
正则要求**恰好两位数字**，本次只扩**字母家族**，不含位数，故拆分仍被拒。

## 3. `automation` 与 `contract` 的口径（防止把规划读成结论）

- `automation` 是 schema 的**必填**字段，且设计 §16 要求每条验收登记「是否自动化」。
  对未开始的条目，它只能是**规划意图**（按用例的性质推断：纯校验/审计 ⇒ unit，跨进程 ⇒ integration，
  并发/降级 ⇒ fault，一致性套件 ⇒ contract，界面 ⇒ ui）。**这不是测得结论**，
  已在每条 notes 末句与 `tests/registry.yaml` 的家族注释里写明。
- `contract` 在 schema 中是**可选**的，规格的措辞也是「所属契约（**如适用**）」。故只在 §37.4
  为该能力命名了契约时填：
  - 技能生命周期/调用类（M01–M03、M05–M08、M11）⇒ `skill.invoke@1`（§37.4：R1 冻结）
  - 数据接入类（M04）⇒ `data.query@1`
  - 设备类（M09）⇒ `device.control@1`
  - 市场客户端类（M13–M18）⇒ `market.catalog@1`
  - **M10（离线包安装与签名校验）、M12（授权过期自动停用）留空**：§37.4 未为这两个流程命名契约，
    不臆造归属。

## 4. 家族守卫的边界：只钉 M，不写通用解析器

「注册表覆盖全部家族」若做成通用检查，需要解析设计文档的表格，脆弱且易误报。
本轮改动的触发点是一个**具体缺口**，故守卫也**具体**：`tests/registry.test.mjs` 断言
M01–M18 全部在册。这既修好当前缺口，又防止它再次发生；至于「通用齐全性检查」，
等第二个家族真的出现同类缺口时再评估——**不为假想的通用性付复杂度**。

## 5. 与 ADR 0042 的关系

ADR 0042（V3.6→V3.7 基线切换）**明确声明不追认 M01–M18 已进入验收范围**，只裁决基线版本。
本变更是那条声明所指向的**后续动作**：把「注册表不完整」这一独立缺口单独修掉。
两者边界清楚——ADR 0042 管「基线是哪一版」，本变更管「注册表是否列全」。
