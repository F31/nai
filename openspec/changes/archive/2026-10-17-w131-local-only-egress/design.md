# Design: W131 — S10 子句一「`local_only` 不外发」

## 缺口（逐项现测，MUST NOT 由「同族」推断）

基线 `docs/直播数字人 + 智能体系统技术方案 V3.11.md`：
- 行 **89**（INV-17）：「数据外发范围……受 `local_only` 约束」
- §**281**：「标记 `local_only` 的文档**只走本地词法检索或人工**」
- §**563**：「上传范围」受 `local_only` 约束
- §**13.2**：「`local_only` 数据不上传」

| 子句 | 现测 | 证据 |
|---|---|---|
| ① `local_only` 不外发 | **零落点** | 全仓 `grep -rn local_only --include=*.{rs,ts,mjs,json,yaml}` 只命中 registry 自己那一行 |
| ② 画像默认关闭 | **已建** | `evaluate/memory.rs` 行 189–222：`allowed_viewer_fields`/`forbidden_sensitive`/`max_retention_ms`/`max_content_chars` 四项**都在 `admit_write` 里真执行**（不是只声明） |
| ③ 撤销与删除按期限清除 | **已建** | `ForgetTrigger::ALL` 含 `Ttl`；`revoke_knowledge` + `purge_memory_body` 已接线 |

⇒ 本轮范围是**子句一**。registry notes 里「`local_only`……已实现」是不实陈述，本轮订正。

## 关键设计决定

1. **标记落在文档级**，不是 kb / 会话 / 全局开关。§281 的原文主语是「标记 `local_only` 的**文档**」；
   做成全局开关就答不出「哪一份不能外发」，清单也就无从谈起。
2. **独立的列**，不复用 `acl_ref` 或 `product_scope`。那是两个不同的事实（访问控制引用、产品域）。
   把 `local_only` 塞进其中任何一个，就是让一格记两件事——读的人无法分辨手里那个值说的是哪一种。
   同一件事 MUST NOT 两处定义，两个不同的事 MUST NOT 挤进同一个字段。
3. **`NOT NULL DEFAULT 0`，不是可空三态**。`local_only` 是一个**二值事实**（是 / 否），没有「未知」这一格；
   导入入口 `ImportedDocument.local_only` **必填**，所以每一条新写入都必须表态。可空会把「未标记」
   与「不知道」混为一谈，而后者在这里不存在。
4. **不改 `0001-foundation.sql`**。`verify()` 逐文件核对已应用迁移的 SHA-256，改 0001 会让每一个
   既有库的校验和漂移。与 0008 / 0009 同一个理由。
5. **判定面不带 policy 参数**。「文档上传是否被允许」是 `RemoteGateway::sync` 的
   `allow_document_upload` 判定。同一个能力开关答两次会漂移（W88 / PD-31：读取面 / 写入面 / 准入面
   共用一处判定），所以本面只回答**标记**问题，不替 `sync` 再答一次策略问题。
6. **不引入新的条数上限**。可外发集合的规模由快照自己的名册上限界定（`MAX_SNAPSHOT_DOCUMENTS`），
   这里再造一个数就是同一件事的第二处定义，而且那个闸门**不可能开火**（域里永远到不了界）。
   一个永远开不了火的守卫是装饰，不是判据。
7. **判定单元是 `(document_id, revision)`**，不是 `document_id`。同一个文档的两个修订是两份东西；
   「同名」≠「同一个」。重复身份**被拒**而不是被计数两次——计数正确不等于清单正确。
8. **存疑取值选不放行那一边**。列上是 `INTEGER`，SQLite 不把取值限死在 0/1。只有 `0` 是「未被标记」，
   任何其它值按**被标记**读：外发是危险方向。
9. **判定输入从存储读出**，MUST NOT 由调用方给——调用方给不了、也改不了那份上传范围。

## 副作用与风险

- **老行一律读到 `0`。** 它的含义是「**从未被标记**」（升级时点的历史事实），
  **不是**「已核实这份文档可以外发」——后者是一个没有人做过的核对，MUST NOT 被写成前者的同义词。
  写进迁移文件注释、写进 `version_ten_upgrade_...` 用例、也写进轮次报告。
- **不外发 ≠ 不可检索。** §281 的原话是「只走本地词法检索或人工」。只钉住前半（被扣留）的判据，
  会让「扣留」在实现上退化成删除——删掉一个文档当然也不外发，但那是另一个（错误的）实现。
  所以正向半 MUST 与反向半同批落地，且用**真实 FTS5 存储**钉住：夹具走 `split_document` + `tokenize`
  真实路径，MUST NOT 用 `synthetic_chunk` 那种按尺寸手搓的块——后者的 `tokens` 是 `t0` 这种占位值，
  于是断言会在**夹具**上失败，而不是在被断言对象上失败。
- **链条的最后一环未闭合。** `remote_egress_targets` 是一份清单生产器，`sync` 的入参没有被强制接它。
  本轮只闭合了「存在一份按存储读出的清单」，**没有**闭合「外发一定经过这份清单」。具名登记，不修。
  （另：`sync` 在仓库里零生产调用点，只有测试调用，与 d09 报告「真实远端 Blocked」一致。）

## 覆盖：注入验证暴露的一处判据退化

注入验证跑到「域 = 活动快照」这条 JOIN 时发现：**没有任何既有用例能走到它那一层**。
原因是既有两次发布的用例里文档修订都变了，旧快照的行被 `s.revision=d.current_revision` 天然挡掉，
于是那条 JOIN 当次**无覆盖**，怎么改都不会红。

⚠️ 这是 W127 记下的第二种成因「注入不变红 ≠ 注入坏了」，但方向不同：这里不是判据被更早的闸门短路，
而是**判据根本没有覆盖那一层**。处置是**补能走到那一层的输入**，不是改判据：
- `the_release_domain_is_the_active_snapshot_not_any_snapshot_ever_published`：
  同一文档在两个快照里、修订未变 ⇒ 去掉活动 JOIN 会得到 `duplicate_document` 而红。
- `a_document_outside_the_queried_scope_is_outside_the_release_domain`：
  两个 `kb_scope` 各有活动快照 ⇒ 去掉 `a.kb_scope=?2` 会红。

两条红的是**不同的用例** ⇒ 两条域判据互不顶替。
