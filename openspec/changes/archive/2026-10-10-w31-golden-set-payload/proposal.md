# W31：黄金集载荷载体与就位门禁（B01 机制侧收口）

## 为什么

W30 把 §6 的质量门槛与 §5.9 的黄金集生命周期落成了 `crates/nai-kernel/src/golden.rs` 里的可执行判据，但**题集本身从哪里来**没有落点：

- §30.1 把「RAG 黄金」指定为一个测试类，目录写作 `tests/rag-golden` —— 该目录此前不存在；
- §6 要求「至少 100 个贴近真实直播的问题」，但整条门槛标注为**（设计值）**，且未指定由哪个系统生成这些题；
- §5.9 把黄金集列为**场景包字段**，并规定被改写或驳回的候选**经人工确认后**才可入集。

于是「100 题黄金集未建」在执行上等价于「什么都可以不做」。本变更给出一处**机器可寻**的位置、一份**结构规范**与一道**就位门禁**，并把三种结论——「合规」「未提供」「缺陷」——分开报告，使任何一者都无法替另一者背书。

本变更**不产生**任何题内容。构造题集会让人把构造出来的题误读成质量水平，因此题集由场景包产出方按场景填入。

## 变更

- 新增 `schemas/rag-golden/case-set.schema.json`：题集结构规范。
- 新增 `tests/rag-golden/README.md`：位置与产出方声明（三条来源、格式、校验口径、当前状态）。
- 新增 `xtask/src/golden.rs`：载荷读取、结构审计与就位门禁，复用 kernel 的 `GoldenSet`/`audit_coverage`（不复制判定逻辑）。
- 新增命令 `cargo xtask check --golden [--dir <目录>]`。
- 新增夹具 `tests/fixtures/rag-golden/example-min.json`（构造的最小集，用于验证加载器本身，**不是**真值）。
- `xtask` 新增 `nai-kernel` 依赖（tool 层，依赖方向不变，`check-deps` 仍为 18 包）；外部依赖**零新增**（复用已有的 `serde_json`）。

## 影响

- **能力**：`knowledge-quality-gate` 增补四条需求（载荷位置与修订、未提供与失败的区分、载荷边界上的确认人、缺陷全量报告）。
- **状态**：`tests/registry.yaml` 中 B01 由 `implemented` **回调为 `blocked`**，理由是 §655 的验收原文为「知识质量：100 题集**达到**第 6 章门槛」——这是实测达标，题集不存在时不可能达成。已交付的判定机制与载体在 notes 中完整保留。
- **不纳入** `check --profile portable`：题集内容不属于工程基础门控。

## 否决方案

- **新增 B01a/B01b 编号**：registry 的 id 正则要求恰好两位数字（`^(S|R|A|B|O|P|X)[0-9]{2}$`），拆分会直接使 `check --registry` 失败；且等于改写规格 §655 的验收口径，超出本仓库的授权。
- **把题集写进 crate 常量**：题集是数据不是代码，规格指定的位置是 `tests/rag-golden`；写进 `crates/` 会让「逐场景各一份」无处安放。
- **用 YAML 存题集**：`xtask` 只有 `serde_json`，引 YAML 需新增外部依赖；仓库既有的 YAML（`tests/registry.yaml`）由 Node 侧读取，Rust 侧无先例。
- **在 xtask 里重新实现判定**：分位与覆盖审计已在 kernel，复制会产生两个真相。
- **把就位门禁并入 portable**：会让工程基础门控因「业务题集未建」而变红，混淆两类不同的缺失。
- **造一份 100 题的示例载荷**：那是臆造真值，会让人把构造数据读成质量水平。
