# w88 设计：第六态与落地点

## 问题形状

W76 的台账用**一个封闭枚举**回答「这条待裁定项属于哪一类」。五态回答的是**「何处能闭合」**：

| 处置 | 闭合发生在 |
| --- | --- |
| `answered_by_baseline` | 基线正文已经回答了它 |
| `decidable_in_repo` | 仓库内可以决定它 |
| `needs_precondition` | 等某个前置 |
| `needs_external` | 等外部条件 |
| `out_of_scope` | 不在本方案范围 |

这五态**都是「还没闭合」**（`answered_by_baseline` 是「已被闭合」，但它说的是
**基线**闭合了它）。⇒ 一个「**仓库已经作出决定并已落地**」的条目**无处可去**：
它只能永远停在 `decidable_in_repo`，而那个状态的名字叫「可决定」，不是「已决定」。

`PD-09` 实测就是这个形状。核实它到底落在哪：

| 子句（PD-09 的推荐） | 仓库事实 | 判据 |
| --- | --- | --- |
| 按目标平台各用系统密钥库 | `NativeVault`（`keyring`） | `crates/nai-security/src/lib.rs` |
| Windows 原生凭据为首发实现 | `keyring` 只在 `cfg(windows)` 下引入 | `crates/nai-security/Cargo.toml` |
| 缺该后端的平台如实登记 `explicit-unavailable` | `linux`/`macos` = `explicit-unavailable`（`not_ported_to_target_os`） | `schemas/platform-matrix/platforms.json` 的 `secret-protection` 行 |
| MUST NOT 自造跨平台密钥库 | 没有这样的东西 | 同上（无落地点即为此条的证据） |

四条子句全部成立 ⇒ 推荐**已被采纳并落地**，但台账里没有表达这件事的位置。

## 决策

1. **「决定已作出且已落地」是第六类，MUST NOT 写成别的处置的注解。**
   两条排除的理由都是**判据级**的、不是措辞级的：
   - 写回 `decidable_in_repo`：该处置的语义是「**可在仓库内决定**」，而条目已经决定了。
     台账读起来会说「还等人决定」，这是**不实**，不是「措辞不够好」。
   - 写成 `answered_by_baseline`：该处置断言「**基线正文回答了它**」，而 PD-09 恰恰相反——
     基线 §11.5 明写「（**具体机制待选型验证**）」⇒ 把 PD-09 记作 `answered_by_baseline`
     是一条**不实声明**。⇒ 排除。

2. **第六态的必填字段是「落地点」（`landing`），不是「决定文本」。**
   与 `answered_by_baseline` 用 `basis`（**答在哪一节**）而不是「答案原文」是**同一条纪律**：
   台账钉「**管到哪**」这个可判事实，内容的语义是否真的落地**刻意留给人读**（ADR 0054 决策 2）。
   决定的内容另有其家：ADR 与报告。⇒ 一个必填字段，六态对称。

3. **落地点 MUST 是仓库**已跟踪**的路径**，判据的输入是 `.git/index`（W75 的 `git-index.mjs`）。**
   为什么不用工作区清单：那是 W75 的 **F2 根因**——未跟踪文件会被算成仓库成员。
   本轮把它做成**直接**的回归守卫：探针以 `node_modules` 为样本（磁盘上存在、索引里没有），
   `readdir` 的实现会放行它，`git-index` 的实现会具名拒绝。
   为什么不用作业项编号（`W55`）：实测基线的工作项表**不含 W41–W55**（§47.6 的编号说明：
   V3.7 计划止于 W40，W41–W44／W46–W55 由后续实际执行轮次占用，第四部分从 W56 起编号）
   ⇒ PD-09 的落地轮次**无法作为 `W\d{2}` 解析**。路径则恒可判。

4. **新增第三类检查类别 `REPO_PATH_FIELDS`，MUST NOT 把 `landing` 塞进 `ID_LIST_FIELDS`。**
   两者虽同为「必须解析得开」，但**解析器不同**（登记 id vs 仓库成员路径）⇒ 归两类
   （W66「不合并不同维度」）。四类 MUST 两两不相交、且并集恰等于 `LEDGER_FIELDS`——
   `shapeErrors()` 的两条断言随之从三扩到四。

5. **「清单型 / 文本型」由类别表决定，MUST NOT 写死字段名。**
   原实现把「清单型 / 文本型」写成 `field === 'precondition'`（由**写死的字段名**决定）。
   W88 实测（真跑改前那一行）：

   | 注入（`PD-09.landing` 给成**字符串**，值是一个**真实存在的跟踪路径**） | 校验结果 |
   | --- | --- |
   | 改前（`field === 'precondition'`） | **0 error** —— 当文本判，「非空」即过关 |
   | 改后（`idListFields ∪ repoPathFields`） | **1 error**：`requires a non-empty landing` |

   ⇒ 写死的字段名在**新增一个清单字段的那一刻就说谎**（W83 同族：清单的补集是盲区）。

6. **路径解析 MUST 按「字段是否存在」触发，MUST NOT 按处置触发**（W80／W83 的既有纪律）。
   把 `landing` 挂到 `needs_external` 的条目上、值不可解析 ⇒ MUST 具名失败；
   值**可解析** ⇒ MUST NOT 红（拒绝的是**不可解析**的引用，不是**放错位置**的引用）。

7. **台账**不是**重分类为「全绿」**。`recommendation` 原文保留在 `PD-09` 上：
   它就是**被采纳的那份建议**，删掉就丢了「决定了什么」。它是注解性的留存，
   本态的**必填**字段仍是 `landing`。

8. **不引入 `tests/pending-decisions.schema.json`**（W76 §遗留 5 预留的判定：等第二次结构变更再判）。
   本轮**正是**那次结构变更（6 态 + 1 字段 + 1 类别 + 1 依赖）。判定为**不引入**，理由：
   校验器已经用**闭世界**（条目键集、信封键集）+ 枚举 + 类别划分把形状钉死；
   再写一份 JSON Schema 会在**同一件事上出现第二处定义**（W86 的教训）——
   两份定义会在某一次合法编辑后**静默分家**，而校验器那一份才是接上电的。

## 假阳性方向（必须证明「不该红时不红」）

- 可解析的落地点出现在**非** `decided_in_repo` 的条目上 ⇒ **不红**（决策 6）。
- 台账里 `recommendation` 保留在 `decided_in_repo` 条目上 ⇒ **不红**（决策 7；闭世界按**键集**判，
  多一个**已声明**的键不是错误）。
- 迁态后总数仍 **34**、分章计数不变 ⇒ 只有 `DISPOSITION_COUNTS` 移动一格（决策 1）。

## 非空洞注入（实测）

F0 干净台账零错误；F1 不存在的路径具名；F2 磁盘上存在但**未跟踪**的路径具名；
F3 把 `landing` 移出 `REFERENCE_FIELDS` ⇒ 同一个坏值**静默**（证明这条检查承重）；
F4/F5 见决策 5 的改前/改后对照；F6 反向注入不红；F7 跟踪集非空（1014 条）。
