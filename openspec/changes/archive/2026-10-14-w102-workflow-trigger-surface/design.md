# w102 设计

## 一、问题形状：**前提**从来不是判据

前十一轮补的是「workflow **里面**」的层。而「**这个 workflow 什么时候会跑**」是它们**共同的前提**：

```
on:                                  ← 不在任何判定域内
  push:
  pull_request:
jobs:
  foundation:
    steps: [门控步, 8 个判定步, 诊断步]   ← W95/W96/W97/W99/W100/W101 全部在这里工作
```

W95 的步层闭世界问「这一步在不在册」；W100 问「它在哪个平台跑、跑不跑」；W101 问「它跑的是哪个目标」。
**没有一条问过「这个 workflow 会不会被跑起来」。** 于是：

- 删掉 `pull_request`（P-C）⇒ PR 不再进门控，所有步层判据**全绿**；
- 把整个 `on:` 缩成仅 `workflow_dispatch`（P-D）⇒ push/PR 都不再触发，**全绿**；
- 把 `push` 限定到一个**不存在**的分支（P-E）⇒ push 事实上不再触发，**全绿**。

这不是「漏了一个字段」，而是**前提从未被建立为判据**。仓库里只有散文（`AGENTS.md:651`、
`docs/development-plan.md:541`：「workflow 有 `on: push`，每次 push 都已自动触发」）。

## 二、证据（探针，改真文件 + 真跑 + 逐字节还原 + `sha256` 逐字一致）

10 个 portable 套件 = registry / schema / platform / workflow / xtask-commands / gate-coverage /
npm-scripts / tier-payment / step-config / step-target。基线 `245 passed / 0 failed`。

| 探针 | 改动（真改 `.github/workflows/foundation.yml`） | 失败向量（10 套件） | 读它的人 |
| --- | --- | --- | --- |
| P-A | 诊断步读方改路径（`nai-gate.log` → 别的名） | `[0,…]` **零信号** | 无（⇒ §八 遗留） |
| P-B | 门控步写方改路径（`tee` 目标改名） | `[0,…]` **零信号** | 无（⇒ §八 遗留） |
| P-C | 删掉 `pull_request`（PR 不再被门控） | `[0,…]` **零信号** | 无 |
| P-D | 整个 `on:` 缩成仅 `workflow_dispatch` | `[0,…]` **零信号** | 无 |
| P-E | `push` 限定到一个不存在的分支 | `[0,…]` **零信号** | 无 |
| P-F | `tee` 目标换成 `/dev/null`（日志消失，诊断步读不到） | `[0,…]` **零信号** | 无（⇒ §八 遗留） |

P-C/P-D/P-E 是本轮**要治理**的零信号向量；P-A/P-B/P-F 是另一条缝（**跨步数据传递**的写方 ↔ 读方
是两处独立字符串），本轮**登记为 §八 遗留**——「一条待裁定项只在本轮裁一个」，同时裁两条会让
判据的边界与证据都变糊。

### 解析事实（`yaml` v2.9.1，实测）

| `on:` 写法 | `YAML.parse(text).on` | 说明 |
| --- | --- | --- |
| `on:\n  push:\n  pull_request:\n` | `{push: null, pull_request: null}` | 映射（裸事件 ⇒ `null`） |
| `on: push` | `'push'` | 字符串 |
| `on: [push, pull_request]` | `['push','pull_request']` | 数组 |
| `on:\n  push:\n    branches: [main, release]\n` | `{push: {branches: ['main','release']}}` | 带过滤器 |
| `on: {}` | `{}` | 空 ⇒ 永不触发 |
| （`on:` 缺失） | 键**不存在**（`hasOwnProperty` 为 `false`） | 永不触发 |

⚠️ **`on` 是字符串键，不是布尔 `true`**（`yaml` v2 默认 YAML 1.2 core schema，实测 `Object.keys(doc)`
为 `['on']`）——因此 `doc.on` 可靠，不需要防御 `doc.true`。

## 三、设计决定

### 决定 1：在册表 `WORKFLOW_TRIGGERS` 单独一份，**不**塞进 `WORKFLOW_STEPS`

W101 决定 1 说「一个 step 的 `target` 住那个 step 自己的条目上，MUST NOT 另开一张表」——
那是**因为** target 是 *step 这个对象* 的属性。本轮的对象是**触发器**，不是 step：
它不是任何一个 step 的属性，而是**整个 job 集的前置条件**。⇒ 它有自己的在册表，
字段 `{host, event, kind, filters}`。

W101 的纪律在这里的正确形式是：**同一件事 MUST NOT 两处定义**——「这个 workflow 有哪些触发器」
只有 `WORKFLOW_TRIGGERS` 一处；解析出的集合与它双向对账，MUST NOT 在 step 条目上再声明一份。

### 决定 2：判定单元是 `(event, filter-key)`，MUST NOT 是裸 filter-key

`branches` 这个键在 `push` 与 `pull_request` 上语义相同但**归属不同对象**：
`push.branches` 与 `pull_request.branches` 是两个可分别篡改的过滤器。
若按裸键名比较，把 `pull_request` 的 `branches` 挪给 `push` **看不出差别**（W91：「同名」≠「同一个」）。
⇒ 单元 = `filterKeyOf(event, key) = `${event}\u0000${key}``，对账时按它建 `Map` 比较，
错误消息里同时带出 `event` 与 `key`。

### 决定 3：事件的**身份**是事件名；`kind` 由 `MANUAL_EVENTS` 表**推导**，MUST NOT 手写

`TRIGGER_KINDS = ['event','manual']` 是闭集（域外 ⇒ 具名失败，W90）。
但 `kind` **不许手写**：它 MUST 等于 `MANUAL_EVENTS.includes(event) ? 'manual' : 'event'`。
⇒ 「自动 / 手动」这件事**只有一处定义**（那张表），改前/改后都要真跑。
手写 `kind` 是**同一件事的第二处定义**——它一定会与表漂移，而且漂移的方向恰好是
「一个手动触发被当成自动触发」⇒ **假阴性**，最危险。

`MANUAL_EVENTS` 的取值由**实测语义**决定（不是「看起来合理」）：一个事件若**不能**
由仓库自身的推送／PR／定时等事实驱动，就是 manual。实测三个：
`workflow_dispatch`（人点按钮）、`workflow_call`（另一个 workflow 调）、`repository_dispatch`（外部 API 调）。

⚠️ **「不存 `kind`」这条决定的兑现物是字段集闭世界**（探针 P-B5 逼出来的）：`kind` 不写，但
**判据也不读它** ⇒ 于是给一个条目**手写** `kind: 'automatic'` 时判据**一个字都不说**。
那不是「少报」，而是**一条没人会读的声明静静地挂在表上**——写它的人以为它有意义，
甚至以为改成 `manual` 就改变了语义。这正是母题「**声明 MUST 付代价**」的反面。
⇒ 条目上的键 MUST **恰好**落在 `TRIGGER_FIELDS = ['host','event','filters']` 里，域外 ⇒ 具名失败
（错拼的 `filter`、多写的 `reason` 同理）。「闭世界 MUST 在每层成立」在这一层的落点就是**字段集**。

### 决定 4：R3「至少一条自动触发」是本轮**唯一**直接钉「前提」的断言，且必须**两侧都断言**

两个方向不重复：
- **在册侧** `automatic.length === 0` ⇒ 「在册表里一条自动触发都没有」⇒ 判据自身退化成恒真；
- **解析侧** `producedAutomatic.length === 0` ⇒ 「这个 workflow 事实上不会被任何仓库事件驱动」。

双向闭世界（R1）会让两者**在大多数情况下同真同假**，但**不是所有情况**：若把 `workflow_dispatch`
也补进在册表、同时删掉 `push`，R1 双向成立（解析出 `workflow_dispatch` 且在册）而 R3 的**解析侧**
仍然红——这正是 P-D 的形状。⇒ 两条都必要，MUST NOT 合并成一条。

### 决定 5：R2 过滤器双向对账——这是**假阴性**方向必须堵的洞

`push: {branches: [main]}` 与 `push: {branches: [nope]}` 在**事件层完全相同**（都只有 `push`），
所以只做 R1 是不够的：`branches` 决定了 push **是否真的会触发**，改成不存在的分支 ⇒
门控事实上不再跑，而事件集一个字没变（P-E 的零信号正来自此）。

对账 MUST 是**双向集合相等**，MUST NOT 是「声明 ⊆ 解析」：
- **施加了而没人声明**（P-E）⇒ 有人**悄悄地关掉**了触发；
- **声明了而没有施加**（把 `branches` 从 workflow 删掉）⇒ 声明是**空话**。

两个方向都具名，且**取值集合**也要双向（`[main]` vs `[main, release]` 具名）。
集合元素排序后比较——**顺序不是声明的一部分**。

### 决定 6：形状闭集切两刀——**解析侧只认形状，判定侧才认域**

`workflowTriggersOf` 只做**形状**归一化：`on:` 必须是字符串／字符串数组／映射三者之一，
事件的配置必须是 `null` 或是「值为**非空字符串数组**的映射」。**它不检查键名域**。
键名域（`FILTER_KEYS`）与 `kind` 域由**判据**检查。

为什么这么切（与 W101 的 `targetsOf`/判据切分同形）：解析器负责「读得懂／读不懂」，
判据负责「读懂了的东西合不合法」。把域检查塞进解析器会让一条笔误（`branch:` 少个 `s`）
把**整个触发面**判成「读不懂」——丢失粒度，也让错误消息说不清是哪种错。

若事件配置**形状**不合法（例如 `schedule: [{cron: …}]` 的取值是对象、`workflow_dispatch: {inputs: …}`
的取值是对象），解析器**抛**一个**具名**错误，判据把它转成一条具名失败——**域外 ⇒ 具名失败，
MUST NOT 静默降级**（本项目未使用这两类事件；出现即要求人显式处置）。

### 决定 7：判分由**在册条目**驱动，且不重复报别的判据已报的东西

`workflowTriggerErrors` 只报**触发面**的事。步集（W95）、执行配置（W100）、目标绑定（W101）
一个都不重复 ⇒ 只改 `on:` 时，那三个判据**必须沉默**（正交性由测试逐条断言）。

### 决定 8：缺输入 / 空注册表 / `on:` 缺失 / `on:` 空 / 事件重名 ⇒ **具名失败**

- `workflowText` 非字符串或为空 ⇒ 具名（不是 `[]`）；
- 在册表为空 ⇒ 具名（否则每条规则恒真）；
- `on:` 键不存在、值为 `null`、空映射、空数组 ⇒ 具名（「空触发面」＝永不触发）；
- 同一个事件名在 `on:` 里出现两次 ⇒ 具名（一个事件两个配置 ⇒ 没有单一回答）。

### 决定 9：**层级差**是本轮立论的核心——W100 与 W102 不可互推

W100 已经在「步」这一层判了「会不会跑」，但它的输入是 `job.strategy.matrix` × `step.if`
——**它读不到 `on:`**。一个 workflow 可以在**每个步上都「会跑」**，而整个 workflow **永不触发**。
⇒ 两层对象不同，不可互推。「已经被判过的」≠「这一层也被判过」。

## 四、边界（与相邻判据互不顶替；实测数字见报告 §五）

| 相邻判据 | 它问的问题 | W102 问的问题 | 是否顶替 |
| --- | --- | --- | --- |
| W95 步层闭世界 | 这一步**在不在册**、`kind` 是什么 | 这个 workflow **什么时候跑** | 否（改 `on:` 对 W95 全绿） |
| W99 站点层级 | 某站点**最低在哪一层跑** | 触发面**有哪些事件** | 否 |
| W100 执行配置 | 这一步跑不跑 / 在哪跑 | 整个 workflow 跑不跑 | 否（步 vs workflow，层级不同） |
| W101 目标绑定 | 这一步跑的是**哪个目标** | 触发面**怎么被触发** | 否（改 `run` 对本判据沉默） |

**层级差**是本轮的关键：W100 已经在「步」这一层判了「会不会跑」，但它的输入是
`job.strategy.matrix` × `step.if` ——**它读不到 `on:`**。一个 workflow 可以在每个步上都「会跑」，
而整个 workflow **永不触发**。⇒ 两层不可互推。

## 五、非空洞

三件事 MUST 分开证：

1. **闭集非空**：`TRIGGER_KINDS` / `MANUAL_EVENTS` / `FILTER_KEYS` 都非空，且三个取值域各有活实例
   （测试断言）。**实例数不钉**（W92 教训：一次合法的收敛不该让判据变红）。
2. **每条规则都有真样本**：合成世界 MUST 覆盖 —— 三种 `on:` 写法、至少一条**自动**与一条**手动**事件、
   **至少一个过滤器单元**（否则 R2 的对账对空集恒真）、`infra` 无关的多步 job 照旧能过。
3. **真实仓库诚实**：`foundation.yml` 的 `on:` 里**没有任何过滤器** ⇒ 真实仓库上 R2 的单元集合**为空**。
   这不是「判据装饰」，而是**在册数据恰好简单**：① 合成世界证规则非空洞；② 注入用例（P-E 形状）
   证规则**在真实文件上真的会响**。两件事都写进报告。

## 六、明确不做 / 如实披露

1. **不判事件配置**：`workflow_dispatch.inputs`、`schedule.cron` 不是「会不会自动触发」的开关。
   本项目未使用；出现即**具名失败**（域外 ⇒ 具名，W90），MUST NOT 静默放行。记入 §八。
2. **不判分支／路径是否真的存在**：那要读 refs，且宿主瞬态 MUST NOT 改变结论（铁律二）。
   本轮只钉「施加的过滤器 == 声明的过滤器」。
3. **不判触发面与 job 矩阵的关系**：那是 W100 的执行配置面。
4. **不判 `permissions:` / `concurrency:` / `env:`**：本轮的对象是**触发面**，不是整个 workflow 头部。
   它们是各自独立的一层，留给后续轮次（MUST NOT 顺手圈进来）。
5. **P-A/P-B/P-F 的缝（跨步数据传递写方 ↔ 读方）本轮不裁**：登记为 §八 遗留，
   连同实测的零信号一起记录，供下一轮裁定落点时兑付。
