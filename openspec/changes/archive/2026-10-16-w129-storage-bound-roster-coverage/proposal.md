# Proposal: W129 — 存储上限名册的行为覆盖（R08 剩余 11 项）

## Why
W125 冻结了 R08 的上限名册（约束「单次写入或单份快照/备份可占用资源」的上限共 **19** 项），
并把其中 **8** 项接上了载体，剩下 **11 项零覆盖**——W125 的 registry notes 逐字写着这件事，
并**具名**列出这 11 项。零覆盖的意思是：这些闸门**可以被删掉、被改成恒真、或把边界挪一格，
而没有任何一条测试会红**。名册管的是「上限是不是它自称的那个数」（幅度），它**不**管
「闸门还在不在、边界在哪一侧」（行为）。W125 自己指出了这个分工，本轮补的就是缺的那一半。

## What Changes
1. **12 个具名常量**（11 项 = 12 个条件，因为 ⑥ 是两个条件一个条目）：把散落的字面量提出来，
   让判据**引用**上限而不是复制字面量（W77 对 `Operation::CEILING` 的同一条规矩）。
   三条 `65536` 是**不同的对象**（配置文本 / 事实编码 / 候选编码）⇒ 三个常量，不共用一个。
2. **拆一处合并拒绝**：`store.rs` 的候选路径原先用一条 `if dependencies.len() > 32 || cue.encode_to_vec().len() > 65536`
   配一个拒绝名；现在拆成 `candidate dependency limit` / `candidate payload limit` 两条具名拒绝——
   否则绊到依赖条数的夹具会替候选编码的上限背书（与 W125 对 `publication` 的同一条规矩）。
3. **两处 SQL `LIMIT` 从上限派生**：撤销批次（`LIMIT 4097`）与快照 artifact（`LIMIT 513`）的
   读窗口改为 `上限 + 1`，并把那个 `1` 的含义写进注释：多读出来的那一行就是「后面还有」的证据。
4. **名册从 8 → 20 个常量**（19 项），并新增 **1 条名册闭世界判据**：`lib.rs` 的每个 `mod`
   都有被扫源文件（文件层）、每个顶格常量**恰好**归入三类之一（元素层，三分是划分）、
   三张清单上的名字都真的扫得到（反方向）。按清单扫的盲区恰恰是清单的补集。
5. **8 条行为边界判据**：每条上限一对夹具（**恰在界上必须过 / 越界必须具名拒绝**），
   夹具从常量派生——于是「抬高常量」**不会**让边界判据变红（那是幅度判据的职责）。

## Modified Capabilities
- `local-persistence`：配置文本、事实编码、候选依赖/载荷、待审批容量、快照文档数、
  托管文件数、撤销批次——每条上限的闸门与边界由具名拒绝钉住。
- `knowledge-pipeline`：一条候选的证据引用条数上限，且它 MUST 与候选编码上限**可分别归因**。
- `scheduling-and-budgets`：账本条目编码上限是**防御性**的（从被认可的路径走不到）；
  读回侧有两条独立闸门（已存文本长度、十六进制窗口），三条件逐个可归因。

## Impact
- registry：`R08` 的收尾判定**由证据决定**（19/19 是否足以升 `tested` 见文档阶段现测），
  MUST NOT 在本文件预先承诺。
- 生产代码：12 个常量提取 + 一处拒绝拆名 + 两处读窗口派生；**无取值改动、无 `ErrorCode` 改动**。
  唯一的语义变化是 ⑥ 越界时返回的 `reason` 从旧名换成更精确的新名（`ErrorCode` 不变）。
- 测试：`nai-storage` 63 → 72（+8 边界 +1 闭世界）。
