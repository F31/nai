# 设计：手机监控面的判定边界

- 基线：V3.7 §3.1（分层与 L5 职责）、§10.2（手机监控包）、§37.3（手机端启用状态与紧急停用）、§663（O03 验收）、§636 与 §86（S09 远程命令）、§742（手机只做监控管理）、§30.1（测试分层）
- 判据：`tests/registry.yaml` O03；回指 S09
- 承接：ADR 0034（写实准入 Gate）

## 背景

O03 的真值（M0b PoC 定路线、真机最小形态通过 S09）需要外部条件，本轮不可达。但 §3.1 L5 与 §10.2 的**判据**很明确，此前没有落点。要把它们落成代码，必须先回答：

1. 「不持有媒体时钟与密钥」靠黑名单挡还是靠投影？
2. 最小形态是哪几项，预览后置算不算缺陷？
3. 「它不是手机开播」怎么落成一条可判的规则？
4. 「预览按需…不得挤占正式出画」四个条件与被后置的预览是什么关系？
5. 「不宣称端到端加密」与「如实披露」怎么区分？
6. 路线未定案是缺陷还是状态？已声明路线的前置条件怎么表达？
7. 命令契约的字段齐备性与 S09 的网络行为是什么关系？
8. 审计会不会被判定函数架空？

## 决策

### D1 落 `crates/nai-kernel`（`monitoring.rs`）

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 放进 `nai-control-api`（loopback 控制面同住） | 与 HTTP 面一起 | **否决**：该 crate 是**传输**层（hyper/tokio、loopback），其文件头明确不做设备认证与预检；把纯判定放进去会让"越界面可判定"依赖一个网络 crate，且 kernel 无法复用。 |
| B. 放进 `nai-media-core`（与 `EmergencyHandle` 同住） | 贴近紧急静音 | **否决**：media 层禁止 http/provider 但也**不属于决策层**；监控面判定是策略，且会反向依赖 kernel 的报告词汇。 |
| C. 放进 `crates/nai-kernel` | 与 `golden.rs`/`realistic.rs` 同 crate | **采纳**：复用 `golden::Finding`（同一报告词汇），依赖方向不变。 |

### D2 「不持有媒体时钟与密钥」靠**白名单投影**，不靠黑名单

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 序列化整份状态后剔除敏感字段 | 黑名单 | **否决**：下一次给 `LiveState` 加字段（例如新增一个 token）就会默认流出；这是 L5 边界最典型的长期失守方式。 |
| B. 只写一份「禁止字段清单」常量 | 仍是黑名单 | **否决**：清单与真实字段之间没有结构性绑定，可以同时正确却失效。 |
| C. `MobileView` 结构上只含十个白名单字段，`LiveState` 的敏感字段在它之上没有落脚处 | 白名单投影 + 一致性断言 | **采纳**：`MobileView::field_names()` 与 `Exposure::ALLOWED` 的标签集合被断言一致，新增字段而漏登记即失败；`LiveState` 的禁止字段名与投影字段集合被断言不相交。 |

### D3 最小形态是**四项清单**，预览/推送后置不是缺陷

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 九项功能缺一即缺陷 | 全都要 | **否决**：§10.2 原文「最小形态：看板、审批、接管、紧急静音；预览与推送可后置」。 |
| B. 只报「不完整」不指名 | 一个布尔 | **否决**：不知道缺哪一项，修法不同。 |
| C. 四项为最小形态，缺项逐条指名 | `MINIMUM_FORM` 常量 | **采纳**。 |

### D4 「它不是手机开播」是**暴露类别**问题

把开播控制建为 `Exposure` 的**禁止类别**之一（`BroadcastControl`），与媒体时钟/密钥/原始音视频同族。这样「可以看状态」「可以下发命令」「不能开播」三件事落在**同一个词汇表**上，且与白名单投影共享一致性断言。

### D5 预览四条件**仅在启用时受检**

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 无论是否启用都检 | 一律检查 | **否决**：§10.2 允许预览后置；对一个**未启用**的特性报"不是按需开启"是把不适用读成不合规。 |
| B. 启用时检四项、未启用时不检 | 条件化 | **采纳**：四条件为按需、真正编码的低码率、关闭立即释放编码器与带宽、不得挤占正式出画。 |

### D6 中继终止 TLS 的**诚实披露**不是缺陷

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 只要用了中继就报缺陷 | 一刀切 | **否决**：§10.2 允许中继方案，只要求**不宣称端到端加密**。 |
| B. 只看是否宣称 E2E，不看协议 | 半条规则 | **否决**：§10.2 说「需要时使用经审核的端到端协议」，协议未审核的 E2E 声明同样不成立。 |
| C. 两条独立规则 | 中继终止 TLS + 宣称 E2E → 违规；宣称 E2E 而协议未审核 → 违规；如实披露 → 无缺陷 | **采纳**。 |

### D7 路线未定案是 `AwaitingRouteDecision`，**且不得掩盖缺陷**

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 未定案即一个缺陷 | 一律 Defective | **否决**：§10.2「M0b PoC 后定案」，未定案是**计划内**的诚实状态。 |
| B. 未定案即 Ready | 乐观 | **否决**：会把「外部决定未做」读成「已就绪」。 |
| C. 三态 `AwaitingRouteDecision`/`Defective`/`Ready`，Defective **优先** | 先看审计再看路线 | **采纳**：未定案不掩盖越界，越界也不被未定案冲淡。 |

路线前置条件落在 `ConnectionRoute` 的载荷上：A 需 `https_domain` 与 `certificate`（PWA Service Worker 需安全上下文）；B 需 `app_distribution` 与 `tauri_maturity_verified`。声明某路线而缺前置条件 → 审计报出。

### D8 命令契约的**字段齐备性**与 S09 的**网络行为**分开

§86 INV-14 与 §636 S09 要求远程命令带身份、会话与 epoch、序号、TTL，返回实际执行 ACK，并拒绝观察者执行高危命令。本轮能判的是**描述符里这些字段是否齐备**与**最低角色是否被声明为观察者**；真实防重放、去重、ACK 语义与吊销即时生效属于 S09 的**集成**验收（已 `tested` 于 loopback 面）。

### D9 审计是描述符的纯函数

与 W30/W32 一致：对描述符自身字段做纯函数，报出**全部**命中项，十九条标记逐条可在测试里直接构造；干净描述符审计为空。

### D10 不新增 xtask 命令与证据目录

§30.1 只为 RAG 黄金集指定 `tests/rag-golden`，UI 层为 `tests/ui`；手机监控面的验收是「最小形态通过 S09」——真值来自**真机与 PoC**，不是仓库载荷。**臆造**一个 `tests/mobile-monitoring` 属过度绑定。待 M0b 定案并立项真机交付后再补载体，届时无需改本模块判定。

## 环境边界

判定骨架在 portable（Linux/WSL 逻辑层）可测，测的是**口径**：一份声明的监控面如何判越界、未定案如何表达、如实披露如何不算违规、预览未启用如何不算缺陷。**不含**任何移动端应用、证书、分发、真机与 S09 真机集成；因此 O03 保持 `blocked`，本变更不升级其状态。
