# 设计（w56 智能体 Harness 与开放互操作）

## 1 为什么是「新增第四部分」而不是就地改写 §5/§35

仓库把**行号**当作引用契约：6 篇既有 ADR 以 `§NNN`（行号）形式引用基线，`tests/registry.yaml` 与 `AGENTS.md` 亦然。
V3.6 → V3.7 之所以能安全升基线，是因为它的 8 处改动**全是 1:1 行替换**，总行数不变、行号一一对应。

就地改写 §5（智能体运行时）会把 harness 写得更紧凑，但必然移动行号，进而使既有 ADR 的 `§NNN` 引用**静默失效**——
引用的失效不像编译错误那样会被发现。故本轮沿用 V3.6 → V3.7 的形状：**在文档末尾追加第四部分**，并在 §0.2 加指针。

**唯一的例外是 8 行 1:1 替换**，且这 8 行不是可选的：

- `1c1`、`3c3`：标题与副标题必须携带版本号与日期。
- `29c29`（§0.2）：不指路，第四部分对读者不可见。
- `56,57c56,57`（§1.4）、`624c624`（§16 前导）、`698,699c698,699`（§17.3）：**这三处是发布线与验收的「索引」**。
  若 H 家族不出现在 §1.4/§16/§17.3 的任何一行里，则第四部分的 18 条验收在整个第一部分**没有任何指针**——
  这正是 ADR 0042 决策 4 之后被判定为缺陷的那种「以注册表为准却把整部分从验收视野里抹掉」的形状。
  在既有行内追加（**不新增行**）既解决可见性，又不破坏行号对齐。

## 2 意图识别：分路径，而不是推翻 §5.2

§5.2 的「一次短上下文 LLM，不先做独立分类」是**实时自动路径的延迟取舍**，本身正确；错在它被写成了全局结论，
于是人工辅助、影子评估、节目编排、入站外部请求这些非实时路径没有意图语义。

设计上取**分路径**（§43.1）：实时路径保持不做独立分类器；非实时路径可做显式意图识别，且入站外部请求**必须先判意图**。
这样既不引入实时路径的额外延迟，也不让「不做分类」这条纪律越界。

意图的表示取「**封闭枚举 + 置信度 + 依据引用**」，并把 `unknown` 设为一等取值。理由是三条既有纪律的必然结果：
INV-09 要求模型自报无效力（故依据必须指向装配片段，不能是「模型说它是」）；INV-29 要求意图不构成授权（故意图不得
参与风险判定）；§5.4 要求守门缺失即拒绝外发（故意图只能是 input 阶段的一个输入）。

## 3 语义缓存与 TTS 精确缓存必须分开

§25.4 的键是**为音频复用设计的**：它绑定事实修订，因为音频一旦合成，内容与事实就固定在一起了。
若把语义相似度套到这个键上，就会允许「相似句复用音频」，从而把「事实绑定」这条链断掉——
价格类内容尤其致命。

故设计上强制两类分开（§45.1）：**TTS 精确缓存**（逐字相同 ⇒ 可复用音频）与**语义缓存**（语义相似 ⇒ 只复用文本或候选，
**不复用音频**）。并且三点硬约束：命中不复制授权（INV-30）、命中后必须重跑证据复核、价格/库存/优惠/承诺进禁用域。
禁用域不是新发明，而是把 §5.3「涉及价格、库存、优惠、承诺的回答不参与合并复用」推广到缓存层，与 M04 的既有判据同向。

**命中率与误命中率必须一起报**：只报命中率会把「复用得多」当成「复用得对」（同 §6 分列三类指标的纪律）。

## 4 MCP 映射进既有面，A2A 走独立入口

MCP 的定位是「给模型接工具与资源」，本项目已有两套面承接它，**不需要新造一层**：

- `tools` → 技能（§35），逐工具审核，不信服务端自报的只读或低风险；
- `resources` → 数据源（§34.2 的 `data.query`），一律带来源与时效，不得直接当证据、不得绕过 §6；
- `prompts` → **不得**直接作系统提示（提示是配置产物，变更按 §11.7 的安全相关变更处理）；
- `sampling`（服务端反向调用模型）→ **默认禁用**，启用需管理员授权并计入预算。

关键是**描述漂移**：§35.3 要求 `model_description` 不得含指令性内容，而远端可以随时改描述，所以工具描述是**注入面的一部分**，
其变更必须触发重新审核。这一条是本轮新增的最实质约束。

A2A 与 MCP 常被混用，设计上把区别写进规范（§46.3）：MCP 的调用方仍是本智能体、产出是数据；A2A 的对端会**自行推理与行动**，
产出是另一个主体的结论。故 A2A 必须更保守：入站走**独立入口**且一律按「**外部请求**」处理（不构成用户指令、不构成授权、
不构成值守），默认只在人工辅助模式下响应；出站不得委派 risk_2 及以上、不得委派需要凭据的动作、委派链深度上限初值 1。

## 5 H 家族就地登记，并把规格早就要求的断言真正实现

`openspec/specs/admission-registry/spec.md` 早已写明：注册表 SHALL 覆盖基线的**全部**验收家族，并
「SHALL 断言 M 家族（§37.5、§38.10 共 18 条）全部在册」。实测 `scripts/contracts/registry.mjs` **没有这个断言**——
规格写了 SHALL，实现没做。本轮既然要扩家族到 `H`，就不能让同一处 SHALL 继续悬空。

实现判据（全部可判定、非空洞）：

1. 编号正则扩为 `(S|R|A|B|O|P|M|H|X)[0-9]{2}`；JSON Schema 的 `acceptance.id` 与 `mapping.targets` 两处 pattern 同步。
2. **家族在册断言**：对每个「基线定义了完整编号段」的家族（当前为 M 18 条、H 18 条）断言
   `{家族}01…{家族}NN` **逐号存在**；缺号即失败并**指名缺哪个号**；同时断言没有超范围的多余号
   （拒绝 `B01a` 这类从既有条目拆分出的编号，沿用既有纪律）。
3. **非空洞守卫**：测试注入「删掉 H05」与「把 H 家族全部删掉」两种注册表，断言两种都被抓到；
   若守卫在缺号时仍通过，则该测试必须失败。
4. M 与本轮新增的 H **分开计**，不合并成「至少 36 条」这种能被互相掩盖的口径。

## 6 不新增契约名，且不靠新契约绕开验证

MCP 的四个概念都能落到**已有**的承接面：`tools` → 技能（`skill.invoke@1`，已 frozen）、`resources` → 数据面
（`data.query@1`，已 Draft）、`prompts` → 配置、`sampling` → 授权。故 MCP **不需要新契约**。

A2A 则相反：协议版本与认证方式**待验证**（§35.2 已如实标注）。此时写下一个 `a2a.*` 的契约名，会产生**半声明的 draft**——
没有请求/响应形状、没有流语义。W52 的能力目录纪律明确禁止它：半声明会让 `stage` 字段失去意义，等于把「已冻结」与
「未冻结」混为一谈，并把「未验证」伪装成「已登记」。故 A2A 契约待协议验证后随 W62 加入目录；本轮 H13/H14 在注册表里
`contract` 留空（沿用 M10/M12 的先例）。

**副产品是一处必须如实登记的基线-目录不一致**：§20.6 把 `memory.access@1` 列为「保持 Draft」，而
`schemas/catalog/capabilities.json` 已标 `frozen`。第四部分以目录为准（§42.6），**不改 §20.6 原文**，
并把该不一致写进文档与验收，而不是悄悄删掉那一句。

**因此能力目录与全部生成物零改动**：CI 的 `cargo xtask schema --check` 断言生成无漂移，
`crates/nai-contracts/src/generated/catalog.rs` 的 `DRAFT_CAPABILITY_IDS` 不应因本变更变化。

## 7 验证命令与环境边界

```bash
cargo xtask check --profile full      # 工程门控 + 前端门控（含注册表、契约目录、tests/ui、tests/platform）
cargo xtask check-deps                # 期望：19 workspace packages（不变）
openspec validate w56-agent-harness-and-interop --strict
openspec validate --all --strict --archived
```

环境边界（如实）：本机为 Windows；Rust 测试目标需先预热两个构建目标以避开既有的间歇性 `LNK1104`；
前端门控依赖仓库根层的依赖副本；两者都是**主机事实**，不读作变更的通过/失败依据。
真实 MCP 服务端、真实 A2A 对端、真实模型与真实平台 SDK **均未接入**，任何「互操作已可用」的表述都不在本变更范围内。
